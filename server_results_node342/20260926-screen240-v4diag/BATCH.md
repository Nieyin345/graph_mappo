## 判读

**筛选**：三模型里 **v4 显著更差**（3/3 训练种子同向，t=−11.85）；**v2 与 v3 不可区分**
（Δ=−0.004，远低于分辨率）——只能说「n=3 下测不出」，**不能报「v2 更好」**。
lr 三档（1e-5/3e-5/1e-4）**全部测不出差异**，默认 3e-5 保持不变。

**分解**：v4 的损失由 **需求隔离（−0.060）** 与 **去掉两个边特征（−0.045）** 两项构成，
二者近似可加。**两项的损失在 BC 起点就已全部造成**，PPO 之后几乎不变
⟹ **问题在观测表示，不在训练**。`stock`（库存边）与 `nofuse` 无害。

**两条设计假设被反驳**：
1. 「需求隔离让 node encoder 只看物理层」——隔离后策略连模仿专家都做不到，
   说明**专家决策依赖需求信息**。
2. 「`relay_importance` / `req_hop` 是冗余特征」——对模仿专家有实质贡献。

## 追加 · v6 臂与 `_obs_class` 修复（2026-09-26 晚）

**v6 是什么**：v3 的**需求隔离**变体——需求边不进 GNN 消息传递
（`model.encoder.fuse_demand_to_node: false`）。回答的问题：**需求边之间经由
共享节点的互相融合，是否会导致结果下降**。对照 = 本批的 v3 臂（0.7599）。

**v6 ≠ 严格单变量（已实测，见 `.tmp/probe_v6_minimality.py`）**：

| | 参数量 |
|---|---|
| v3 默认 | 1,496,708 |
| v3 + `fuse_demand_to_node: false` | 1,496,708 |
| **v6** | **1,200,388** |

v6 除隔离外**删掉 12 个 demand MLP 张量（−301k）**并**新增
`pair_endpoint_proj`（+49k）**（把该对两个端点 GS 的纯物理节点向量融进需求 token，
作为「需求不进 GNN」的补偿）。**这个补偿是新机制**，不是最小改动。

机制上「单开开关就够了」已由扰动探针证实（`.tmp/probe_v6_minimality.py`）：
v3 关掉开关后，扰动 demand[0]，**demand[1:] 变化 = 0.000e+00**、节点/物理边变化
亦为 0 ⟹ 需求边之间的融合已被完全切断。v6 的层在 demand 非空时直接 raise。

**⚠ v6 不是"新模型"，是 v4diag `nofuse` 臂的重实现**：两者是同一个改动，
两个独立实现 / 独立 BC / 独立训练，读数吻合到 0.001（见下表）。**v6 的独立
价值 = 交叉验证**，不是新信息。

### 结果（窗 A，15 请求种子，240 步）

| 臂 | 实现 | BC 起点 | PPO 终点 | vs v3 配对 |
|---|---|---|---|---|
| v3（对照） | — | 0.7560 | 0.7599 | — |
| **v6**（隔离，新实现） | 独立模型 | 0.7571 | **0.7491** | **Δ=−0.0108, t=−2.59 ⟹ 测不出** |
| v3 `nofuse`（隔离，旧实现） | v3+配置 | 0.7506 | 0.7484 | Δ=−0.0116 ⟹ 测不出 |

**两个独立实现给出同一读数**（−0.0108 vs −0.0116）⟹ 隔离的效应是**真实的、
可复现的、但很小**（约 −1 点），且 **n=3 下测不出**。逐训练种子差
`[−0.0056, −0.0077, −0.0191]` 三种子**同向为负**。

⚠ **与 `iso`（特征）臂混淆的风险**：本批的 `iso` 臂是**关掉四个 node 的
`include_demand_*` 特征**（需求信息从节点输入整个拿掉），测出 **−0.0596**
（t=−8.09，可分辨）；`nofuse`/v6 才是**只改 GNN 融合**。两者不是一回事，
引用时务必分清（`iso` 是特征级、`nofuse`/v6 是结构级）。

### `_obs_class` 修复（配套，commit 待提交）

`supervised_train_pg_phased._obs_class()` 原先**硬编码只认 `"v3"`**，其余
落到基类 `qkd_rl/env/graph_builder.GraphObservation`——而基类**没有**
`pair_path_edge_masks` / `pair_path_weights`（grep 计数 0），v4/v6 的
pair_path 打分器却要读它们。

- **影响范围**：仅 `--data-dir` 轨迹回放路径。**v6 的 BC 未受影响的**——启动脚本
  未传 `--bc-data`，走 `env.reset()` 在线路径，obs 由
  `model_zoo.graph_builder_class(config)` 按 `model: v6` 分派到 v6 自己的 builder。
  探针实测（`.tmp/probe_v6_bc_obs.py`）：v3/v6 在线 obs 的 pair_path masks
  **均为 n=11、非零 16，完全一致**。
- **修复**：`_obs_class` 改为按 model 名从 `model_zoo.<m>.graph_builder` 取类
  （与在线路径**同源**）；`rebuild_obs` 改用「类是否声明该字段」判定，
  避免给 v2（字段集与基类相同）误加。
- **回归测试**：`tests/test_bc_obs_class.py`（9 passed）。含一条守门：
  「开 `pair_path_attention` 的模型，其 obs 类必须声明 pair_path 字段」，
  防止未来静默复发。

## 附录 · PPO 是否真的在更新（**本批最重要的副产品**）

按项目自身判据（`docs/实验产物规范.md` §7：**`clip_frac > 0` 或 `kl > 1e-4`**，
**不能**用 `kl > 0`），本批**每个臂、每个种子**都判定「训练发生」：

| 臂 | max kl | max clip_frac |
|---|---|---|
| v2 | 5.3–6.0e-3 | 0.28–0.31 |
| v3 | 5.5–5.6e-3 | 0.27–0.29 |
| v4 | 4.0–4.5e-3 | 0.23–0.25 |
| v6 | 6.9e-3–1.2e-2 | 0.32–0.43 |
| v4diag 各臂 | 4.9e-3–7.1e-3 | 0.26–0.35 |

而 `docs/当前状态与优化方向.md` §3 P0#0 记录：**冻结批、`retrain8_*`、
`diagnostics/probe-*`、v4 全部 `clip_frac=0` 且 `kl≈1e-5`**，即 PPO 从未更新。

⟹ **本批是本项目第一次 PPO 真正在训练**。推论：

1. 先前的 0.75 级读数只能读作「**BC 起点 + 噪声**」；本批的 0.7641/0.7599/0.6911
   是**首个真实 PPO 读数**，两者**不可并列**。
2. **P0#0 在本配置下解决**：`minibatch_size=256` + 8 集×240 步 ⟹ `nb=8`。
3. **但 PPO 在训练分布上只前进约 +2~4 点（首5轮 vs 末5轮，12 条种子-run 全同向）**，
   PPO 后 vs BC 起点在窗 A 几乎不动（v6 −0.0080、nofuse −0.0023、stock −0.0044）。
   ⟹ **瓶颈不在「PPO 能不能动」这个开关，而在训练 regime 与评测 regime 不匹配**
   （训练 0–295 天起始日 / 0.83–0.86 饱和；验证 330–365 天 / 0.75）。
