## 设计要点

**归属**：v4 = **需求隔离 + 库存边**变体。相对 v3 的改动全在观测与 GNN 消息传递上
（见本目录 `config.yaml`；代码与服务器工作树逐字节相同，sha256 已核对）：

- 节点特征**去掉全部需求聚合**：`include_demand_in/out/queue_pressure/recent_demand: false`
- GNN **不让需求边进入**：`fuse_demand_to_node: false`
- 观测图**并入有库存的边**（含速率 0）：`include_stocked_edges: true`
- 去掉 `relay_importance` / `req_hop` / `on_pending_path` 三个特征
- `include_pair_history: false`、`history_encoder.enabled: false`（打开会直接 raise）

### ★★ 原因已定位：问题在**观测/动作表示**，不在 PPO

评估 **BC 起点**（PPO 之前，各模型仅 8 集模仿专家），协议与主评估逐字段相同
（窗 A / 15 请求种子，已核对 `protocol` 相等）：

| 模型 | BC 起点 | PPO 后（20 轮） | 变化 | BC 损失 |
|---|---|---|---|---|
| v2 | 0.7639 | 0.7641 | +0.0002 | 4.007 |
| v3 | 0.7560 | 0.7599 | +0.0039 | 4.027 |
| **v4** | **0.7024** | 0.6911 | **−0.011** | 4.028 |

**v4 的劣势在 BC 起点就已存在**（0.7024，比 v2 低 0.062）：8 集行为克隆足以把
v2/v3 带到 0.756–0.764，却只把 v4 带到 0.702。PPO 随后还在 v4 上**掉**了 0.011
（v2/v3 都微涨）。⟹ **与 PPO 优化无关，是 v4 的表示本身的问题。**

⚠ **BC 损失与成功率方向相反 —— 已解释（见下「为什么会有差距」）**：
更差的臂 BC 损失反而**更低**（iso 3.962、nofeat 3.929 vs 对照 4.007），
因为策略转向了「多产密钥」这个更容易拟合的代理目标。**不是过拟合，也不是
「学不动」——是学到了对的目标之外的、更容易优化的东西。**

### v3 ↔ v4 的完整差异（代码级，逐项核对过）

⚠ 这不是「v3 调了几个开关」—— **消息传递层被重写了**。按文件：

| 文件 | 差异 | 性质 |
|---|---|---|
| `model.py` | 2 行（仅 docstring） | 无 |
| `model_impl.py` | **378 行 / 35 个 hunk** | **结构性** |
| `graph_builder.py` | 140 行 | 掩码定义 + 库存边 |

**`model_impl.py` 的三处结构改动**：

1. **消息传递层被替换**：v3 的 `EdgeConditionedGraphLayer` 有 `_node_message` /
   `_edge_message` 两个方法，**同时聚合物理边与需求边**（`fuse_demand_to_node`
   可开关）；v4 的同名类删掉这两个方法，并在构造时就**禁止**需求边进入：
   ```python
   if fuse_demand_to_node:
       raise ValueError("v4 never passes demand edges through the GNN")
   ```
   v4 的 `forward` 还会断言输入里没有需求边（`if demand_emb.size(0): raise`）。
   ⟹ **v4 的 GNN 只看物理边**。

2. **需求对编码方式不同**：v4 在 `PairPathEncoder` 里把需求边按**对**取均值
   （`pair_raw = demand_emb.reshape(-1, 2, H).mean(dim=1)`）再编码，v3 无此步。

3. **`PairPathAttentionScorer`（actor 打分头）逐字节相同** —— 所以差距**不在
   actor**，在它拿到的输入表示。这与「问题在观测表示」的结论一致。

**配置级改动（5 项）与维度后果**：

| 改动 | v3 | v4 | 维度影响 |
|---|---|---|---|
| 节点需求特征 4 项 | 全部 true | **全部 false** | node **17 → 11**（−6：`recent_demand` 占 3 个窗口 + in/out/queue 各 1） |
| `relay_importance` / `req_hop` | true / true | **false / false** | edge **44 → 39**（−5） |
| `include_stocked_edges` | false | **true** | 观测图并入库存边（含速率 0） |
| `fuse_demand_to_node` | true | **false** | 见上面第 1 条 |
| pair_path 掩码定义 | 距离和判据（含 `s-a-x-a-t` 类绕行） | **≤max_hops 简单路径并集**（DFS 拒死端） | 代码级 |

**⟹ 这个 −0.073 是上述改动的合力。** 已测的分解（下一节）把其中两项**量化**了；
掩码定义那一项是代码级、无法在 v3 上单变量打开，**仍未测**。

### ★★★ 「为什么会有差距」：策略拿掉需求信息后转向**多产密钥**，而非服务需求

上面回答了「是哪两项」，这一节回答「为什么」。**注意它推翻了「表示更难学」这个
想当然的解释**——恰恰相反。

**反直觉的事实**：表现更差的臂，**BC 损失反而更低**（同口径：32 批 / 8 集）：

| 臂 | BC 损失 | BC 起点 SR |
|---|---|---|
| v3 对照 | 4.007 | 0.7560 |
| **iso** | **3.962**（更低） | **0.6905** |
| **nofeat** | **3.929**（最低） | 0.7067 |
| stock | 3.975 | 0.7685 |

在 v3 家族内**损失越低 → 成功率越低，近乎单调**。所以不是「学不动」，是**学到了
一个更容易拟合、但不对的目标**。

**两侧独立测量指向同一机制**（窗 A，3 种子）：

| 指标 | v3 对照 | iso | nofeat | 含义 |
|---|---|---|---|---|
| generated_keys | 2121M | **2288M (+8%)** | 2303M (+9%) | 产出**更多** |
| served_keys | 14M | **13M** | 13M | 服务**更少** |
| `key_efficiency`（=generated/served，越小越好） | 152.3 | **181.7 (+19%)** | 178.4 | 每服务 1 单位需求**烧 19% 更多**密钥 |
| mean_activated_edges/步 | 57.8 | 56.1 | 56.3 | 激活边数**没变** |
| 需求路由重叠度（确定性 rollout 探针） | 0.0276 | 0.0261 | 0.0277 | **几乎相同** |

⟹ **不是「激活更多边」，也不是「激活的边离需求更远」**（重叠度持平）。
逐项算：**每条激活边的产出，iso/nofeat 比对照高 11%**（125.8 vs 112.9 密钥/边）。

**机制**：拿掉需求聚合后，策略不再知道需求在哪，于是**转为最大化「密钥生成量」
这个它在观测里还能看到的代理指标**——多激活高产出率的边。产出量高**恰好让逐决策
平均 NLL 更友好**（分布更铺开、更好拟合），所以 BC 损失更低；但服务量反而下降，
因为**密钥产在了不对的需求上**。

**这是「代理指标被优化」而非「表示学不会」**：任务目标是 served，策略优化的却是
generated。

### 归因分解（把改动逐项加回 v3）

v3 的代码本就支持这些配置开关，所以可单测；每臂 3 训练种子 × 20 轮，
配对对 v3 对照，临界 t=4.303：

| 臂 | 改动 | **BC 起点** | vs v3 | PPO 后 | vs v3 |
|---|---|---|---|---|---|
| v3 对照 | — | 0.7560 | — | 0.7599 | — |
| **iso** | 需求隔离（4 个 include_demand_*） | **0.6905** | **−0.0655 (t=−7.85)** | **0.7003** | **−0.0596 (t=−8.09)** |
| **nofeat** | 去 relay_importance + req_hop | **0.7067** | **−0.0493 (t=−13.03)** | **0.7151** | **−0.0449 (t=−7.09)** |
| nofuse | fuse_demand_to_node=false | 0.7506 | −0.0054 (测不出) | 0.7484 | −0.0116 (测不出) |
| stock | include_stocked_edges=true | 0.7685 | +0.0124 (测不出) | 0.7641 | +0.0041 (测不出) |
| v4 全改 | 以上全部 | 0.7024 | −0.0537 | 0.6911 | −0.0689 (t=−20.80) |

**结论**：

1. **主因 = 需求隔离（−0.060）**，次因 = **去掉 relay_importance/req_hop（−0.045）**。
   两者之和 ≈ −0.105 略超 v4 实际的 −0.069 ⟹ 有轻微正交互补（stock 的 +0.004 抵消一部分）。
2. **两项的损失在 BC 起点就已全部造成**（iso 起手 −0.066、nofeat −0.049），
   PPO 之后几乎不变 ⟹ **坐实「问题在观测表示，不在训练」**。
3. **`stock` 与 `nofuse` 无害**（stock 在 BC 起点还略正 +0.012，但 t=4.13 未过临界）。

**设计含义（两条假设被反驳）**：

- **「需求隔离让 node encoder 只看物理层」是错的**：去掉需求聚合后，策略
  **连模仿专家都做不到** ⟹ 专家的决策**依赖需求信息**，不能隔离掉。
- **「relay_importance / req_hop 是冗余特征」是错的**：它们对模仿专家有实质贡献。

⚠ **本分解未覆盖的一项**：v4 的 `graph_builder.py` 把 pair_path 掩码定义从
「距离和判据」改成了「≤max_hops 简单路径并集」——这是**代码级**改动，无法在
v3 上单独打开，**不在本波内**。若要彻底归因，需为它单独建臂。
