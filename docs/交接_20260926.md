### 成果 4 · 测出天花板（§10.9）—— **本次最重要的结论**

**问题**：模型停在专家克隆水平（0.76），推不动。是**结构不行**，还是**专家已经到顶**？

**先排除坏工具**：`outputs/eval/milp_ub*/summary.json` 报 `success_rate_upper_bound` **0.11–0.17**，
**低于**专家 0.7674 —— 真上界不可能低于已达值。`receding_horizon_milp.py` 自己注释说它除以
**modeled demand** 而非 arrived demand，是**另一个量**。**不要用这三个数字。**

**方法**：把 `docs/训练诊断记录.md` 探针 N 的严格分解移植到**冻结窗 A**
（脚本 `.tmp/probe_ceiling_frozenA.py`）。

**结果（15 种子，量加权）**：

| 桶 | 请求数 | **占到达量** | 含义 |
|---|---|---|---|
| served | 2186 | **73.77%** | 已服务 |
| C（曾全通、没搬完） | 152 | 8.73% | 策略相关 |
| B_avail（窗口内从未全通） | 427 | **16.11%** | 物理受阻 |

- **C 桶里 8 成是速率硬约束**：`bn_sum >= 剩余量`（独占窗口也搬得完）只有 **13 条/0.97%**；
  其余 **139 条/7.76%** 的 `bn_sum` 不够 ⟹ **C 桶「策略可争」仅 ~1 点**。
- 交叉表：**库存不够+物理够 = 2.45%**（策略能挣的那一格，完成度仅 0.374）；
  物理不够 = 5.31%（攒不出来）。
- ⟹ **现实策略天花板 ≈77–78%，专家 0.7674 已吃到 ~96–98%。**
  **真正「有货可攒却没攒」只有 2.45% 到达量。**

**端口预算（`.tmp/probe_port_headroom.py`）**：

| 量 | 值 |
|---|---|
| 端口上限（每节点 ≤1 Tx 且 ≤1 Rx；节点**可同时收+发**） | **88 边/槽**（**不是 44**） |
| 专家实际激活 | 60.58 边/槽（**占用 68.8%**） |
| **剩余预算** | **~27.4 边/槽（31%）** |
| 激活边在**某个 pending 请求路径上** | **1.5%** |
| **与当前请求无关** | **59.67 边/槽（98.5%）** |

**★ 这条推翻了会话前期的一个判断**：曾以为"专家是反应式、根本不预置"。
实测**专家每槽激活 60 条边、其中 59 条与当前请求无关** —— 它**早就在大量铺货**，
只是**无脑广撒网**（不区分哪个 GS 对将来会要货）。

## 2. 用户提出的新模型设计（**尚未实现，这是下一步的核心**）

用户在会话末尾提出了一个**两阶段模型**，并明确要提前生成密钥来"为未来铺货"：

> 第一个阶段和现在的 v3 差不多，通过注意力机制服务之前的请求（`max_hops` 4→2，
> 只选"能让通道完整"的边）；第二个阶段对**第一阶段没选择到的边**再做全局打分，
> 根据全局情况**为未来提前攒密钥** —— 相当于第一阶段为了过去，第二阶段为了未来，
> 且第二阶段是"第一阶段选剩下的"。

**这个设计在端口预算上成立**：实测第一阶段（专家式）只用 68.8% 端口，
**剩 31%（27.4 边/槽）** 可作为阶段二的预算。

**关键前提问（用户认同的方向，但未验证）**：模型不知道未来请求是什么，
**要用 LSTM 根据历史请求趋势预测未来**，然后定向生成。

**基础设施已经齐备、只是没开**（详见 `configs/train_hist.yaml` 头部论证）：
- `features.history_encoder`（LSTM）**整块 `enabled: false`**；
- `HistoryBuffer` 已跟踪节点 4 通道 **`arrived / served / failed / qkp_total`**
  —— **「节点历史到达量」正是预测未来需求所需的信息**；
- `GraphBuilder` 已把窗口装进 `GraphObservation`；`configs/train_hist.yaml` 已写好
  （只开节点通道、不开边通道，`node_dim 17→81`）。
- 边特征里已有 `prediction_horizon: 6` 的**未来**窗口（速率/可用性），
  但那是「链路会不会通」，**不是「将来要多少货」**。

## 3. 下一步该做什么（**建议的顺序**）

> **⚠ 先做便宜的判定，别直接写模型。** 若预测不出来，两阶段模型会退化成"另一种盲铺"。

### 第 1 步（便宜、决定后续）：需求可预测性判定

**问题**：历史上每个 GS 对的到达率，能否预测未来需求？

- 用冻结窗的请求流，算"过去 N 槽的到达率 → 未来 M 槽的到达率"的相关性 / top-k 命中率。
- 若 top-k 命中率高 ⟹ LSTM 可行，**值得建两阶段模型**；
- 若需求太随机 ⟹ **该方向关闭**，别写模型。

### 第 2 步（若第 1 步通过）：实现两阶段模型

- 阶段一：现有 v3 注意力，`max_hops` 4→2（只补全通道）。
- 阶段二：对**未选中的边**做全局打分，用 LSTM 的历史编码 + 剩余端口预算，
  定向为未来铺货。
- 建议先只**打开 `history_encoder`（= 跑 `configs/train_hist.yaml`）**，看单开 LSTM
  有无增益，再决定是否建两阶段。**这是最便宜的一个动作。**

### 备选方向（若上面都关闭）

- **P0#0d**：论文口径统一（绝对 SR 强依赖种子集，改用「相对专家的 ΔSR」）—— 低成本。
- **P0#0b**：中途错边的服务通路归因 —— 唯一还开着的机制性缺口。
- **`normalize_by_arrived_demand: true`**：唯一未被否决的奖励改动（会消除跨回合
  奖励尺度漂移）。判据：若它仍不改变 success，则「奖励口径」可正式关闭。

## 4. 交接时必须知道的坑（本次踩到的）

1. **`nx.widest_path` 在 networkx 3.4.2 里不存在**（抛 AttributeError）。
   原探针 N 调它，外层 `except Exception: return 0` **静默把每个瓶颈变 0**，
   全表判成"100% 物理不可服务"（与专家服务 80% 直接矛盾）。
   **教训与项目既有红线一致：`except` 吞异常 + 「不是上界的上界」= 方向判反。**
   改用**最大生成树上的最短路**。
2. **冻结窗的槽号是绝对值**（`env.t ≈ 484746`），而诊断窗从 0 起算。
   探针用请求的绝对 `arrival_t` 索引数组 ⟹ 永远越界 ⟹ 判成"从未全通"。
   修法：`slots_components(env, horizon, t0=env.t)` + 所有请求时间按 `t0` 归一，
   **且 `t0` 必须在 `env.reset()` 之后取**（reset 才决定随机起日）。
3. **`outputs/eval/milp_ub*` 的上界是坏的**（见成果 4）。不要引用。
4. **`server_results_node342/**` 在 .gitignore 里**，只 un-ignore 了本批的记录文件
   （`20260926-screen240-v4diag/` 的 BATCH.md + eval JSON + v6 train 记录）。
   **checkpoint 不入 git。**
5. **本机不跑 Python**（`.claude/hooks/no_local_python.sh` 会拦，exit 2）；
   一切在服务器（SSH 别名 `qkd`，**地址是动态的**）。探针写 `.tmp/`，
   `scp` 到服务器 `/tmp/` 再 `cp` 进 `.tmp/` 跑。
6. **并发墙是线程不是内存**：`cpu_threads=16`（配置**覆盖** `OMP_NUM_THREADS` 环境变量），
   所以 `MAX_CONCURRENT × 16 ≤ nproc(64)` ⟹ **最多 4 并发**。
7. **门/判据类代码必须打印它自己的输入**（项目曾因 `live_runs()` 恒返回空而
   "条件恒真、无条件启动"）。本次三个探针都打印了判读依据。
