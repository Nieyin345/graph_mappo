# 训练结果审查与下一步建议

## 针对《饱和与加难度汇报.md》的最终建议

> 核心结论：现在不建议直接通过“增大请求数量”来解决训练饱和。
>
> 当前更像是三个问题叠加：
>
> 1. BC 起点已经非常强，PPO 没有找到明显高于 BC 的策略方向，并出现了策略漂移；
> 2. 训练 regime 与验证 regime 存在明显差异，且验证侧专家本身就只有约 0.767，因此验证侧低 SR 不能简单解释成“RL 没训练够”；
> 3. 当前 reward 对 served key 最敏感，但对生成效率、库存结构和部分失败行为约束较弱，PPO 存在 reward-neutral / low-cost policy drift。
>
> “加大请求强度”可以作为后续压力测试或训练数据增强，但不应该作为当前第一步修复方案。

---

# 1. 当前结果首先说明什么？

报告给出的结果是：

```text
训练 regime:
    Expert ≈ 0.9+
    RL ≈ 0.9226

验证 regime:
    Expert ≈ 0.7674
    RL     ≈ 0.7665
```

同一 regime 内：

\[
RL \approx Expert
\]

因此最重要的信息不是“RL 只有 0.77”，而是：

\[
\boxed{\text{验证集上 RL 已经基本追平专家}}
\]

---

# 2. “第 1 轮就 0.94”不应该简单解释成“训练很容易”

第一轮：

\[
SR\approx0.94
\]

后面：

```text
u1  ≈ 0.940
u10 ≈ 0.929
u20 ≈ 0.922
u30 ≈ 0.908
```

而且没有持续上升趋势。

这更准确地说明：

\[
\boxed{\text{BC 初始化已经把策略放到了高质量区域}}
\]

不是 PPO 从随机策略快速收敛到了 0.94。

---

# 3. 但“训练侧长回合所以容易”目前证据不足

训练：

```text
0–295 天
1440 steps
```

验证：

```text
330–365 天
240 steps
```

长度确实不同，但还有一个更强的证据：

```text
训练 Expert ≈ 0.9+
验证 Expert ≈ 0.767
```

也就是说即使不用 RL：

> 专家本身换到验证 regime 后也明显下降。

因此至少存在：

\[
\boxed{\text{场景/分布差异}}
\]

不能把全部差异归因于 episode 长度。

建议后续把差异拆成：

\[
\Delta_{total}
=
\Delta_{environment}
+
\Delta_{policy}
+
\Delta_{horizon}
\]

而不是直接说“长回合容易”。

---

# 4. 当前真正值得警惕的是 PPO 在破坏 BC

报告给出的训练轨迹：

```text
u1 → u30

success_rate:
0.9400 → 0.9077

generated_keys:
7,771,638 → 6,858,118

waiting_keys:
308,774 → 433,486

failed_keys:
4,494 → 7,018

qkp_utilization:
0.1055 → 0.0887
```

这组数据比“饱和”更值得关注。

因为它表现为：

\[
\boxed{
SR\downarrow,\quad
Generated\downarrow,\quad
Waiting\uparrow,\quad
Failed\uparrow
}
\]

说明 PPO update 没有产生持续增益，反而发生了：

\[
\boxed{\text{BC policy drift}}
\]

---

# 5. 可能的根因：reward 对部分维度不敏感

已有 decomposition：

```text
served       96.5%
urgency       1.9%
failed        1.3%
storage       0.17%
keep_active   0.09%
```

因此 reward 的绝大部分信号来自：

\[
served\_keys
\]

而：

```text
generated_keys
waiting_keys
inventory efficiency
```

没有强约束。

于是可能发生：

```text
BC
 ↓
高质量 KeyGen
 ↓
PPO 修改少量 Action
 ↓
短期 served_keys 没有立刻明显下降
 ↓
策略逐渐偏离 BC
 ↓
长期 waiting / failed 增加
```

这可以解释为什么：

> 生成量下降，但模型一开始仍能保持较高 SR。

---

# 6. 现在不要因为这个现象马上改 Reward

当前正在做的是：

> DemandResidual 的单变量结构实验。

如果同时修改：

```text
Model
+
Reward
```

那么实验失去因果解释。

因此：

\[
\boxed{\text{当前 DemandResidual 实验先冻结 reward}}
\]

reward stabilization 应作为独立实验。

---

# 7. 第一优先级：做 PPO Drift Diagnostic

先不要加请求，不要重训。

用同一个 BC checkpoint 比较：

```text
BC/u0
u1
u5
u10
u20
u30
```

记录：

```text
success_rate
served_keys
generated_keys
waiting_keys
failed_keys
qkp_utilization
```

再记录 PPO 本身：

```text
approx_kl
clip_fraction
entropy
policy_loss
value_loss
explained_variance
mean_advantage
advantage_std
```

目的：

> 判断是“PPO 更新过猛”，还是“低 KL 下慢性策略漂移”。

---

# 8. 如何解释 Drift Diagnostic

## 情况 A：KL 很快升高

同时：

```text
entropy 快速下降
SR 快速下降
```

更像：

> PPO update 太激进。

这时后续应该考虑：

- 更小 learning rate；
- 更少 PPO epochs；
- 更严格 target KL；
- 更弱/更合理的 policy update。

---

## 情况 B：KL 很小，但 SR 慢慢下降

同时：

```text
generated_keys ↓
waiting_keys ↑
```

更像：

> policy 在 reward 不敏感方向上发生低幅漂移。

这时更值得研究：

- BC/KL anchor；
- 早停；
- reward credit assignment；
- Action/Decoder stability。

---

# 9. 必须增加一个 BC Action Drift 指标

对于完全相同 observation：

```text
BC policy
vs
PPO checkpoint
```

比较：

```text
Tx/Rx action agreement
selected arc overlap
top-k arc overlap
```

例如定义：

\[
Overlap=
\frac{|E_{BC}\cap E_{PPO}|}
{|E_{BC}\cup E_{PPO}|}
\]

然后看：

```text
BC → u1
BC → u10
BC → u30
```

这能回答：

> PPO 是否真的已经改变了大量 KeyGen 决策。

---

# 10. 如果 Action Drift 很小但 SR 已下降

重点查：

> 少量关键边的改变是否造成服务瓶颈。

这会直接指向：

\[
\boxed{\text{Decoder / edge-set selection}}
\]

而不是“整体 policy 学坏”。

这也是之前把 Decoder 放在 Priority 3 的原因。

---

# 11. 如果 Action Drift 很大

可以单独做 PPO 稳定性实验，例如：

\[
L=L_{PPO}+\beta D_{KL}(\pi_\theta||\pi_{BC})
\]

或者早期加入：

\[
L_{BC}
\]

但：

\[
\boxed{\text{不要和 DemandResidual 同时改}}
\]

否则无法知道提升来自哪里。

---

# 12. 先做验证失败归因，比“加请求”更重要

当前验证：

```text
Expert ≈ 0.7674
RL     ≈ 0.7665
```

二者基本打平。

这说明：

> 当前验证瓶颈很可能不只是 RL 能力。

应该把失败请求/失败时隙拆成：

### A. 物理不可服务

例如：

```text
visibility
topology
physical disconnection
```

### B. 路径存在但库存不足

### C. 生成能力不足

### D. 有可服务机会，但 Actor 选择了不好的生成边

### E. 其他规则造成失败

其中真正和 DemandResidual / Decoder 最相关的是：

\[
C,D
\]

如果大多数失败属于 A：

> 加更复杂的 Attention 也不会解决。

---

# 13. 建议增加一个“边选择 Oracle Diagnostic”

不训练新模型。

只对验证失败状态做离线分析：

> 假设在当前候选边集合上，可以得到更好的可行 edge set，理论上最多能恢复多少 success？

目的：

\[
\boxed{
\text{估计 KeyGen decision 的可争空间}
}
\]

例如：

```text
oracle 只能提升 0.5 pt
```

那么 DemandResidual 很难带来大收益。

如果：

```text
oracle 可以提升 5 pt
```

说明：

> 当前确实存在大量 KeyGen / Decoder 可争空间。

---

# 14. 关于“增加请求数量/强度”

当前不建议立即进行。

历史扫描已经显示：

```text
arrival_rate:
0.80 → 0.08

SuccessRate:
0.8247 → 0.8780
```

需求降低十倍只改变约：

\[
+5.3\text{ points}
\]

说明需求拥塞只贡献一部分差异。

其他限制更可能来自：

```text
visibility
topology
物理可达性
```

所以：

\[
\boxed{
增加请求量不会创造新的可争空间
}
\]

它只是把拥塞部分放大。

---

# 15. “加难度”的正确用途

如果以后加请求强度，应该把它定义成：

\[
\boxed{\text{Stress Test / Training Augmentation}}
\]

而不是：

\[
\boxed{\text{解决当前训练饱和}}
\]

两者不是一回事。

---

# 16. 如果后续需要增加训练难度，不能污染 holdout

验证：

```text
330–365 天
```

继续严格留出。

不要为了提高训练覆盖率直接把验证天数加入训练。

否则：

> 泛化实验会失去意义。

---

# 17. 更合理的训练场景增强

如果后续确实决定增强训练多样性，优先考虑：

### 负载增强

```text
arrival rate
request amount
```

### Deadline / urgency 增强

```text
不同 expiration distribution
```

### Burstiness

```text
突发请求
```

### Visibility / topology augmentation

```text
cloud blocking
visibility gaps
```

相比只做：

```text
arrival_rate ×2
```

这些变化能覆盖更多真正不同的训练状态。

---

# 18. 如果要做 Load Augmentation，不要只训练一个更高负载

不要简单：

```text
训练 arrival_rate = 1.6
```

更建议训练侧混合多个负载：

```text
0.8
1.0
1.2
1.5
```

随机采样。

目的：

\[
\boxed{
让 policy 学到不同 congestion regime
}
\]

而不是只适应某个新的固定负载。

---

# 19. 但是现在暂时不要做 Load Augmentation

当前首先要回答：

\[
\boxed{
PPO 为什么从 BC 高质量起点开始后反而下降？
}
\]

以及：

\[
\boxed{
Validation 剩余失败到底有多少是 KeyGen decision 可争？
}
\]

这两个问题比“加请求”更基础。

---

# 20. DemandResidual 实验应该怎样解读

非常重要：

如果 baseline：

```text
BC ≈ 0.94
u30 ≈ 0.91
```

而 DemandResidual：

```text
BC ≈ 0.94
u30 ≈ 0.93
```

即使它没有超过 BC：

> 也可能说明 DemandResidual 提高了 PPO 的稳定性。

因此不能只比较：

```text
最终 baseline SR
vs
最终 residual SR
```

还应比较：

```text
BC/u0
best checkpoint
final checkpoint
```

---

# 21. 建议正式实验报告同时给三个差值

每个 seed：

\[
\Delta_{BC}
=
SR_{trained}-SR_{BC}
\]

以及：

\[
\Delta_{Attn}
=
SR_{Attn}-SR_{Baseline}
\]

最好同时给：

```text
BC → best
BC → final
Baseline → Attn
```

这样可以区分：

### 能力提升

> 真正比 BC 更好。

### 稳定性提升

> 虽然没有超过 BC，但 PPO 退化更少。

### 没有效果

> 两组都同样退化。

这三种情况完全不同。

---

# 22. 当前最值得研究的实验路线

## Experiment 1：PPO Drift Diagnostic

不改变模型。

```text
BC / u1 / u5 / u10 / u20 / u30
```

---

## Experiment 2：Validation Failure Attribution

按：

```text
A 物理不可行
B inventory 不足
C generation 不足
D edge selection 不合理
E other
```

统计。

---

## Experiment 3：DemandResidual

冻结：

```text
reward
environment
holdout
action space
decoder
```

跑 paired 5 seeds。

---

## Experiment 4：Decoder

只有 D 类失败明显时开展。

---

## Experiment 5：Load / Scenario Augmentation

只有需要增强泛化时开展。

---

# 23. 当前不建议做的事情

暂时不要：

```text
❌ 直接 arrival_rate ×2
❌ 直接把验证天加入训练
❌ 改 Reward
❌ 加 GRU
❌ 加 Edge Self-Attention
❌ 换 Action Space
❌ 换 Decoder
❌ 一次搜索多个 Attention heads
```

每一次都只改一个变量。

---

# 24. 最终判断

现在最值得研究的不是：

> “为什么 RL 第 1 轮就收敛到 0.92？”

而是：

\[
\boxed{
BC 已经很好，
PPO 为什么没有进一步提升，甚至产生策略漂移？
}
\]

同时：

\[
\boxed{
验证侧 0.77 的剩余差距，
到底多少来自物理不可争，
多少来自 KeyGen / Decoder 可争？
}
\]

---

# 25. 最终路线

\[
\boxed{
BC\ Drift\ Diagnosis
\rightarrow
Validation\ Failure\ Attribution
\rightarrow
DemandResidual\ Evaluation
\rightarrow
Decoder\ Ablation
\rightarrow
Scenario/Load\ Augmentation
}
\]

其中：

\[
\boxed{
330\text{–}365\text{ 天继续作为严格 holdout}
}
\]

任何“加难度”都只能作用于训练侧，不能污染验证集。

---

# 26. 最终一句话

\[
\boxed{
\text{先诊断“策略为什么漂”，再诊断“哪里有可争空间”，最后才决定是否加难度。}
}
\]

当前证据不足以支持“训练任务太简单”是主因；目前更有证据支持：

\[
\boxed{
BC\ ceiling
+
PPO\ drift
+
train/validation\ distribution\ shift
}
\]

这三个问题共同造成了现在的训练现象。
