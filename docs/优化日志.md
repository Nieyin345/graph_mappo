## 一、删掉 Stockholm（2026-09-21，**已完成**）

### 1.1 问题：一个永久不可达的 GS 在给所有度量加常数下拖

用户问「我这么多卫星基本全覆盖，咋会没有通路呢，你是怎么算出来的」——
这个问题**问得对**，我的原始说法有两处错，先纠正：

| 我说错的 | 实际 |
|---|---|
| 拿 `link_registry_skipped.csv` 解释「为什么没通路」 | 那些是**零速率链路，本来就不进 graph**。用户指出「全年零速度的直接都不会在 graph 里面出现呀」——**对** |
| 「22.5% 无路」 | 那是**另一个口径**（候选边里无路），不是 GS 对不可达 |

**正确判据（按用户澄清）**：在 **graph 的候选边**上做 BFS。

### 1.2 实测：89→90 节点里只有 1 个孤岛

在真实 graph（1978 条候选边）上不限跳数 BFS：

```
GS 度分布：28 个 GS = 31~35 度；McMurdo = 1 度（弱连但通）
           Stockholm  = 0 度   ← 唯一孤立
跳数分布：378 对 2 跳、28 对 3 跳、29 对不可达
关键判据：每个不可达对都含度为 0 的节点 = True
         ⟹ 不可达 = 孤立节点，没有别的成因
```

**Stockholm 为什么度为 0**：它的 30 条 GS-SAT 候选链路在上游数据集生成时
**全部被以 `zero_rate_all_year` 剔除**（不是几何遮挡，是密钥速率全年为 0），
而 HAP-GS 又全部超过 700 km 静态预筛阈值。

> ⚠ **文档串号更正**：`训练诊断记录.md:13905` 写「`(8,38)` = Stockholm ↔ HAP_Stockholm
> min_distance 867.47 km」。实测 `867.47 km` 那行是 **`(9,38)` = London↔HAP_Stockholm**；
> `(8,38)` 的真实原因是 `zero_rate_all_year`（距离列为空）。

### 1.3 改动：`active_nodes.exclude`（**不删 registry 行**）

```yaml
# configs/env_full.yaml
scenario:
  active_nodes:
    exclude: [Stockholm]
```

代码在 `qkd_rl/data/scenario_builder.py` 的 `_apply_active_nodes` 里，
**在 count 限制之前**执行。

**为什么不直接删 CSV 行**：`scenario_builder.py:261` 用
`all_nodes[u]`（原始 `node_id` 当**数组下标**）查端点，删行会让 London
起全部错位。在节点层排除则下标仍对。

**为什么只删 GS 不用管 HAP_Stockholm**：HAP_Stockholm 的 30 条边全是 SAT-HAP、
**一条 GS 边都没有**。Stockholm GS 一走，它就失去唯一 GS 邻居，
由 smart 模式自己的规则丢弃（「没有附近 GS 的 HAP 是无用的，丢掉而不是凑数」）。

### 1.4 预检（三道门全过）

| 门 | 结果 |
|---|---|
| 造反证：不 exclude 时必须复现 **29** 个不可达对 | **29** ✓ |
| exclude 后不可达必须归零 | **0** ✓ |
| BC 权重加载：加宽/丢弃/缺失/多余 | **0/0/0/0** ✓ |

图的变化：`90 节点 / 1978 边 / 30 GS / 435 对` → `88 节点 / 1948 边 / 29 GS / 406 对`
（少的 30 条边正是 HAP_Stockholm 的 SAT-HAP）。

**★ BC 权重零损失的原因**：模型是逐节点共享 MLP，`n_nodes` 是**运行时算的**
（`len(obs.node_ids)`），不是固定维度 ⟹ 参数量与节点数无关。

## 二、奖励口径的问题（**诊断完成，未改**）

用户的担心是「只把成功率当奖励会被稀释」。摊开代码后有**三条独立路径**：

| 项 | 公式 | 尺度 | 时变 |
|---|---|---|---|
| **served**（主项，101.4%） | `50 × served_keys / 100000` | 每 key **固定** 5e-4 | ❌ |
| **failed**（1.6%） | `5 × failed_keys / denom` | `denom` = 60 步滑窗 arrived 均值 | ✅ |
| **success_delta**（关闭） | `delta × 50` | `Δ(累计 served/累计 arrived)` | ✅ |

### 2.1 「成功率 delta」在 γ<1 时优化的是**早期**成功率

望远镜求和只在 γ=1 时成立：

```
Σ γ^t · (R_t − R_{t−1}) = γ^T·R_T + (1−γ)·Σ γ^t·R_t − γ·R_0
                            ↑                  ↑
                      最终成功率          早期成功率的加权和
```

| regime | 回合长度 | `γ^T` |
|---|---|---|
| 训练 | 1440 步 | `0.99^1440` = **5.2e-7** |
| 验证 | 240 步 | `0.99^240` = **0.09** |

⟹ 代码注释里 `decaying, cold-start-biased scale` 是**数学必然，不是权重调不好**。

### 2.2 但「稀释」的担心不成立（一个反直觉的好消息）

```
arrived（分母）是**外生的**：RequestGenerator 只吃 (env_seed, t)，与策略无关
                           ⟹ 整局 A_T 是常数
⟹ 最大化 S_T/A_T ≡ 最大化 S_T（总服务量）
```

而现状的 served 奖励**就是** `served_weight × served_keys` ⟹ **用户想要的奖励已在（近似）实现**。
差的是折扣：γ<1 时优化的是「折扣服务量」，方向一致。

### 2.3 「惩罚小」与「尺度时变」是同一个 bug 的两面

`failed` 除以 60 步滑窗 arrived 均值，`served` 除以固定 `100000` —— **两个分母不同源**。

**★ 下一步要先量**：`failed` 与 `served` 是否高度负相关？
若是，加大惩罚 ≈ 加大 served 权重，**是冗余的，改了白改**。
