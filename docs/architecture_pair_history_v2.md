# 动态 QKD 网络调度架构说明：地面站对历史需求、图网络与注意力策略

本文描述服务器 `/opt/qkd/ppo-stock-fix-20260922` 在提交 `94e35946` 上运行的 `pairhist_v2_s42/43/44_from_dminj30` 实验。依据是服务器代码和各运行目录的 `resolved_config.yaml`，而不是本地工作区当前文件。本地工作区与该服务器提交尚未完全同步，复现实验时应以服务器提交和解析后的配置为准。文中“当前实现”特指这次正在训练的版本；设想和待验证事项单独列出。

## 1. 问题与一个时隙内的执行顺序

网络由地面站（GS）、高空平台（HAP）和卫星（SAT）构成。物理拓扑的注册边集合可以固定，但卫星运动使每个时隙的视距、密钥生成速率和可用动作变化。每条物理边有链路密钥池（QKP），此前生成但尚未消耗的密钥可以留到后续时隙。地面站之间的请求具有到达量、等待时间和截止期限。调度器每个时隙选择一组有方向的物理链路，使相应发送端与接收端配对；环境按链路速率生成并入池密钥，再用可用密钥路径服务请求。

一次决策的主要流程是：读取当前链路窗口和密钥池 → 计算动作掩码 → 构造动态异构图 → GNN 编码节点、物理边与需求边 → Actor 对合法有向边打分 → 全局顺序匹配并允许 STOP → 环境执行、生成密钥和服务请求 → 计算奖励 → 进入下个时隙。这里的策略输出是**本时隙的链路激活集合**，不是直接输出一条端到端路径；端到端请求路由由环境中的路由与密钥池规则执行。这个区分对理解 BFS、注意力和成功率都很重要。

## 2. 动态图与可见信息

`GraphBuilder.build` 先用当前动作掩码筛选物理边：两端的对应有向候选都合法时，该边进入当前可生成密钥的集合。配置 `features.edge.include_stocked_edges: true` 再把密钥池中有正存量的边加入**消息传递图**。后一类边可能当前速率为零，只用于感知已有库存和可用服务通路，不因此变成生成动作。`actionable_edge_ids` 保留原始合法生成边，两种集合不会混为一谈。物理无向边在 GNN 中展开为两个方向，需求边亦如此。

节点输入包括节点类型、相邻密钥池状态、入/出需求、队列压力、多个窗口的近期需求以及时间周期特征。物理边输入包括类型、当前可用性和速率、未来短窗口的速率/可用性、速率变化、容量余量、已激活信息、请求端点距离和中继重要性等，具体开关以 `resolved_config.yaml` 为准。当前实验的 `features.node.include_position: false`：**没有直接输入纬度、经度、高度**。模型通过时变邻接、链路可用性、速率和节点身份的结构关系间接感知卫星运动及相对位置，但不能宣称已经显式学习到三维坐标。若论文要论证“空间位置感知”，应补充坐标或相对几何特征，并做消融。

## 3. 地面站对作为需求单位

当前配置 `features.demand_edge.build_mode: active_or_history_pairs`。一个地面站对对应一条逻辑需求边，不把单个请求当作单独图实体。当前有待处理请求的站对一定保留；历史上出现过但目前没有待处理请求的站对按历史强度选取，最多额外保留 32 对。强度由 15、60、240 时隙的到达速率和累计到达量占比组成。这使模型既能看到当前拥塞，也能看到长期热点；历史信息只使用已观察到的过去，不包含未来请求。

逻辑需求边的特征包括待处理量、请求数、剩余截止时间、平均等待时间、优先级、等待分桶，以及上述多个窗口的到达/已服务速率和累计到达占比。`features.history_encoder.enabled: false`，所以本实验**没有启用 LSTM 历史编码器**；历史通过统计特征输入。每个地面站对在需求注意力中被汇成一个 token，避免把同一需求边的两个消息传递方向当成两个独立请求。

这套设计解决了“需求单位应是地面站对”这一建模问题，但仍有边界：历史统计是预设窗口的摘要，不能表达任意长时依赖；历史热点不等于未来一定有请求。32 对截断和窗口长度都需在不同流量分布下验证。

## 4. GNN 与两种注意力

编码器是三层、隐藏宽度 128 的边条件消息传递网络（配置名 `graphsage`）。物理边与逻辑需求边各用独立的输入投影、消息 MLP 和边更新 MLP，避免把“链路能力”和“请求压力”混成同一种边语义。每层先把邻边信息聚合到节点，随后用更新后的两端节点表示更新边；节点带残差和归一化。这样物理边可获得邻域的需求和链路状态，但三层传播不等于全图任意距离可达，也不保证精确求出可行端到端通路。

对每个合法有向物理边 `u → v`，基础打分器读入 `[h_u, h_v, h_uv]`。`demand_residual` 以该候选边为 Query，以各地面站对的需求嵌入为 Key/Value，输出一个需求条件修正分数。`path_edge_attention` 则以候选边为 Query，以当前请求规范路径上的物理边嵌入为 Key/Value，输出第二个修正分数。最终分数为基础分数与两项残差之和。两项残差的末层初始权重为零，载入旧模型时初始动作分数不被突然扰动；训练之后可学习偏离。

路径边集合由环境路由器的规范最短路径计算，并通过 `request_path_edge_mask` 进入 Actor。这是**对当前请求路径的软提示**，不是对全部可行路径的穷举，也不是约束 Actor 必须选择其中的所有边。注意力在当前候选边与需求/路径边之间建立关系；它没有一次性产生完整通路。历史需求 token 可影响链路打分，因此无当前请求的时隙仍可利用历史热点；路径注意力在当前没有请求路径时返回零修正。

## 5. 发送/接收端口与合法动作

节点动作表示为 `(tx_target, rx_source)`，每个节点最多选一个发送目标和一个接收来源。Actor 对 `u → v` 与 `v → u` 分别打分。顺序匹配策略每一步在剩余合法有向边和 STOP 间采样，选中 `u → v` 后屏蔽已占用的 `u` 发送口、`v` 接收口和该无向节点对的反方向重复匹配。因此单节点可以同时向一处发送、从另一处接收，但不能在同一时隙从两个邻居接收或向两个邻居发送。`mutual_choice` 解析器要求发送端提议与接收端接受相互一致，最终再由环境执行。动作掩码处理当前不可用、低于最低速率及不允许的链路类型。

模型在每一步使用全局匹配决策，而 PPO 用**整段动作序列的联合 log-probability**计算重要性比率；不能把各次选择的 log-probability 先平均，否则梯度尺度随选边数错误变化。STOP 使策略能够在已无值得激活的边时停止，避免被迫用满端口。

## 6. 奖励：先满足需求，再准备未来

当前实验采用 `reward.mode: shaped`。按解析配置，主要正项为已服务密钥量：`served_weight=50`，以 `served_reference=100000` 归一化；对当前需求可用路径上新生成且未在本时隙消耗的库存给 `storage_reward_weight=0.5`、`storage_reference=1000000` 的存储奖励；维持链路激活还有很小的 `keep_active_weight=0.001`。主要负项为未满足/超期需求 `failed_weight=5` 和过期密钥 `expired_key_weight=0.01`。总奖励最后乘 `reward_scale=0.002`，让 Critic 的回报目标处于更易拟合的量级。

这里的“先满足现在”体现在服务量的较大权重和失败惩罚；“为未来备货”目前由**当前未完成请求的可用路径上的存储奖励**和历史需求特征间接推动。要准确描述局限：当前 `generated_weight=0`、`dense_enabled=false`、`waiting_enabled=false`、`switch_enabled=false`，因此并非“所有闲置边生成密钥都有正奖励”。无当前请求的历史热点边能被 Actor 识别，但若它不属于当前 pending 路径，存储项可能为零。若目标真是对未来热点建立库存，需要另设计按历史强度、预测需求、容量及密钥有效期加权的备货目标，并与当前服务目标做对照实验；简单奖励所有生成量会鼓励填满高速度但无用的边。

奖励在环境执行后计算，离散选边本身不可微；PPO 使用动作 log-probability 与优势函数作策略梯度，不需要让环境路由或奖励函数对动作求导。`storage_reward` 的归因是新入池且未被本时隙消费的密钥，较原始速率奖励更贴近“真正存下来”。但是它仍是 shaping，权重与最终跨时隙成功率是否一致，需要用独立验证集确认。

## 7. Critic、PPO 与梯度

Actor 和 Critic 共享上述 GNN 编码器。Critic 的 `typed_mean` 池化分别取节点、物理边和需求边的均值，再拼接三类实体数量的 `log1p` 计数，经过 MLP 预测一个**全局状态价值**。它评估整个网络状态，不对每条候选边分别打价值。这样的输入可感知图规模与整体负载，但均值池化可能弱化少数即将到期的关键请求；需要结合价值预测与回报的相关性、解释方差和按负载分组误差评估，不能只看训练 loss。

训练使用 MAPPO/PPO：每轮 8 个并行 rollout worker，单次 rollout 1440 时隙；`gamma=0.99`、`GAE lambda=0.95`、每轮 1 个 PPO epoch、裁剪阈值 `0.1`、熵系数 `0.01`。Actor 与 Critic 分别使用 `1e-5`、`1e-3` 的学习率，并按角色分别裁剪梯度范数。旧动作的 log-probability 存在 rollout buffer；更新时重新前向计算当前策略的联合 log-probability，梯度会传入基础打分器、两种注意力残差和共享编码器。Critic 的回归梯度也进入共享编码器。训练日志中的 Actor/Critic 梯度范数、KL、裁剪比例、`value_return_corr` 是判断优化是否真的发生的直接证据。

当前三种子实验从旧 `dminj` 模型 update 30 继续到 update 60，每 5 次更新保存 checkpoint 并在固定验证集评估。验证窗口为第 330–365 天，训练窗口不应覆盖它；比较时须用相同请求种子的配对成功率差，而不只比较不同随机 rollout 的训练均值。截至 2026-09-23 04:00（北京时间），三组均完成 update 31，KL 约 `0.0023–0.0026`，裁剪比例约 `0.112–0.136`，`value_return_corr` 约 `0.888–0.906`，尚未到新一轮验证点。因此这些数字只能说明初步训练稳定，**不能证明新架构优于旧模型**。

## 8. 需要继续检验的设计问题

1. **位置表示：**当前无显式经纬高，需检验仅凭速率/可用性是否足够，并做相对位置特征消融。
2. **通路关系：**规范路径提示不保证选择完整可服务通路，应分别记录路径覆盖率、链路库存瓶颈和真正服务量；比较需求注意力、路径注意力单独及共同启用的版本。
3. **未来备货：**当前存储奖励偏向已有 pending 路径，与“无请求时也为未来重要边生成”并不完全一致。需以跨时隙收益和过期/溢出成本校准，而非只提高即时生成量。
4. **Critic 信息压缩：**检查高负载、短期限、稀有站对上的价值误差；若均值池化遗漏极值，可实验启用按类型的 max 池化或注意力池化。
5. **分布泛化：**历史热点与请求生成器的 Zipf 分布相符时可能获益；需要在改变热点、到达率及卫星窗口的验证场景上测试，避免只记住训练分布。
6. **因果结论：**必须等 update 35、40……60 的固定种子验证结果，与旧 checkpoint 做配对比较，并检查改善是否同时伴随更高的成功率、合理的密钥生成和无明显端口冲突。

运行中的自动同步结果位于本地 `server_results/pairhist_v2/`：`report.md` 给出汇总，`status.json` 记录每个种子的状态和验证对照，各子目录保存训练日志、指标与 checkpoint。服务器训练独立于本地轮询；本地机器持续运行时，计划任务每 15 分钟同步一次。
