## 第四部分：urgency 加权等待惩罚 —— 对比训练计划（**2026-09-22 定**）

> **状态**：机制已实现并验收（四道门全过），**尚未起臂**。

### 4.1 机制一句话

每个**未被服务**的请求按**剩余寿命**加权后被罚：

```
urgency(req) = 1 − 剩余步数 / deadline_steps     （0 = 刚到，1 = 快死）
penalty      = urgency_wait_weight × Σ urgency×剩余量 / served_reference
```

逐 step 计算 ⟹ **及时**；**不规定顺序**（模型自己决定先做谁，只是救急的回报更高）。

### 4.2 为什么需要它（与现状的对照）

生效配置里三项奖励（训练 regime 实测 570 轮）：

| 项 | 每步均值 | 占 served | 对 urgency 敏感吗 |
|---|---|---|---|
| `served_weight`（服务成功） | 0.066313 | 100% | ❌ 服务 1 个 key 恒定给 5e-4，不论多急 |
| `failed_weight`（过期失败） | 0.001068 | **1.61%** | ❌ 只在过期那一刻扣，是**事后**信号 |
| **`urgency_wait`（新）** | 见 4.4 | — | ✅ **唯一的「优先救谁」方向信号** |

**★ 关键**：`served` 与 `failed` 只定奖励**水平**，不定**方向**——
服务 A 而让 B 过期，净得 `w_s − w_f`；反过来选 B 一样。
只有 urgency 项能区分「先救急的」和「先服务从容的」。

### 4.3 验收记录（起臂前必须全过）

| 门 | 判据 | 结果 |
|---|---|---|
| ① | 诊断字段 `urgency_weighted_keys` 不被 `reward_scale` 缩放 | ✓ 逐位一致 |
| ② | 手算 = env 输出（4 个抽样点） | ✓ 逐位一致 |
| ④ | `w=0` 时新项逐位为 0，且 served/failed 逐位不变 | ✓ 正交 |

**造反证抓到我自己的两个错误**（都已修）：

1. 诊断字段被 `reward_scale=0.002` 缩放（手算 280,013 vs env 510，差 549 倍）
2. **权重推导多除了一次 `served_reference`**——三项共用同一分母，做比值时约掉，
   正确值是 `w = failed_weight/14.5 ≈ 0.345`，不是 3.2e-6（差 5 个数量级）

### 4.4 剂量臂设计

**唯一变量**：`reward.urgency_wait_weight`。其余全部锁定。

| 臂名 | `urgency_wait_weight` | urgency 项/步（预检实测） | 占 served |
|---|---|---|---|
| **`u0`（对照）** | `enabled: false` | 0 | 0% |
| **`u1`（0.5×）** | 0.17 | 0.00104152 | 2.35% |
| **`u2`（1×）** | **0.35** | **0.00214431** | **4.83%** |
| **`u3`（2×）** | 0.70 | 0.00428863 | 9.66% |
| **`u4`（4×，上界）** | 1.40 | 0.00857725 | 19.32% |

> ★ 上表是**预检实测**（`probe_urgency_precheck.py`，验证 regime，专家策略，
> 40 步，种子 100）。此前一版用**训练 regime** 的 `waiting_keys` 外推，
> 得到 u2=1.98% —— 两个 regime 的积压量不同，**以预检实测为准**。
> 剂量仍是**线性**的（0.17→1.40 恰好 8 倍，占比 4.83%→19.32% 也约 4 倍，
> 因为占比里 served 项相同），所以「剂量」这个旋钮是**单调可控**的。

**`u2` 是「让等待与失败同等重要」的点**（4.83% vs failed 的 1.61%，即等待被罚得比失败更重），
是推导出来的平衡点，不是拍的。`u1/u3/u4` 用来量曲线形状。

### 5.1 两处改动（都是**模型结构**，会改参数量）

#### 改动 A：删 `actor.idle_scorer`

**位置**：`qkd_rl/rl/models/graph_mappo.py:454-458`（定义）、
`:675` 与 `:1086`（前向两处）。

**为什么是死重**（两条独立证据，见记忆 `idle-scorer-is-dead-weight` /
`idle-scorer-has-no-gradient-not-no-input`）：

| 证据 | 结果 |
|---|---|

#### 改动 B：去 Actor 打分公式的冗余

**位置**：`qkd_rl/rl/models/graph_mappo.py:667-670`

```python
pair_emb = torch.cat([node_emb[src_t], node_emb[dst_t], edge_emb_directed[pos_t]], dim=-1)
edge_scores = self.edge_scorer(pair_emb).squeeze(-1)
```

**问题**：`edge_emb_directed` 是 encoder 的输出，而 encoder 的每一层都做


⟹ **边嵌入里已经含有它两个端点的节点信息**（还经过 3 层累积）。

⚠ **这条不是「确定的 bug」**，是**冗余**。MLP 可以学会忽略重复项，

**所以本次改动会丢两层**：`edge_scorer`（因为变窄）+ 本来就会重置的 `critic.value_head`。

> 需求边的请求……**不要用标量，要用向量去扩散**，**不要用经验公式**，
> 如果扩散要像网络一样**可以学习**」

### 6.1 现状的两个缺陷（用户指出的）

**缺陷 1：BFS 那个标量是「求和」，AB 和 BC 分不清**

`relay_importance` 对经过的每条请求做**加权求和**，得到**每条物理边一个标量**。
一条物理边如果同时被 AB 和 BC 两条需求覆盖，它只知道自己被「总共需要多少」，
**不知道是 AB 还是 BC**。

**缺陷 2：节点注入也是求和**

```python
# graph_mappo.py:277
aggregated = aggregated + self._node_message(demand_mlp, node_emb, src_d, dst_d, demand_emb)
#                          ↑ index_add_ 到节点，AB 和 BC 在共享节点处被求和
```

**两套现有机制都有同一个缺陷。** 用户的设计是**第一个能区分它们的机制**。

### 6.2 机制：需求边当 Query，在其 BFS 路径上做注意力

```
① BFS 筛选（拓扑事实，不需要学）
   对每条需求边 (src, dst)，筛出所有满足
       dist(src,·) + dist(dst,·) + 1 ≤ max_path_links(=8)
   的物理边 ⟹ 候选对 (需求边 i, 物理边 j)。实测每步 100~460 对。

② 注意力（权重全部可学习，无经验公式）
   Q = 需求边 i 的嵌入              ← ★ 需求边当 Q
   K = 物理边 j 的嵌入
   V = 物理边 j 的嵌入
   α_ij = softmax_j( <Q_i, K_j> / √H )    ← ★ softmax 在**每条需求自己的候选集**内
   ctx_i = Σ_j α_ij · V_j                  ← 这条需求看到的「整条通道状况」

③ Scatter 回写（把需求的判断写回它路径上的边）
   phys_emb[j] += W_out · ( α_ij · ctx_i )   ← 按注意力权重加权回写
```

**为什么需求边当 Q 是对的**（用户 2026-09-22 指正，我先前讲反了）：

> **一条物理边看不见整条路径，但一条需求边看得见。**
> 而「服务需要连成通道」是**需求的属性**，不是链路的属性。

★ 而且 `α_ij` 天然能学出「**这条路径上哪一跳最关键**」——

让网络自己学，比写死公式好。

### 6.5 ★★ 必须带的检查：新通路的**梯度范数**

**为什么不能省**：本项目训练已饱和（`kl≈0.001`，clip 从未激活），
actor 可能被 advantage 塌缩冻住 ⟹ **新通路可能拿不到梯度 ⟹ 停在零 ⟹
前向永远等于基线**。

**症状伪装**：「实现了但学不动」与「正确实现但确实没用」**长得一模一样**。
本仓库栽过多次（`idle_scorer`、`history_encoder`）。

```

梯度恒零 ⟹ 停在零是"学不动"不是"没用" ⟹ 结论完全不同
```

**实现**：训练中打印新参数（`dem_q/dem_k/dem_v/dem_out`）的 `grad.norm()`，

### 6.9 实现时必须处理的坑

**坑 1：需求边在 `edge_index` 里是加倍**

```python
# graph_builder.py:404-405 docstring
"""physical edges first as (src,dst) then (dst,src),
   followed by the same doubled representation for demand pairs."""
```

⟹ `edge_index` 里需求部分有 `2*n_demand` 行，而 `demand_emb` 只有 `n_demand` 行。
**下标对不上**，直接写会静默取错行（不报错，结果错）。
映射：`edge_index` 里第 `2*n_phys + 2*i(+1)` 行 ⟹ `demand_emb[i]`。

**坑 2：零候选必须输出 0**

`α` 在空集上做 softmax 会得 NaN。必须显式处理，且造反证要覆盖。

**坑 3：BFS 索引每步重建**

需求边和物理边**每步都在变**（实测 1~12 条 / 134~205 条），
所以稀疏对 `(i, j)` 必须**每步重建**。用 numpy 建索引，切成 `index_add_` /
`segment_softmax` —— 与现有 `_node_message` 同一路子。

## 第八部分：需求 → 物理边 的路径内注意力（**2026-09-22 讨论记录**）

> **状态**：**讨论中，未定稿**。本部分是**讨论记录**，不是执行计划。
> **出发问题**：用户 2026-09-22——
> 「一条边可能会进入到多个请求的注意力里，每个请求都会得到一个它所倾向的边的重要性，
> 要把所有的汇总起来」；「标准的注意力**不要全局一起做，单独一个请求边做**，
> 先用 BFS 筛选，然后把筛选的边做自注意力，结果和需求边做交叉注意」。

### 8.1 出发点：现有两套机制的共同缺陷

**用户指出的问题**：节点注入会让 AB 和 BC 混淆。

```python
# graph_mappo.py:281  现有节点注入
aggregated = aggregated + self._node_message(demand_mlp, node_emb, src_d, dst_d, demand_emb)
#                          ↑ index_add_ 到节点 ⟹ AB 和 BC 在共享节点 B 处被**求和**
```

**★ 而且 BFS 标量（`relay_importance`）有同一个缺陷**——
它对经过的请求**加权求和**，得到**每条边一个标量**，同样分不清 AB 和 BC。

**用户原话**：「ab 节点的需求边和 bc 边如果是按照节点注入都会是往 b 里面注入呀，
这区分不出来，我要的是 ab 作为一个整体去注入」。

### 8.2 为什么不能全局做自注意力（**用户判断，已确认正确**）

```
全局：北京→东京 的边  与  伦敦→纽约 的边  互相"注意"
      但物理上它们毫无配合关系
      ⟹ 模型学到"任意两条边都可能相关"，与"能不能凑成通道"无关

按路径：只保留真实关系（同一条通道的边才互相注意）
```

**★ 用户原话**：「就是这个标准的注意力不要全局一起做，单独一个请求边做」。

**⟹ BFS 的用途就是回答「哪些边属于同一条通道」。**

### 8.3 已达成共识的设计（**三步**）

```
对每一条需求边（GS 对 A→B）单独做：

① BFS 筛选
   筛出这条需求**路径上**的物理边
   候选集 = 路径上的边 ∈ (活跃边 ∪ 有存量密钥的边)

② 自注意力（★ 只在这条需求的候选集内，不是全局）
   筛出来的这些边互相注意
   边特征 = [自身特征, 左端点嵌入, 右端点嵌入]    ← 用户定：用端点表达位置

③ 交叉注意
   需求边当 Q，去查 ② 的结果
   ⟹ 得到 α_rj = "对请求 r 来说，边 j 有多重要"
```

### 8.4 存量边的角色（**用户澄清**）

> 用户原话：「库存边就是为了**提供信息**的，让模型判断如果现在选择某一个边，
> 对现在的情况来说**能不能凑出来通道**来满足请求」

| 边类型 | 提供信息 | 接受注入 | 实现上 |
|---|---|---|---|
| **活跃边** | ✅ | ✅ | 在 `phys_emb` 里，有完整嵌入 |
| **有存量的边** | ✅ | ❌ | **不在 `physical_edge_ids` 里** ⟹ 天然没有位置可写 |

**★ 实现上天然成立**：存量边不在 `phys_emb` 里 ⟹ 想注入也没有位置。
且损失只通过**活跃边**的分数回传 ⟹ **存量边输出没有梯度** ⟹
模型自然专注活跃边。（用户原话：「库存边无论输出什么都不影响」）

**实测规模**（`probe_stock_edges.py`，两条对照均过）：

| step | 活跃边 | 有存量 | **额外存量** | 并集 |
|---|---|---|---|---|
| 0 | 205 | 58 | 0 | 205 |
| 20 | 134 | 139 | **56** | 190 |
| 40 | 204 | 205 | **81** | 285 |

**⟹ 额外存量最多 81 条 —— 这些边现在完全不在模型视野里。**

### 8.5 ★ 讨论中未定：交叉注意力的输出怎么变成边的分数

**问题**：注意力输出形状 `(n_demand, 128)`，而 actor 要 `(n_edge,)`。**对不上。**

**用户选定的方向**：**甲 —— 加一步 scatter**

```
① 需求 r 的注意力 → out[r] (128 维)
② 用 α[r,j] 把 out[r] scatter 回边 j
   ⟹ 边 j 得到 Σ_r α[r,j]·out[r]
③ 再投影成 (n_edge,)
```

⚠ **未定**：第 ③ 步的投影怎么做（是否会被批评为"又做一次选择"）。

### 8.6 ★ 讨论中：分数怎么变成「边的选择」

**用户的发现**：「现在不能用双向的选择了，现在只有一个边的分数了」。

**背景（已核实）**：

```python
# 现在分数挂在**有向弧**上，不在无向边上
pair_emb = cat([node_emb[src], node_emb[dst], edge_emb[pos]])
#              ↑ 顺序固定 ⟹ s(A→B) ≠ s(B→A)
# _edge_score_map docstring: "u->v and v->u keep their own learned scores"
```

**新设计下每条边只有一个分数 ⟹ 双向选择退化**（`mutual_choice` 会变成
"只要双方都想要就成"，方向由字典序决定，不看分数）。

**三条候选路线**：

| 路 | 做法 | 代价 |
|---|---|---|
| **1** | 改成**边级 + 全局最优匹配**（`max_weight_matching`） | **失去去中心化执行**（不再是 MA） |
| **2** | 边分数复制给两个方向，保留双向 | 两边分数相同 ⟹ "互选"变成"各按同一分布独立采样" ⟹ **可能一边中一边不中，白丢** |
| **3** | 改「一方发起，另一方确认」 | 需重新设计 |

### 8.7 ★★ 已核实的硬约束：`max_weight_matching` 与 PPO 冲突

**实测**（`probe_mwm_cost.py`，节点 88、L/R 拆后 V=176、候选弧 268~410）：

```
max_weight_matching 单次 = 7.1 ~ 8.6 ms
每步预算（训练实测 53~97 s / 11520 步）≈ 13 ms
```

**单次看似可接受，但——**

```
① rollout 阶段：每 env step 一次
② ★ PPO 更新：**每个 minibatch 都要重算 log_prob**
   现在 mutual_choice 下**不需要重跑 resolver**
   （policy.py:51 注释：mutual_choice 是"执行采样匹配"，概率只依赖 scores）
   换成 max_weight_matching ⟹ 概率分布是匹配结果的函数 ⟹ **每 minibatch 重跑一次**
   n_minibatches = 45（实测）
```

**⟹ 开销放大 ~45 倍 ⟹ 7~9 ms × 45 = 300~400 ms/步 ⟹ 30~40 小时/条臂。**

**结论**：**不是"慢一点"，是它和 PPO 的 on-policy 性质冲突。**
要绕开只能：改 off-policy 算法、或接受采样的动作与执行不一致（梯度是错的）。

专家边合计仅 4 条。第一次错边平均在第 12.6 次选择，说明优先问题是**中途边排序**，

### 10.7 攻「PPO 相对 BC 无增益」：三个判定（**2026-09-26**）

**动机**：§10.5 发现 PPO 首次真正更新后，窗 A 上 PPO 后 − BC 起点仅 +0.004。
跑三个便宜判定，定「欠训练 / 被误导 / 尺度不够」中的哪一个。

**① 窗 B 复核**（此前所有 frozen 臂只评了窗 A）。BC 与 PPO 种子无关，故同一份共享
BC 评一次即可：

| 窗 | BC 起点 | PPO 终点（3 训练种子） | 增益 |
|---|---|---|---|
| A（专家 0.7674） | 0.7560 | 0.7599 | +0.004 |
| **B（专家 0.8674）** | **0.8561** | **0.8555** | **−0.001** |

⟹ 零增益在**两个窗上都成立**（v3 窗 B 逐种子 0.8562/0.8544/0.8559）。
v6 窗 B 0.8493（窗 A 0.7491），同样贴 BC。

**② 续训曲线**（v3 s42，同一共享 BC，训练 1/5/10/40 轮，各评窗 A）：

| 轮数 | 0(BC) | 1 | 5 | 10 | 20 | 40 |
|---|---|---|---|---|---|---|
| 窗 A SR | 0.7560 | 0.7637 | 0.7647 | **0.7674** | 0.7583 | 0.7625 |

**不是「零增益」，但也不是可分辨的增益**：全程落在 **[0.756, 0.767] 约 1.1 点的带内**，
而项目**单种子分辨率 ~0.035**（n=3 临界 4.303）——**整条带在分辨率以下**。
u10 的 0.7674 是 6 个点的最大值，须按 max-of-k 偏差打折。**无单调趋势、不收敛**。

**③ 训练侧 40 轮**（同一 run 的 metrics）：reward 首→末 **+1.04**，
success **0.8307 → 0.8306（−0.0001）**；分块 u1-10 / u11-20 / u21-30 / u31-40 的
success 为 0.8549 / 0.8574 / 0.8535 / 0.8504——**无趋势**。
⟹ **不是欠训练**：PPO 能持续优化其奖励，但**奖励的改进不转化为成功率**。

**④ 奖励是否失配？——否，且项目已论证过**（`docs/优化日志.md` §2）：
`arrived`（分母）外生（`RequestGenerator` 只吃 `env_seed`）
⟹ 整局 `A_T` 是常数 ⟹ **最大化 served ≡ 最大化 success_rate**。
所以 `served` 主项（实测占总奖励 ~100%，`mean_reward_served=0.0612` vs 总
`mean_reward=0.0609`）**与评测指标同向**，不存在「在优化代理指标」。
`success_delta` 之所以关闭也有数学原因：γ<1 时望远镜求和给出
`(1−γ)·Σγ^t·R_t` 权重 ⟹ 优化的是**早期**成功率，非最终成功率。

**⟹ 结论（三条）**：
1. **「PPO 无增益」的本质是「效应量 ~1 点 < 项目分辨率 0.035」**，不是配置错误、
   不是欠训练、不是奖励失配。在这个预算下，**PPO 与 BC 的差异测不出来**。
2. 模型停在**专家克隆水平**（贴 BC、贴专家，稳定落后 ~0.7–1.2 点），
   两个窗口一致。
3. **240 步筛选 regime 无法分辨架构**：v2/v3/v6 全在分辨率内，只有 v4 可分辨
   （且 v4 是**大幅更差** −0.073）。若目的是选架构，**当前 regime 不是合适的尺子**。

**未做的候选（若继续攻此方向）**：把奖励改成对 **arrived 归一化**
（`normalize_by_arrived_demand: true`，现为 false）——由 ④，它在单回合内与现状
等价（arrived 外生），**但会消除跨回合的奖励尺度漂移**（不同起始日需求量不同，
reward 绝对值随日漂移）。这是唯一未被项目论证否决的奖励改动，判据：若它仍
不改变 success，则「奖励口径」这条可以正式关闭。

**产物**：`outputs/experiments/v3/gainlim_v3_u{1,5,10,40}_s42/`、
`outputs/frozen_eval/*_gainlim_*_A.json`、`outputs/frozen_eval/*_{v3,v6}_*_B.json`。

### 10.9 天花板在哪里：专家还剩多少空间 + 端口预算（**2026-09-26**）

**★ 先排除一个坏工具**：`outputs/eval/milp_ub*/summary.json` 报

——`receding_horizon_milp.py` 自己的注释说它的上界除以 **modeled demand** 而非 arrived
demand，是**另一个量**。**不要用这三个数字。**（项目已记录过「不是上界的上界会把方向判反」。）

**方法**：复用 `docs/训练诊断记录.md` 探针 N 的严格分解，把它的窗口从诊断窗

### 10.11 v8：把“预备”变成有直接标签的监督（**2026-09-26 建好并验证，训练中**）

**设计**（与 v7 的区别只有一处，但这是关键一处）：给“将来会不会用到这条边”
一个**直接、稠密、不需要奖励的标签**：

```
label_t(e) = 1  若物理边 e 在接下来 K 个槽内出现在某个请求的路径上
            = 0  否则
```

- 环境**本来就算**当前步的版本（`GraphObservation.request_path_edge_mask`），
  v8 的标签只是它的 K 步前瞻版本，在回合结束时从记录下来的逐步 mask 算出。
- 它只依赖**请求流**，不依赖策略 ⟹ **不可被刷**（对比“存了货就给奖励”，策略可以靠囤货刷分）。
- 两个用途、**分开开关**以便归因：
  - `loss_weight > 0`：训头（BCE）。**即使 bias 为 0 也塑造 encoder** ⟹ 纯表示变化。
  - `bias_weight > 0`：把 `w·tanh(logit)` 加到弧的分数上 ⟹ 主动预备行为。
    **走的是 v3 那套单阶段匹配**，没有第二遍（因为端口余量 31%，不稀缺）。

**消融**（同一 BC、同一 20 轮预算，对照是现成的 `pairhot20_v3_s{42,43,44}`）：
- `v8loss`（只损失）：隔离“表示变好” ⟹ 与 v3 差 = 表示效应。
- `v8bias`（损失+偏置）：隔离“主动预备” ⟹ 与 `v8loss` 差 = 行为效应。

**★ 建的过程中踩到并修掉的四个坑（都是**静默**失败，前三个会让 batch 白跑）**：

1. **`_make_buffer` 插进了 `__init__` 中间**（缩进对、但把 `__init__` 的尾巴——
   `curriculum_stages`/`_seed_stride`/`fixed_episode_seed` —— 变成了 `return buffer`
   之后的**死代码**）。那三个属性从未被赋值 ⟹ **16 个测试 AttributeError**。
   教训：往 `__init__` 里插方法，必须确认 `__init__` 已经闭合。
2. **batched 路径的预测头输出 2× 长度**。标签是**无向**物理边（`len(physical_edge_ids)`），
   而 encoder 存**两个方向**（`num_physical_directed = 2×`）。单图路径本来就 `[::2]`，
   批量路径没有 ⟹ 502 vs 251。trainer 的 `label.numel() == logit.numel()` 守卫因此
   **每步都跳过**，`usage_terms` 恒空、头**永不训练** —— 症状与
   `usage_forecast.enabled: false` **逐位相同**。
3. **`bias_weight` 只在单图路径生效**。训练走的是批量路径 ⟹ 行为臂会**静默退化成**
   纯表示臂，消融对比全错。
4. **偏置必须 tanh 有界**。头是 BCE 训的 log-odds，**会无界增长**；实测弧分数
   std≈0.01 而未训练头 logit std≈0.03（比值 ~2.7）⟹ 固定权重迟早被头淹没。
   改 `w·tanh(logit)`，`w` 直接以**分数单位**读（饱和时 0.01 ≈ 1 个分数 std）。
   且在头还随机时 logit≈0.03、偏置 ~w·0.03 **几乎不动** ⟹ 顺序是对的：
   先学表示，后起作用。

**验证（三道，全部通过）**：
- `tests/test_v8_usage_forecast.py`：标签前瞻性、horizon 边界、按 id 不按位置、horizon=0 关闭。
- `tests/test_v8_forecast_paths.py`（新增）：**单图与批量逐位一致**、长度=无向边数、
  `bias_weight>0` 确实改变弧分数。这个测试存在的理由就是坑 2/3 **只在批量路径**上，
  而只有单图路径的冒烟测试是**绿的**。
- `.tmp/probe_v8_trainer_wiring.py`：走 **trainer 自己的** `_collect_rollout_serial`
  + `_loss_for_batch`，断言 `loss_weight=0.05` 与 `=0` 的 actor_loss **不同**
  （实测 Δ=+0.0376）、且头拿到梯度。**这一条是启动前的硬门**（见下）。

**启动门（写进了 launcher，不通过就拒绝起 run）**：跑 6 条 run 前先跑接线探针，
`grep -q "WIRING OK"` 才继续。理由：坑 2 的症状是“跑了 6 条与 v3 无差别的 run”，
**没有任何报错**；用一个**打印自己输入并断言已知答案**的门挡住它，是唯一可靠的做法
（与 CLAUDE.md「门/判据类代码必须打印它自己的输入」同一条）。

**批次状态**：`v8loss`/`v8bias` × 种子 42/43/44，4 并发 ×16 线程 = 64 核，
`Threads: torch=16 OMP=16 MKL=16` 已确认。开局 clip_frac **0.11–0.25**
（对比 v7 的 0.05–0.07）⟹ **PPO 这次确实在动**。

|---|---|

这和 §10.11 的坑 2/3 是同一类：**静默的空操作会被误读成“无效应”**。

#### 10.12 附：**靶子本身被“持续性”主导** —— 这解释了头为什么学不好，也限制了“预备”的价值上限

上表的 AUC 对比指向一个更根本的事实。标签并不是“未来会不会用到”，而是**几乎等于
“现在是不是在用”**：

| 条件 | 未来 K 步仍在路径上的比例 |
|---|---|
| 当前步**在**请求路径上 | **100.00%**（10496 / 10496） |
| 当前步**不在**路径上 | **10.63%**（118194 条里 12579 条） |

后果有两层：

1. **头（AUC 0.60）学不过“照抄当前 mask”（AUC 0.73）**。原因不是缺信息：
   `fuse_demand_to_node: true` 已把需求融进 `node_emb`，头**够得着**这些信号；
   是它没把这个**平凡**规则提取出来（三个种子里两个 AUC≈0.5 = 完全没学到）。
   —— “网络里能算出 X” ≠ “梯度会找到 X”。

2. **更重要的：既然当前在用的边 100% 继续会被用，而 actor 本来就在优化当前 mask，
   那么 actor 已经在隐式地“预备”持续性需求了。**“主动预备”真正能加的价值，
   只落在**那 10.6% 的新激活**上 —— 从当前状态看，它们是小概率事件。
   这与第一批测得的行为效应 ≈0 **不矛盾**，但也**不支持**“预备有害/无效”的结论
   （那条臂是空操作，见上）。

**⟹ 下一步的正确靶子不是“未来会不会用到”，而是“接下来会不会**新**变为在用”。**
把持续性那部分从标签里扣掉，头才有可能学到比“照抄 mask”更好的东西；
否则无论头多好，它相对 actor 已有的 mask 都没有增量。

#### 10.12 附二：把靶子换成「会不会**新**变为在用」后，信号是**可测的**（决定要跑 batch 2）

只用**数据**（不训练）测「新激活」的可预测性 —— 只在**当前步不在路径上**的边上统计
（118194 条），标签 `new_t(e) = 1 若 e 在 (t, t+K] 内被用到且 t 时刻没被用`：

| 预测器 | AUC |
|---|---|
| 当前步 mask | 0.5000（按定义恒 0，即 actor 已有的信息，对“新激活”无用） |
| 历史是否用过（0/1） | 0.5857 |
| **最近使用时间的倒数**（一行特征） | **0.6329** |

**判读**：新激活**确实可预测**（0.63 >> 0.5），而且**一行平凡特征就比头在旧标签上
学到的 0.60 更好**。这坐实了上一节的结论：不是“不可预测”，是**靶子选错了**
（旧标签被持续性主导，头在学一个 actor 已经会的东西）。

**⟹ batch 2 的设计**（未跑，待定）：
1. **换标签**：训练 `new_t(e)`（扣掉持续性），而不是 `e 在窗内被用到`。
2. **给头一个多槽的近期路径成员历史**。核实过头的输入：它是
   `[node_src, node_dst, edge_emb]`，而 `edge_emb` 来自物理边特征，其中
   **有** `include_last_activated`（**1 槽**的「上一步有没有被激活」）和
   `include_rate_future_window`（未来的**链路速率**，即「链路通不通」）。所以头
   **不是**完全没有时间信息 —— 但这两者都不是本次测出信号的那个量：
   - `last_activated` 是**1 槽**、且指的是**是否被激活（生成密钥）**，不是**是否在请求路径上**；
   - `rate_future_window` 是「链路会不会通」，不是「将来要不要货」。
   而 AUC 0.63 的信号来自**多槽的路径成员近期历史**，头够不着它。
   （`history_encoder` 在 v8 里是关的；它能为节点/边提供 32 槽回看，是现成的承载体。）
   **这一点解释了为什么三个种子里两个的头 AUC≈0.5** —— 最该用的那条信号不在输入里。
3. **偏置权重按训练后尺度标定**：`bias_weight ≈ 4`（约 20% 分数 std），不是 0.01。

⚠ **诚实的预期**：即便头学好，能加的也只在“新激活”那一部分需求上，而它只占未被使用
边的 11.6%。而且 §10.9 测过总可竞争空间只有 2.45%。所以 batch 2 的合理预期是
**方向一致的小效应**，不是翻盘；它的价值主要是**把 v8 这条路走完**（判定“表示/预备
到底有没有用”），而不是指望它超过 v3。

### 10.13 请求流到底是随机的还是有时间规律？（**2026-09-27 实测，结论与配置意图不符**）

**问题**（用户提出）：密钥请求是随机的，还是和时间有关、有规律？

**先看代码**（`qkd_rl/env/request.py` → `RequestGenerator.generate(t)`）：
- 每槽**到达条数** = `rng.poisson(总率)` ⟹ **随机**（泊松）。
- **选哪个 GS 对** = 按 `pair_rates` 做 `rng.choice(p=...)` ⟹ 给定时刻 t 后是确定性概率、
  随机抽样。
- **请求量** = `rng.exponential(amount_mean)` ⟹ 随机。
- 速率表本身**只依赖 t**（不依赖历史），所以**整个流的统计特性是 t 的确定函数**。

**所以答案是“两层”：数量随机，速率与偏好由时间确定。**

**★ 但实测发现：配置里那个 13× 的昼夜周期，在环境里几乎不存在。**

配置 `hourly_weights` = `[0.15 … 1.3 … 0.25]`，峰谷比 **13.0×**，本意是明显的日周期。
实测（14–20 天合并、以及不采样的解析计算）**全局每 UTC 小时的到达率**：

| 口径 | 峰谷比 | 日内 CV |
|---|---|---|
| 忽略时区（配置字面） | **13.00×** | 0.606 |
| **实际生效（时区感知 + Zipf 权重）** | **1.23×** | **0.058** |

**原因**：`generate()` 走的是**时区感知分支**——每个配对用**其源节点的本地小时**
（`local_hour = (t//60 + tz_off) % 24`）取 `hourly_weights`。29 个 GS 分布在全球
（时区偏移横跨 −8…+12，18 个不同值），任一时刻总有节点在高峰期、有节点在低谷，
**求和后互相抵消**。解析计算（带 Zipf 权重，与代码逐项一致）给出 1.23×，
采样给出 1.26×（r=0.88，差异来自泊松噪声）⟹ 两种口径互相印证。

**⟹ 三条对建模有直接影响的结论**：

1. **全局到达率基本是平的（~1.2×）**。模型输入的 `minute_of_day_sin_cos` 是**全局** `t`，
   而全局流量没有明显日周期 ⟹ **这个时间特征在当前环境下几乎没有预测力**。
2. **周期性在“节点/配对”层面，不在全局层面**：每个配对按其**源节点本地时**有
   13× 的日内摆动，但聚合后被抹平。模型拿到的是**单一全局时间**，要靠**节点身份**
   才能推回各自的本地时（可学，但很间接）——这是**特征上的一个错配**，值得记。
3. **热点 GS 对是固定常数**：`pair_hotness: zipf, pair_seed: 0`，`pair_seed`**不随
   `--seed` 变** ⟹ **所有训练种子、所有回合看到的是同一组热点对**。实测集中度很高：
   `MexicoCity→NewYork` 占 **15.4%**，前三对 28%，前十五对约 55%（共 406 个可能对）。

**对 v8 那条路的意义**：请求流**有强确定性结构**（固定热点对 + 节点本地周期），
所以“预测哪些边将来会被用”**本来就应该可预测**——这与 §10.12 实测「新激活 AUC 0.63」
一致。但也提醒：**若要靠时间特征，得用节点本地时间而不是全局时间**，否则那一路信息
在输入里是错位的。

**工具**：`.tmp/probe_request_periodicity.py`（直接调 `generate(t)` 采样）、
`.tmp/probe_request_tz_smoothing.py` / `.tmp/probe_request_zipf_cycle.py`（解析对照，
无采样噪声）。

### 10.14 v8 batch 2：按第一批的诊断改三处（**2026-09-27 已启动**）

第一批（§10.12）的三条实测直接决定了这一批改什么：

| 第一批的诊断 | batch 2 的改动 | 依据 |
|---|---|---|
| 行为臂是**空操作**（偏置只有分数 std 的 0.05%） | `bias_weight: 0.01 → 4.0` | 训练后 |tanh(logit)|≈0.05、分数 std≈1.05 ⟹ w=4 约 20% 分数 std |

**★ 关于 recency 这一列，先验了一个容易搞错的点**：我先前测出 AUC 0.63 的

| 候选特征 | AUC（对 `new` 靶子） |
|---|---|
| **实装的『衰减计数』** | **0.6240** |
| 『历史上用过(0/1)』 | 0.4731 |
| 『1/(1+距上次使用槽数)』 | 0.6136 |

⟹ 实装的那一列**不弱于**先前测到的 0.63，可以直接用。
（顺带纠正一个读法：冒烟测试里 recency 与标签的 **Pearson r 只有 0.094**，
看起来像“死列”。但关系是**非线性**的，`r` 会被这一点严重低估——
判据要用 **AUC** 而不是相关系数。这条记下来，因为很容易照着 `r` 把好特征删掉。）

**接线验证（启动前的硬门，全过）**：
- 维度：`physical_edge_dim` 28 → **29**（正好 +1）。

  这一条很重要：新特征若要靠丢权重换来，就与 v3 对照不可比了。
- `new` 标签基准率 **0.1248**（vs 第一批 `used` 的 **0.179**）⟹ 持续性确实被扣掉，
  且非空。
- trainer 自己的损失路径：`loss_weight=0.05` 与 `=0` 的 actor_loss 差 **Δ=+0.0337**，
  头 4/4 张量有梯度 ⟹ **不是空操作**。

**批次**：`v8b2loss`（表示臂）/`v8b2bias`（行为臂）× s42/43/44，4 并发×16 线程，
`Threads: torch=16 OMP=16 MKL=16` 已确认。

**对照与判读**（同一 BC、同一 20 轮预算，对照是现成的 `pairhot20_v3_s{42,43,44}`）：
- `v8b2loss − v3` = 表示效应（与第一批的 +0.0038 对照，看换标签+加特征有没有改善）

### 11.12 失败解剖：丢掉的密钥去哪了？（2026-09-27 07:35）

`scripts/diag/failure_anatomy.py`（开发种子 100–104，s42 检查点，结果 `outputs/eval/anatomy3_*.json`）。
对每个到期未完成请求，在"生命周期内逐步可见 ∪ 有库存"的边上用 0-1 BFS 找缺货跳最少的路径，给缺货跳归类；
不连通者再看并上到达前 W 步可见边后能否连通（密钥不过期 ⟹ 提前囤货可行）。
注：流体 UB 输出里的 routable_amount 只检查端点是否在图里，**不是**连通性，不能当"可路由"用。

**彻底无路**（回合开始以来所有出现过的边都连不通）：2× 13.85%、3× 13.55%，所有策略相同 ⟹ 任何策略都救不了。
扣掉后，可路由需求上的服务率（2×）：UB 94.6%、noattbias 86.5%、专家 82.8%。

可控损失分解（占到达量）：

| 类别 | 2× 专家 | 2× v3 | 2× noatt | 2× noattbias | 3× noatt | 3× noattbias |
|---|---|---|---|---|---|---|
| 没提前囤货（到达前 30–120 步可见过） | 2.3 | 2.4 | 2.9 | **3.1** | 4.5 | **4.9** |
| 瓶颈跳激活过但不够（非端口原因） | 4.6 | 2.4 | 3.2 | 2.3 | 2.4 | 3.4 |
| 端口冲突（omitted_busy + drained_busy） | 4.1 | 4.0 | 3.9 | 2.8 | 8.3 | 6.7 |
| 存货被抢光 | 1.5 | 1.0 | 1.0 | 0.9 | 1.6 | 0.9 |
| 可见、端口空闲却没开 | 0.3 | 2.7 | 1.9 | **0.5** | 3.4 | **0.4** |

结论：
1. 预测头的增益 ≈ 消灭"可见、端口空闲却没开"（2.1–2.7 → 0.5），与 +0.03 吻合；注意力在任何一类上都没有差别。
2. 最大的可控块是**提前囤货**（3–5 个点）：需要提前 30–120 步预判，而模型只看当前可见边未来 6 步
   （prediction_horizon: 6），且看不到"有存货但不可见"的边（include_stocked_edges: false）⟹ 信息缺失，学不会。
3. 第二块是端口冲突（3–7 个点，3× 更大）：同一节点的端口在多条候选弧之间的分配 ⟹ 联合决策问题。
4. ⟹ 注意力的新角色候选：**在未来接触计划（确定、可预知）上推理**，回答"哪条边快消失、消失后哪些请求对没路"。
