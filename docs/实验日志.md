## 第一部分：统一的评测环境（**这是基准，所有对比都必须用这一套**）

### 1.1 两个 regime 的区分（**别混**）

| | **训练 regime** | **验证 regime** |
|---|---|---|
| 天数窗口 | 0–295（`activation_window` 限制回合**起始日**） | **330–365** |
| 回合长度 | **1440 步** | **240 步** |
| 回合起始模式 | `random_day` | `random_day` |
| 种子（请求） | 训练种子 `--seed` | **100–114（固定 15 个）** |
| 出处 | `configs/train_full_rl.yaml` 的 `env:` | 同文件的 `validation:` |

**两个 regime 不可混用**：训练侧成功率 ~0.86 已近饱和（看不出差距），
差距在验证 regime。

### 1.2 验证 regime 的规范构造（**唯一入口**）

```python
# qkd_rl/evaluation/test_protocol.py
load_validation_profile(cfg_path)      # 读 validation 段；读不到就抛错，不用默认值兜底
build_validation_env_config(profile, include_baselines=..., episode_steps=240, start_mode="random_day")
```

**配置链**（`build_validation_env_config` 内部）：

```
load_default_config()
  → deep_merge(configs/env_full.yaml)          ← ★ 我们改的 exclude 在这里
  → deep_merge(configs/baselines.yaml)         （仅 include_baselines=True 时）
  → rate_provider.provider = "h5"
  → env.episode_start_mode = "random_day"
  → env.episode_steps = 240
  → activation_window = [330, 365]、window_days = 35
  → scenario.time_limit.days = 365 + ceil(240/1440) = 366
```

**★ 关键**：`env_full.yaml` 被套在这一层——所以**专家、基线、训练器的
`evaluate_validation` 读的是同一份配置**（含 `exclude: [Stockholm]`）。

### 1.3 三个评测入口（**已对齐，写新脚本照抄任一处**）

| 入口 | 文件 | 说明 |
|---|---|---|
| 专家 | `scripts/eval/eval_expert.py --seeds 100-114` | 用 `PathScoreGreedy(weights=(1,10,1,0.5,0.2), phased=True, principles=False, router=ServeProbe(env))` |
| 全部基线 | `scripts/baselines/run_baselines.py` | 读 `configs/baselines.yaml` 的开关 |
| 训练器内置 | `mappo_trainer.evaluate_validation()` | 用 `validation.request_seeds = [100..114]`、`episodes: 15` |

**★ 三处的种子来源**（已核实一致）：

```yaml
# configs/train_full_rl.yaml
validation:
  window: {start_day: 330, end_day: 365}
  start_mode: random_day
  episode_steps: 240
  episodes: 15
  request_seeds: [100, 101, ..., 114]
```

⚠ **`configs/global.yaml` 里的 `validation.request_seeds: [7,8,9,10,11]` 和
`episodes: 5` 是旧的**，训练与专家脚本都**不读它**（被 `train_full_rl.yaml`
覆盖，或由 `--seeds` 覆盖）。**别照 global.yaml 写种子。**

### 1.4 评测调用路径的 token 级细节（**可比性的前提**）

RL 策略 step 环境时必须传：

```python
env.step(actions, scores,
         edge_scores=st.edge_scores,
         expected_matched_edges=(None if resolver_mode in DETERMINISTIC_RESOLVER_MODES
                                 else list(st.matched_edges or [])))
```

专家是 `env.step(actions, scores)`（不传 edge_scores）。
`eval_expert.py`、`Evaluator._act`、`trainer.evaluate_validation` **三处已对齐**。

### 1.5 `start_seed` 的用法（**容易错**）

```python
env.reset(seed=seed, start_seed=start_seed_base + seed)
```

- `seed` = **请求种子**（100–114）
- `start_seed_base` = `validation.start_seed`（默认 **0**）
- 两者相加是环境起日种子 ⟹ **专家脚本与训练器用同一加成**

### 2.3 基线因删节点而上升（**配对，同 15 种子**）

| 策略 | 不删 | 已删 | Δ | 同向 |
|---|---|---|---|---|
| random | 0.126321 | 0.130057 | +0.0037 | 7/15 |
| greedy_qkp | 0.107498 | 0.121392 | +0.0139 | 8/15 |
| greedy_relay_diffusion_v3 | 0.378926 | 0.397530 | +0.0186 | 10/15 |

| **expert** | 0.697922 | **0.767435** | **+0.0695** | **15/15** |

**★ 全部 8 个同向上升**，但幅度差 **12 倍**（random +0.4 点 vs 专家 +6.95 点）
—— 弱策略本来就没在服务，少掉不可达需求对它们影响小。

**机制对账（不是分母效应）**：

```
arrived（分母）= 18,078,315 → 18,126,378   +0.27%   ← 几乎没变
served （分子）= 12,879,569 → 14,107,397   +9.53%   ← 在这里
```

请求总数不变（总到达率固定），但原来 6.67% 的对贡献 arrived、贡献 0 served。
删掉后同样多的请求全落在可服务的对上。

### 2.4 读数可信度（**独立复现**）

配对探针与单独跑的 `run_baselines`（同 5 个种子 100–104）**逐位一致**
（差 `0.00e+00`）⟹ 两个入口给出相同读数。

### 2.5 基线怎么用（**判据，别用错**）

| 用法 | 对 | 错 |
|---|---|---|
| 与**专家**比 | ✅ 专家 0.767435 是论文的对照锚 | — |
| RL 臂之间比 | ✅ 必须**同环境**（都删了节点） | ❌ 拿旧环境的臂比新环境 |
| 拿 `greedy_relay` 当对照 | ⚠️ 比专家弱 27 点，只能说明「比弱基线好」 | ❌ 拿它当「击败对象」 |
| 比绝对值 | ⚠️ 跨策略绝对值无意义 | ❌ 用 Δ 之外的量下结论 |
| 配对 | ✅ 必须**逐种子配对**（不配对 SE≈0.062，配对≈0.012） | ❌ 只看均值差 |

## 第三部分：待讨论（**训练什么，由用户定**）

以下是我认为需要讨论的点，**不是我要执行的计划**：

1. **RL 臂要在新环境重跑**——旧臂跑在含 Stockholm 的环境上，
   无法与专家 0.767435 对比。重跑要几个种子？
2. **奖励改动**（用户提的失败惩罚 + 成功率 delta）——有一处前置测量没做：
   `failed` 与 `served` 是否高度负相关？若是，加大惩罚 ≈ 加大 served 权重，**冗余**。
3. **预训练是否困住上限**（用户的假设②）——从零训对照的种子扩展。
4. **GNN 是否过重**（E1 去图臂）——n=5 时 p=0.053，差一点。
