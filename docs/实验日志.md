## 第四部分：urgency 加权等待惩罚 —— 对比训练计划（**2026-09-22 定**）

> **状态**：机制已实现并验收（四道门全过），**尚未起臂**。

### 4.1 机制一句话

每个**未被服务**的请求按**剩余寿命**加权后被罚：

```
urgency(req) = 1 − 剩余步数 / deadline_steps     （0 = 刚到，1 = 快死）
penalty      = urgency_wait_weight × Σ urgency×剩余量 / served_reference
```

逐 step 计算 ⟹ **及时**；**不规定顺序**（模型自己决定先做谁，只是救急的回报更高）。

### 4.2 为什么需要它（与现状的对照）

生效配置里三项奖励（训练 regime 实测 570 轮）：

| 项 | 每步均值 | 占 served | 对 urgency 敏感吗 |
|---|---|---|---|
| `served_weight`（服务成功） | 0.066313 | 100% | ❌ 服务 1 个 key 恒定给 5e-4，不论多急 |
| `failed_weight`（过期失败） | 0.001068 | **1.61%** | ❌ 只在过期那一刻扣，是**事后**信号 |
| **`urgency_wait`（新）** | 见 4.4 | — | ✅ **唯一的「优先救谁」方向信号** |

**★ 关键**：`served` 与 `failed` 只定奖励**水平**，不定**方向**——
服务 A 而让 B 过期，净得 `w_s − w_f`；反过来选 B 一样。
只有 urgency 项能区分「先救急的」和「先服务从容的」。

### 4.3 验收记录（起臂前必须全过）

| 门 | 判据 | 结果 |
|---|---|---|
| ① | 诊断字段 `urgency_weighted_keys` 不被 `reward_scale` 缩放 | ✓ 逐位一致 |
| ② | 手算 = env 输出（4 个抽样点） | ✓ 逐位一致 |
| ④ | `w=0` 时新项逐位为 0，且 served/failed 逐位不变 | ✓ 正交 |

**造反证抓到我自己的两个错误**（都已修）：

1. 诊断字段被 `reward_scale=0.002` 缩放（手算 280,013 vs env 510，差 549 倍）
2. **权重推导多除了一次 `served_reference`**——三项共用同一分母，做比值时约掉，
   正确值是 `w = failed_weight/14.5 ≈ 0.345`，不是 3.2e-6（差 5 个数量级）

### 4.4 剂量臂设计

**唯一变量**：`reward.urgency_wait_weight`。其余全部锁定。

| 臂名 | `urgency_wait_weight` | urgency 项/步（预检实测） | 占 served |
|---|---|---|---|
| **`u0`（对照）** | `enabled: false` | 0 | 0% |
| **`u1`（0.5×）** | 0.17 | 0.00104152 | 2.35% |
| **`u2`（1×）** | **0.35** | **0.00214431** | **4.83%** |
| **`u3`（2×）** | 0.70 | 0.00428863 | 9.66% |
| **`u4`（4×，上界）** | 1.40 | 0.00857725 | 19.32% |

> ★ 上表是**预检实测**（`probe_urgency_precheck.py`，验证 regime，专家策略，
> 40 步，种子 100）。此前一版用**训练 regime** 的 `waiting_keys` 外推，
> 得到 u2=1.98% —— 两个 regime 的积压量不同，**以预检实测为准**。
> 剂量仍是**线性**的（0.17→1.40 恰好 8 倍，占比 4.83%→19.32% 也约 4 倍，
> 因为占比里 served 项相同），所以「剂量」这个旋钮是**单调可控**的。

**`u2` 是「让等待与失败同等重要」的点**（4.83% vs failed 的 1.61%，即等待被罚得比失败更重），
是推导出来的平衡点，不是拍的。`u1/u3/u4` 用来量曲线形状。

### 5.1 两处改动（都是**模型结构**，会改参数量）

#### 改动 A：删 `actor.idle_scorer`

**位置**：`qkd_rl/rl/models/graph_mappo.py:454-458`（定义）、
`:675` 与 `:1086`（前向两处）。

**为什么是死重**（两条独立证据，见记忆 `idle-scorer-is-dead-weight` /
`idle-scorer-has-no-gradient-not-no-input`）：

| 证据 | 结果 |
|---|---|
| 更新前后权重 | **逐位不动**（`torch.equal` = True，差恰好 `0.000e+00`） |
| `register_hook` 的梯度 | **一个都没触发** ⟹ 不在计算图里 |

**根因**：`padded_logits`（含 idle 分数的那个张量）**全仓库没有消费者**。
系统的「停」语义完全由 `stop_logit`（一个全局标量）承担——**两条停机制，死了一条**。

**规模**：`actor.idle_scorer.{0.weight,0.bias,2.weight,2.bias}` = 128×128 + 128 + 1×128 + 1
= **16,641 参数 = actor 参数量的 20%**。

#### 改动 B：去 Actor 打分公式的冗余

**位置**：`qkd_rl/rl/models/graph_mappo.py:667-670`

```python
pair_emb = torch.cat([node_emb[src_t], node_emb[dst_t], edge_emb_directed[pos_t]], dim=-1)
edge_scores = self.edge_scorer(pair_emb).squeeze(-1)
```

**问题**：`edge_emb_directed` 是 encoder 的输出，而 encoder 的每一层都做
（`graph_mappo.py:313` `_edge_message`）：

```python
msg = edge_mlp(cat([edge_emb, new_node[src], new_node[dst]]))
new_edge = edge_norm(msg + edge_emb)
```

⟹ **边嵌入里已经含有它两个端点的节点信息**（还经过 3 层累积）。
Actor 又把 `node_emb[src]`、`node_emb[dst]` 拼了一遍：**同一份信息进了两次。**

⚠ **这条不是「确定的 bug」**，是**冗余**。MLP 可以学会忽略重复项，
所以效果未知——**必须用实验回答，不能靠读代码断言**。

### 5.4 ★★ 一个必须先说清的妥协：`edge_scorer` 会丢暖启动

**这是本次改动的真实代价，不是没有。**


```python
if data.config.get("reward") != self.config.get("reward"):
    self.model.critic.value_head.apply(_reset_module)   # critic 价值头本来就重置
```

**所以本次改动会丢两层**：`edge_scorer`（因为变窄）+ 本来就会重置的 `critic.value_head`。
**共享 encoder 与其余 actor 部分仍完整保留。**

> 「需求边想象是一个**源**……单向的去扩散到物理边……主要的物理边的选择去满足
> 需求边的请求……**不要用标量，要用向量去扩散**，**不要用经验公式**，
> 如果扩散要像网络一样**可以学习**」
> 「**以需求边为单位去注入**，而不是节点注入……**ab 作为一个整体去注入**，
> ab 和 ba 都是一样的」
> 「**bfs 只是用来筛选的**，筛选出来的边来进行注意力，就是一个需求边对多个
> 物理边的注意力」

### 6.1 现状的两个缺陷（用户指出的）

**缺陷 1：BFS 那个标量是「求和」，AB 和 BC 分不清**

`relay_importance` 对经过的每条请求做**加权求和**，得到**每条物理边一个标量**。
一条物理边如果同时被 AB 和 BC 两条需求覆盖，它只知道自己被「总共需要多少」，
**不知道是 AB 还是 BC**。

**缺陷 2：节点注入也是求和**

```python
# graph_mappo.py:277
aggregated = aggregated + self._node_message(demand_mlp, node_emb, src_d, dst_d, demand_emb)
#                          ↑ index_add_ 到节点，AB 和 BC 在共享节点处被求和
```

**两套现有机制都有同一个缺陷。** 用户的设计是**第一个能区分它们的机制**。

### 6.2 机制：需求边当 Query，在其 BFS 路径上做注意力

```
① BFS 筛选（拓扑事实，不需要学）
   对每条需求边 (src, dst)，筛出所有满足
       dist(src,·) + dist(dst,·) + 1 ≤ max_path_links(=8)
   的物理边 ⟹ 候选对 (需求边 i, 物理边 j)。实测每步 100~460 对。

② 注意力（权重全部可学习，无经验公式）
   Q = 需求边 i 的嵌入              ← ★ 需求边当 Q
   K = 物理边 j 的嵌入
   V = 物理边 j 的嵌入
   α_ij = softmax_j( <Q_i, K_j> / √H )    ← ★ softmax 在**每条需求自己的候选集**内
   ctx_i = Σ_j α_ij · V_j                  ← 这条需求看到的「整条通道状况」

③ Scatter 回写（把需求的判断写回它路径上的边）
   phys_emb[j] += W_out · ( α_ij · ctx_i )   ← 按注意力权重加权回写
```

**为什么需求边当 Q 是对的**（用户 2026-09-22 指正，我先前讲反了）：

> **一条物理边看不见整条路径，但一条需求边看得见。**
> 而「服务需要连成通道」是**需求的属性**，不是链路的属性。

★ 而且 `α_ij` 天然能学出「**这条路径上哪一跳最关键**」——
这正是 `v2_bottleneck` 手工表达的那个量（`argmin(hop_levels)`）。
让网络自己学，比写死公式好。

|---|---|---|---|---|

### 6.4 ★ BC 暖启动：**能用，但取决于怎么改**

| 改法 | BC 可用？ | 可检测效应 |
|---|---|---|
| **只加**新通路 + **零初始化** + 配置开关默认关 | ✅ **完整保留** | **0.008** |


### 6.5 ★★ 必须带的检查：新通路的**梯度范数**

若新通路梯度恒零，说明训练真饱和了，**所有增益类旋钮都该停**，方向要转向别处。
这比单看成功率差更有信息量。

### 6.9 实现时必须处理的坑

**坑 1：需求边在 `edge_index` 里是加倍**

```python
# graph_builder.py:404-405 docstring
"""physical edges first as (src,dst) then (dst,src),
   followed by the same doubled representation for demand pairs."""
```

⟹ `edge_index` 里需求部分有 `2*n_demand` 行，而 `demand_emb` 只有 `n_demand` 行。
**下标对不上**，直接写会静默取错行（不报错，结果错）。
映射：`edge_index` 里第 `2*n_phys + 2*i(+1)` 行 ⟹ `demand_emb[i]`。

**坑 2：零候选必须输出 0**

`α` 在空集上做 softmax 会得 NaN。必须显式处理，且造反证要覆盖。

**坑 3：BFS 索引每步重建**

需求边和物理边**每步都在变**（实测 1~12 条 / 134~205 条），
所以稀疏对 `(i, j)` 必须**每步重建**。用 numpy 建索引，切成 `index_add_` /
`segment_softmax` —— 与现有 `_node_message` 同一路子。

## 第七部分：需求 → 物理边 的路径内注意力（**2026-09-22 设计定稿，待执行**）

> **状态**：**设计定稿，未实现**。
> **触发条件**：第五部分（去死重）、第六部分之后。
> **与第六部分的关系**：第六部分是**初版设计**；本部分是**用户澄清后的定稿**，
> 两者是同一件事的两个版本，**以本部分为准**。

### 7.1 用户的最终设计（原话）

> 「标准的注意力**不要全局一起做，单独一个请求边做**，先用 BFS 筛选，
> 然后把筛选的边做**自注意力**，结果和需求边做**交叉注意**」

**三步**：

```
对每一条需求边（一个 GS 对 A→B）：

① BFS 筛选
   筛出这条需求**路径上**的物理边
   候选集 = 路径上的边 ∈ (活跃边 ∪ 有存量密钥的边)

② 自注意力（★ 只在这条需求的候选集内做，不是全局）
   筛出来的这些边互相注意 ⟹ 得到"这条通道"的整体表示
   （因为它们是**同一条通道的组成部分**，彼此配合关系真实存在）

③ 交叉注意
   需求边当 Q，去查 ② 融合出来的结果
   ⟹ 输出这条需求看到的"通道状况"

最终：活跃边拿到属于它的分数 / 选择依据
```

### 7.2 为什么不能全局做（用户的判断是对的）

**全局自注意力会引入虚假关系**：

```
全局：北京→东京 的边  与  伦敦→纽约 的边  互相"注意"
      但在物理上它们毫无配合关系
      ⟹ 模型学到的是"任意两条边都可能相关"
      ⟹ 与"能不能凑出通道"无关
```

**按路径做则只保留真实关系**：

```
需求 A→B 的路径 = {边 x, y, z}
  ⟹ x、y、z 互相注意（它们是同一条通道，**真的需要配合**）
  ⟹ x 不去注意别的路径上的边
```

**⟹ 这正是 BFS 筛选的用途**：它回答「哪些边属于同一条通道」。

### 7.3 存量边的角色（用户 2026-09-22 澄清）

> 「库存边就是为了**提供信息**的，让模型判断如果现在选择某一个边，
> 对现在的情况来说**能不能凑出来通道**来满足请求」

| 边类型 | 提供信息 | 接受注入 | 理由 |
|---|---|---|---|
| **活跃边** | ✅ | ✅ | 它会被激活、会生成密钥 |
| **有存量的边** | ✅ | ❌ | 只回答"这里还有多少货" |

**★ 实现上是自然的**：存量边**本来就不在 `physical_edge_ids` 里**，
`phys_emb` 里没有它们的位置 ⟹ **想注入也没有地方可写**。
不需要额外机制去压制。

**★ 而且这是自动的**：损失只通过**活跃边**的分数回传，
存量边的输出**没有梯度来源** ⟹ 模型会自然专注于活跃边。
（用户原话：「库存边无论输出什么都不影响，就会去专注与可选择边的输出」）

### 7.4 实测规模（2026-09-22）

### 7.5 ★★ 但有一个物理约束必须在聚合里体现

**「凑出通道」是 AND 逻辑，注意力是加权平均。**

```
能不能服务 ⟺ min(路径每一跳的密钥) > 0    ← 全都要有货
              （routing.py:238 `min(hop_levels)`）
注意力输出  = Σ α·v                        ← 平均，弱跳被抹平
```

**只用注意力，模型学不到「这条通道能不能走通」。**

**这个项目已经证明过同一件事**：`cmax` 臂给 critic 加 **max 池化**，
因为「全仓池化只有 mean，而瓶颈是 **min** 型」。

**⟹ 聚合必须两路**：

| 路 | 形式 | 表达 |
|---|---|---|
| **mean 路** | `Σ α_ij · v_j`（注意力） | 通道**整体**状况 |
| **min 路** | `min_j(该跳的可用量)` | **最弱一环**有多少货 |

**两路拼起来才是完整的「这条路径现在能不能凑出来」。**
