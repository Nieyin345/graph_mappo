## 第四部分：urgency 加权等待惩罚 —— 对比训练计划（**2026-09-22 定**）

> **状态**：机制已实现并验收（四道门全过），**尚未起臂**。

### 4.1 机制一句话

每个**未被服务**的请求按**剩余寿命**加权后被罚：

```
urgency(req) = 1 − 剩余步数 / deadline_steps     （0 = 刚到，1 = 快死）
penalty      = urgency_wait_weight × Σ urgency×剩余量 / served_reference
```

逐 step 计算 ⟹ **及时**；**不规定顺序**（模型自己决定先做谁，只是救急的回报更高）。

### 4.2 为什么需要它（与现状的对照）

生效配置里三项奖励（训练 regime 实测 570 轮）：

| 项 | 每步均值 | 占 served | 对 urgency 敏感吗 |
|---|---|---|---|
| `served_weight`（服务成功） | 0.066313 | 100% | ❌ 服务 1 个 key 恒定给 5e-4，不论多急 |
| `failed_weight`（过期失败） | 0.001068 | **1.61%** | ❌ 只在过期那一刻扣，是**事后**信号 |
| **`urgency_wait`（新）** | 见 4.4 | — | ✅ **唯一的「优先救谁」方向信号** |

**★ 关键**：`served` 与 `failed` 只定奖励**水平**，不定**方向**——
服务 A 而让 B 过期，净得 `w_s − w_f`；反过来选 B 一样。
只有 urgency 项能区分「先救急的」和「先服务从容的」。

### 4.3 验收记录（起臂前必须全过）

| 门 | 判据 | 结果 |
|---|---|---|
| ① | 诊断字段 `urgency_weighted_keys` 不被 `reward_scale` 缩放 | ✓ 逐位一致 |
| ② | 手算 = env 输出（4 个抽样点） | ✓ 逐位一致 |
| ④ | `w=0` 时新项逐位为 0，且 served/failed 逐位不变 | ✓ 正交 |

**造反证抓到我自己的两个错误**（都已修）：

1. 诊断字段被 `reward_scale=0.002` 缩放（手算 280,013 vs env 510，差 549 倍）
2. **权重推导多除了一次 `served_reference`**——三项共用同一分母，做比值时约掉，
   正确值是 `w = failed_weight/14.5 ≈ 0.345`，不是 3.2e-6（差 5 个数量级）

### 4.4 剂量臂设计

**唯一变量**：`reward.urgency_wait_weight`。其余全部锁定。

| 臂名 | `urgency_wait_weight` | urgency 项/步（预检实测） | 占 served |
|---|---|---|---|
| **`u0`（对照）** | `enabled: false` | 0 | 0% |
| **`u1`（0.5×）** | 0.17 | 0.00104152 | 2.35% |
| **`u2`（1×）** | **0.35** | **0.00214431** | **4.83%** |
| **`u3`（2×）** | 0.70 | 0.00428863 | 9.66% |
| **`u4`（4×，上界）** | 1.40 | 0.00857725 | 19.32% |

> ★ 上表是**预检实测**（`probe_urgency_precheck.py`，验证 regime，专家策略，
> 40 步，种子 100）。此前一版用**训练 regime** 的 `waiting_keys` 外推，
> 得到 u2=1.98% —— 两个 regime 的积压量不同，**以预检实测为准**。
> 剂量仍是**线性**的（0.17→1.40 恰好 8 倍，占比 4.83%→19.32% 也约 4 倍，
> 因为占比里 served 项相同），所以「剂量」这个旋钮是**单调可控**的。

**`u2` 是「让等待与失败同等重要」的点**（4.83% vs failed 的 1.61%，即等待被罚得比失败更重），
是推导出来的平衡点，不是拍的。`u1/u3/u4` 用来量曲线形状。

### 5.1 两处改动（都是**模型结构**，会改参数量）

#### 改动 A：删 `actor.idle_scorer`

**位置**：`qkd_rl/rl/models/graph_mappo.py:454-458`（定义）、
`:675` 与 `:1086`（前向两处）。

**为什么是死重**（两条独立证据，见记忆 `idle-scorer-is-dead-weight` /
`idle-scorer-has-no-gradient-not-no-input`）：

| 证据 | 结果 |
|---|---|
| 更新前后权重 | **逐位不动**（`torch.equal` = True，差恰好 `0.000e+00`） |
| `register_hook` 的梯度 | **一个都没触发** ⟹ 不在计算图里 |

**根因**：`padded_logits`（含 idle 分数的那个张量）**全仓库没有消费者**。
系统的「停」语义完全由 `stop_logit`（一个全局标量）承担——**两条停机制，死了一条**。

**规模**：`actor.idle_scorer.{0.weight,0.bias,2.weight,2.bias}` = 128×128 + 128 + 1×128 + 1
= **16,641 参数 = actor 参数量的 20%**。

#### 改动 B：去 Actor 打分公式的冗余

**位置**：`qkd_rl/rl/models/graph_mappo.py:667-670`

```python
pair_emb = torch.cat([node_emb[src_t], node_emb[dst_t], edge_emb_directed[pos_t]], dim=-1)
edge_scores = self.edge_scorer(pair_emb).squeeze(-1)
```

**问题**：`edge_emb_directed` 是 encoder 的输出，而 encoder 的每一层都做
（`graph_mappo.py:313` `_edge_message`）：

```python
msg = edge_mlp(cat([edge_emb, new_node[src], new_node[dst]]))
new_edge = edge_norm(msg + edge_emb)
```

⟹ **边嵌入里已经含有它两个端点的节点信息**（还经过 3 层累积）。
Actor 又把 `node_emb[src]`、`node_emb[dst]` 拼了一遍：**同一份信息进了两次。**

⚠ **这条不是「确定的 bug」**，是**冗余**。MLP 可以学会忽略重复项，
所以效果未知——**必须用实验回答，不能靠读代码断言**。

### 5.3 ★ 起臂前必须过的预检（**这次比以往更严**）

这两处改动**会改模型结构**，所以过去那套「差异字段 + 维度 + BC 权重」要收紧：

| 门 | 判据 | 为什么 |
|---|---|---|
| ① 差异字段 | 恰好是 `idle_scorer`（删除）+ `edge_scorer`（第一层输入 384→128） | 证明单变量 |
| ② **维度** | `node_dim` / `edge_dim` **不变** | 保证 BC 起点可用 |
| ③ **BC 权重加载** | `idle_scorer` 的 4 个键会出现在 **`unexpected`（多余）** 里，**这是预期的**；`missing`（缺失）必须为 **0** | 见 5.4 |
| ④ **`edge_scorer` 的形状** | `edge_scorer.0.weight: (128, 384) → (128, 128)` ⟹ **变窄，补零救不回** ⟹ 这层**会进 `dropped`** | ★ 必须先确认丢掉它不致命 |
| ⑤ **造反证** | 跑 1 轮训练，确认能正常出 `update` 行、无异常 | 防「配了但没接线」 |

### 5.4 ★★ 一个必须先说清的妥协：`edge_scorer` 会丢暖启动

**这是本次改动的真实代价，不是没有。**

```
edge_scorer 输入 = [起点节点(128), 终点节点(128), 边嵌入(128)] = 384 维
去掉重复端点后 = [边嵌入(128)]                                    = 128 维
```

**变窄 ⟹ `_expand_last_dim` 救不回**（那个函数只能加宽）⟹ `edge_scorer.*` 会进
**`dropped`**，即**该层回到随机初始化**。

同时注意 `load_checkpoint` 里还有一条（`mappo_trainer.py:1690`）：

```python
if data.config.get("reward") != self.config.get("reward"):
    self.model.critic.value_head.apply(_reset_module)   # critic 价值头本来就重置
```

**所以本次改动会丢两层**：`edge_scorer`（因为变窄）+ 本来就会重置的 `critic.value_head`。
**共享 encoder 与其余 actor 部分仍完整保留。**

⚠ **这降低了可检测效应**（暖启动损失 ⟹ 族内方差上升）。起臂前**必须**用探针量出
新族的 `Δ_s` SD，据此报「可检测效应」，否则会重蹈 `demand_edge` 那种「测不出却以为是无效」。

### 5.5 判据（预注册）

| 结果 | 阈值 |
|---|---|
| **清理有效** | Δ ≥ +0.020 且 5/5 同向 ⟹ 死重/冗余确实在损害性能 |
| **清理有害** | Δ ≤ −0.020 且 5/5 同向 ⟹ ★ 说明「冗余」其实在起作用（容量/正则） |
| **测不出** | \|Δ\| < 0.020 ⟹ 写有界结论：**影响 < X 点，但换来了更小的模型** |

**★ 「测不出」也是有用结果**：若清理后性能不变，那就是「参数少了 20%+ 而性能不掉」，
对论文的**模型简洁性**是一个正面证据。**这种情况要额外报参数量与推理时间的前后对比。**

### 5.7 与已有结论的关系

- 记忆 `idle-scorer-is-dead-weight` 与 `idle-scorer-has-no-gradient-not-no-input`：
  两条独立证据都指向「死重」，**本实验把「死重」升级为「删掉有没有代价」的实测**。
- ⚠ **`scripts/diag/probe_idle_del_risk.py` 的结论已过期**：它说「checkpoint 里存着
  `actor.idle_scorer.*` 的键，而 `load_state_dict` 没有 `strict=False` ⟹ 删模块会抛异常」。
  **实测（2026-09-22）该链路已被取代**：`mappo_trainer.py:1666` 先调
  `_upgrade_state_dict_for_model`，它把「模型里不存在」的键收集进 `unexpected` 并**忽略**
  （`:1685` 打印「checkpoint 多余 N 个键，已忽略」），再 `load_state_dict(state)`。
  ⟹ **删模块是安全的**，只是会打印一行「多余 4 个键」。
- **同族**：本仓库的「存在但没接线」（`history_encoder` 37,760 参数、
  `success_delta` 权重 50）——本实验是针对这一类失效的**第一次实测**。
