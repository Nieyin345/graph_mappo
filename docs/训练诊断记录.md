## 探针 A：PPO 比率正确性 ✅ 已排除

**问题**：rollout 存下来的 log-prob，和更新时重算的，是不是同一个定义？
不一致的话比率会系统性偏离 1，PPO 就在优化错的目标。

**脚本**：`.tmp/probe_ppo_ratio.py`
**方法**：同一份策略、同一批观测，先走 rollout 路径采样并记录 `mean_log_prob`，
再用 `evaluate_actions_batched` 对**同一批动作序列**重算，逐条比较。
200 个样本（8 环境 × 25 步）。

**结果**：

```
更新期重算 − rollout 存储的 log-prob：
  均值        -2.38e-09
  标准差       2.00e-07
  最大绝对值   7.15e-07
  隐含比率     mean 1.000000  (min 0.999999, max 1.000000)
参考量级：log-prob 均值 -3.6221，标准差 0.2385
```

**结论**：差异是纯 float32 噪声（相对 log-prob 标准差是 3e-6 倍）。
**rollout 与更新的 log-prob 定义一致，PPO 比率是对的。**
所以 `mean_ratio` 稳定小于 1 是更新过程中的真实漂移，不是定义错误。

## 探针 B：奖励对动作的敏感度 ⚠️ 部分结论

**问题**：在**同一个环境状态**下换一个合法匹配，即时奖励变不变？
不变的话，策略梯度没有可学的信号。

**脚本**：`.tmp/probe_reward_sensitivity.py`
**方法**：建 K+1 个完全相同环境，同 seed reset、同一个动作同步走到第 t 步
（此时状态完全一致），然后分叉 —— 前 K 个各给一个从策略自身分布独立采样的动作，
最后一个给确定性（贪心）动作。**不需要 deepcopy**，避免复制 H5 句柄。

**结果**（8 个种子 × 分叉步 5/20/60/150，每状态采 8 个动作）：

```
局内标准差（动作引起，同一状态换动作）  0.010790
局间标准差（局面引起，同一动作换状态）  0.043256
信噪比 局间/局内 = 4.009
奖励量级（均值）                        0.0387
贪心动作 − 采样均值（32 个状态的平均）   −0.00015
```

**结论**：

- 奖励**确实对动作有反应**：动作引起的波动 0.0108 是奖励量级 0.0387 的 **28%**。
  所以"奖励完全不区分动作"这个假设**不成立**。
- 但单步信噪比只有 1/4（局面影响的波动是动作的 4 倍）——这在 RL 里正常，
  靠 baseline 扣掉，而 critic 确实做到了（`corr(V,R)→0.99`）。
- **贪心动作并不比随机采样更好**（−0.00015，相对动作波动 0.011 可忽略）。
  说明**即时奖励不是策略区分动作的依据**，得看多步。这一条待细查。

**待办**：按 `info['reward_detail']` 分项拆开，看**动作真正能推动的是哪几项**。
served 是主项（`served_weight 50 / served_reference 1e5`，约 21/步原始值），
如果主项对动作不敏感、敏感的是几个小项，那梯度方向就是被小项主导的。

## 探针 C：策略梯度是信号还是噪声 ⚠️ 指向优化过程

**脚本**：`.tmp/probe_grad_coherence.py`
**做法**：收集一次真实 rollout（11520 条样本），按 `update()` 的方式切 minibatch，
对每个 minibatch 单独反传拿到 **actor（策略参数组）梯度**，比较两两余弦与合矢量长度。

**结果**（45 个 minibatch，990 个配对）：

```
normalize_advantages = True （现状）
  两两余弦：均值 -0.0052   中位数 +0.0023   范围 [-0.81, +0.80]
  与合梯度的余弦：均值 +0.1242
  ||Σg|| / Σ||g|| = 0.0988        （方向完全一致=1.0，互相独立=1/√45=0.1491）

normalize_advantages = False
  两两余弦：均值 -0.0060
  与合梯度的余弦：均值 +0.1241
  ||Σg|| / Σ||g|| = 0.1287        （独立噪声参考 0.1491）
```

**结论**：

- 每个 minibatch 梯度与真实梯度的对齐度只有 **~12%**（`与合梯度的余弦` = 0.124），
  而 Adam 会把梯度幅度归一化掉，所以 45 步里约 88% 的方向是噪声。这与"每轮 KL
  只有 0.001（目标 0.02）""成功率平""熵在涨（随机游走）"三个现象一致。
- **正确解读这个 0.124**：设每样本梯度独立同分布，则该余弦的理论下界是
  `√(m/N) = √(256/11520) = 0.149` —— 这个下界对应的情形恰恰是**真实期望梯度 ≈ 0**，
  此时整批的合梯度本身就是噪声的平均。实测 0.124 略低于它（约 20%），
  属于轻微负相关，**不是"数学上不可能"**。
  **真正的含义是：这一批数据里几乎不存在可用的梯度方向。**
- 这只说明"当前策略在当前训练分布上已经接近驻点"，**不能**据此说策略已最优 ——
  它只说明从训练分布上拿不到改进方向。与"专家在留出窗口上仍高 3 个点"合起来看，
  更像**泛化差距**而不是训练不足（见下）。
- **`normalize_advantages=False` 略好（0.1287 vs 0.0988）但没有质变** ——
  按 minibatch 归一化确实在放大弱信号批，但它不是根因。
- 小样本陷阱：用 8 个 minibatch 时两两余弦是 **-0.085**，看着像强负相关；跑到
  全量 45 个才发现是 **-0.005**（≈0）。**别用 n=8 下结论。**

**判读**：这个批次里没有可用的改进方向。两条岔路 ——
(a) 优化过程本身有问题（步数/步长/归一化），下一步的配置筛选就是测这个；
(b) 策略在训练分布上确实已到驻点，那就得从泛化或观测空间下手。
筛选结果出来才能分。

## 探针 D：学习率从未生效（**真 bug，已修**）

`lr1e3` 和 `base` 的**训练指标逐位相同**（只有 `rollout_s`/`update_s`/`elapsed_s`
三个时间字段不同），而 `resolved_config.yaml` 里两者的 `actor_lr` 确实是
0.0003 与 0.001 —— 配置生效了，但训练没变。这本身就说明学习率没被用上。

**根因**：BC 权重里**带着 `optimizer_state`**，而
`mappo_trainer.load_checkpoint` 里的 `self.optimizer.load_state_dict(...)`
恢复的是**整组 `param_groups`，学习率也在里面**：

```
构造后（配置值）：       encoder 0.0003  actor 0.0003  critic 0.001
checkpoint 里存的：      encoder 0.001   actor 0.001   critic 0.001
热启动之后（修复前）：   encoder 0.001   actor 0.001   critic 0.001   <- 配置被盖掉
热启动之后（修复后）：   encoder 0.0003  actor 0.0003  critic 0.001   <- 配置生效
optimizer.state 条目数 = 91（Adam 动量仍恢复，续训不受影响）
```

**后果**：`rl_algorithm.yaml` 里的 `train.optimizer.actor_lr: 0.0003` **从来没生效过**；
从 BC 权重热启动的每一次训练，encoder/actor 实际都跑在 **0.001** 上。
**此前所有基于学习率的实验和结论全部作废。**

**修复**（`mappo_trainer.py`）：构造时把配置的 lr 记进 `self._configured_lrs`，
`load_state_dict` 之后按它写回 `param_groups`；Adam 的一二阶矩保持不动。

**另一个坑**：确认 checkpoint 内容时我一度用 `getattr(d, "optimizer_state", None)`
—— 而 `torch.save` 存的是 **dict**，`getattr` 在 dict 上取属性会**静默返回 None**，
于是错误地得出"checkpoint 里没有 optimizer_state"。要用 `d["optimizer_state"]`
或先判 `isinstance(d, dict)`。**凡是"没找到"的结论，先确认查找方式对。**

**验证脚本**：`.tmp/probe_lr.py` —— 直接打印"配置值 / checkpoint 里的值 / 加载后实际值"。

## 窗口对比：能力问题，不是泛化问题

**问题**：训练不涨，是"学不到"还是"学过头了（过拟合训练期、泛化不出去）"？
这两者的修法完全不同，必须先分清。

**做法**：让**专家**（没有学习过程，它在各窗口的差异只反映窗口本身的难度）和
**BC 权重**在四个窗口上跑同一协议（12 个种子、240 步），**按种子配对**比。

配对不是可选步骤：逐种子成功率跨度 0.29–0.88，不配对的标准误约 0.06，
测不出 0.02 量级的差距；配对后约 0.012。

| 窗口 | 专家 | BC | 配对差 | 标准误 | t |
|---|---|---|---|---|---|
| early_train (0-35) | 0.7242 | 0.7098 | +0.0144 | 0.0110 | 1.31 |
| mid_train (100-135) | 0.7763 | 0.7168 | **+0.0595** | 0.0212 | 2.81 |
| late_train (200-235) | 0.7756 | 0.7411 | +0.0345 | 0.0155 | 2.23 |
| heldout (330-365) | 0.7359 | 0.6988 | **+0.0371** | 0.0142 | 2.61 |

**差中之差**（留出窗口的差距 − 训练窗口的平均差距）= **−0.0099**，即各窗口的差距
**基本一样大**。

**结论**：策略相对专家的差距**不是分布偏移造成的** —— 它在训练窗口上也没追平专家。
这是**能力问题（欠拟合）**，不是泛化问题（过拟合）。

**推论**：不要往"缩小训练/验证分布差"（正则化、扩充训练窗口、域随机化）的方向修；
该往"让 RL 真正把 BC 权重推得更好"的方向修。而 BC 已经落在训练分布上了，
说明这一步是可达的 —— RL 应当能先在训练窗口上把那 ~0.04 补上。

**顺带排除**：专家自己在留出窗口也只有 0.7359，低于训练窗口的 0.7756（−0.040），
所以留出窗口本身确实略难，但这与策略的差距无关，别把它算到策略头上。

**复现**（都在节点上跑）：
```bash
bash .tmp/screen_windows.sh                    # 专家，四窗口，按窗口分文件
bash .tmp/screen_windows_rl.sh <ckpt> <tag>    # 策略，同种子同窗口
/opt/qkd/venv/bin/python /tmp/compare_windows.py <tag>   # 按种子配对
```

## 第二轮变体筛选（进行中）

### 要先说清楚"涨没涨"是看哪个数

这里有个**一直没讲清、导致前面结论跑偏**的点：

| 指标 | 是什么 | 噪声 |
|---|---|---|
| `mean_success_rate`（训练侧） | **采样**成功率，温度 1.0 | 大 —— 逐种子跨度 0.29–0.88 |
| `eval_validation`（验证侧） | **确定性**策略，固定场景、12 种子 | 小 —— 12 种子均值 SE ≈ 0.012 |

第一轮的 `base`：训练侧 0.7728 → 0.7736（**平**），验证侧却到 **0.8166**。
而 BC 起点的验证侧是 **0.7680**（本轮实测，见下）。所以**训练其实是在涨的**，
只是涨在确定性策略上；训练侧那个采样均值被不断上升的熵（3.92 → 4.15）压平了。

**判据一律以验证侧为准。**

### BC 起点基线（本轮实测，必超的数）

用**训练器自己的 `evaluate_validation`** 取，不是 `run_baselines.py` ——
后者走 `MAPPOTrainer.evaluate`，是另一套协议，混用就没法按种子配对。

| | |
|---|---|
| checkpoint | `outputs/supervised_pg_phased/supervised_pg_phased_latest.pt` |
| 协议 | 固定场景（第 0 天）、240 步、12 种子 (7–18)、确定性 |

### 新增：验证侧记逐种子

`evaluate_validation` 现在把 `per_seed_success` 一起写进 `metrics.jsonl`
（`mappo_trainer.py`）。理由是 SE：均值对均值仍有 0.012 的标准误，而**同种子
对同种子**的配对差才压得下去。没有逐种子，两个变体差 0.02 就会被判成噪声。
冒烟已确认字段正确落盘（`.tmp` 之外，配置 `configs/var2_smoke.yaml` 把
`eval_interval` 压到 1，让第 1 轮就触发验证）。

### 排法：一浪 24 个进程

按 `docs/并行与吞吐.md`：这台机器单进程吃不满，24 进程 × 2 线程是吞吐拐点
（0.172 轮/s，比最快的单进程配置快 9.6×）。所以实验从"一次一个"改成"一次一浪"。

**浪里的变体成本必须相当** —— 墙钟由最慢的那个决定。`epochs` /
`episodes_per_update` 成倍抬高 update 成本，所以单独一浪。

**第一浪**（epochs=1，12 个变体，30 轮，预计 ~85 分钟）：

| `mini128lr1e3` | 两者叠加 | 最直接"多走几步"的组合 |

## 第一浪结果：训练确实有效，而且学习率 bug 是真因

**判读口径**：三列配对差**正数一律表示更好**（对 base / 对 BC / 对专家）。
配对分辨率约 0.012，所以 `±0.005` 的栏不是噪声底 —— 12 个种子逐点相减之后，
凡是 `|t| >= 2` 的都是真的。

| **mini512** | minibatch 512 | **0.8226** | **+0.0546** | +10.3 | **+0.0397** |

| kl001 | target_kl 0.01 | 0.8119 | +0.0439 | +8.6 | +0.0290 |
| lr1e4 | actor_lr 0.0001 | 0.8085 | +0.0405 | +9.5 | +0.0257 |
| mini128lr1e3 | 叠加 | 0.8080 | +0.0400 | +7.8 | +0.0251 |
| mini128 | minibatch 128 | 0.8034 | +0.0355 | +5.9 | +0.0206 |

### 三个结论

**1. 训练确实有效 —— 12 个变体里 11 个显著超过 BC 起点。**
`base` 就是 +0.0439（t = +8.6），即"修好学习率、什么都不改"就能从 0.768 涨到 0.812。
**之前"训练不涨"的判断，根因就是那个学习率 bug**：它让配置里的 0.0003 从未生效，
实际一直跑在 0.001 上。

**2. 方向明确：学习率越小越好，遍历越大越好。**
`lr1e4`(+0.0405) > `base` 0.0003(+0.0439 打平) > `lr3e3`(+0.0191) > `lr1e3`(**−0.0104**)。
`lr1e3` 是唯一的**负数**。这条完全自洽：**全部历史实验都卡在 0.001 上，而 0.001
恰好是这个任务上唯一会掉的方向。** 难怪怎么调都不涨。
batch 侧同理：`mini512`(+0.0546) > `base` 256 > `mini128`(+0.0355)，大 batch 更好。

**3. `mini512` 和 `vcoef1` 是仅有的两个超过专家（0.7828）的配置**，
各 +0.039。其余变体都还没到专家线。所以第一浪拿到的最好结果是
"约等于专家、略好"（0.8226 vs 0.7828），离天花板还远，但**方向已经打开**。

### 但先别急着信：两次"同配置"差 0.06

第一轮的 `base`（0.8166，因为 bug 实际跑在 0.001）和第二轮的 `lr1e3`
（0.7576，显式 0.001）看着应该等价，却差 0.059 —— **比 `mini512` 相对 `base`
的优势（+0.011）还大**。逐轮比对：**第 1 轮逐位相同，第 2 轮开始分叉**。

两轮之间唯一不同的运行时条件：第一轮 6 进程 × 4 线程，第二轮 24 进程 × 2 线程。
`rl_algorithm.yaml` 自己就记着块对角前向的 BLAS 分块随图数变化会让采样有微小差别。

**这条必须先查清**：如果线程数真的会改变训练结果，那所有跨并行度的比较都不成立。
`.tmp/probe_thread_repro.sh` 在测（同配置 2×2 线程 vs 2×4 线程，各跑两次，
比较"同线程重复差"和"跨线程差"谁大）。**结论出来之前，上表的跨轮次比较都先存疑。**

## 线程数会改变训练结果（评测不会）

`.tmp/probe_thread_repro.sh`：同配置、同 checkpoint，只改 `OMP_NUM_THREADS`，
四种运行同时起。结果**非常干净**：

| 对比 | 末次验证差 | 说明 |
|---|---|---|
| 2 线程 两次独立运行之间 | **+0.0000（逐位相同）** | 固定线程数下训练完全确定 |
| 4 线程 两次独立运行之间 | **+0.0000（逐位相同）** | 同上 |
| 2 线程 − 4 线程 | **+0.0176 ± 0.0023，t = +7.68** | 两次重复给出**同一个数** |

所以线程数**确定性地**改变训练结果，不是随机噪声。0.0176 和这一轮里
`mini512` 相对 `base` 的优势（+0.0107）是同一个量级 —— **足以颠倒结论**。

**连带推翻了一条旧记录。** `probe_thread_repro.sh` 里我写的
"两轮之间唯一不同的运行时条件"是错的 —— 调度器把 4 线程那两次也排在了
24 进程背景下执行，而 2 线程那两次逐位复现了 *24 进程背景* 下的 `r2_base`
（30 轮全部逐位相同）。所以**"背景负载改变结果"不成立**，真正的变量只有
`OMP_NUM_THREADS` 本身。

### 但评测不受影响（这条保住了所有参照点）

`.tmp/probe_eval_threads.sh`：同一个 checkpoint、同一套验证协议，
2 线程跑两次 + 4 线程跑一次，再和先前那次对照 —— **四种组合逐位相同**
（0.767955）。所以：

* BC 起点（0.7680）和专家（0.7828）**可以**直接和 2 线程训练的变体比；
* 线程敏感性只存在于**训练**里，不在评测里。

### 连带的编码问题：`var2_base.yaml` 当时不存在

查版本历史发现：`var2_base.yaml`（以及全部 `var2_*.yaml`）是 `screen_r2.sh` 在
首次运行时才生成的，而第一轮的 `screen_ppo_variants.sh` 用的是另一套文件名
（`var_base.yaml` 等）。也就是说**第一轮的 `base` 根本没加载 var2_base.yaml**，
它用的是 `rl_algorithm.yaml` 的默认值 —— 这解释了它为什么与配了
`var2_base.yaml` 的第二轮结果不同。**修复前后**（`806bc80` 之后才有
`_configured_lrs`）两批结果的差异，一部分来自这个，一部分来自线程数。

### 结论：判据必须钉死在固定线程数上

**所有跨轮次、跨并行度的绝对数值比较都作废。** 往后：

1. **固定 2 线程**（它是逐位可复现的那一档），筛选脚本已按此设成
   `THREADS=2`；
2. 第一轮（6×4 线程）与第二浪（24×2 线程）之间**不能直接比**；
3. 需要重做的事：把第一轮验证过的关键变体在 2 线程下补跑，才能和本轮并列。

这不是"又出问题了"，而是把之前那条"训练完全确定性、给定代码+种子逐位可复现"
的**假设**证伪了 —— 它只在固定线程数下成立。记在
`docs/测试规范.md` §6 里，比记在诊断记录里更该常驻。

### 两浪合起来读出的规律

**1. 学习率：越小越好，0.001 是唯一会掉的方向。**
`lr1e4`(0.0001) ≈ `base`(0.0003) > `lr3e3`(0.003) > `lr1e3`(0.001)**负**。
0.001 是最差的 —— 而**全部历史训练都跑在 0.001 上**。这条单独就解释了为什么
之前怎么调都不涨。0.0001 和 0.0003 差别不大（+0.0405 vs +0.0439），
说明这附近已经进了平台，不必再往下压。

**2. batch 越大越好。** `mini512`(+0.0546) > `base` 256(+0.0439) > `mini128`(+0.0355)，
单调。每轮梯度步数从 45 降到 22，方差换来的收益比步数损失大。

**3. `epochs > 1` 一律有害。** `ep2`(+0.0380)、`ep4`(+0.0282)、`ep4mini128`(+0.0135)
全都低于 `base`，而且 **epochs 越多越差**。第一轮里 `ep4` 看着最好（0.7860）
是假象 —— 那一轮跑在 4 线程 + bug 未修的 0.001 上。这条规律和"小学习率更好"
是一致的：epoch 和学习率都在放大每轮更新的幅度，而这个任务**受不了大步长**。

**4. 两个真正有效的方向：`mini512` 和大 `value_coef`。**
两者都指向同一件事 —— **降低 actor 更新的方差**。`vcoef1` 把 critic 训得更准，
优势估计更干净；`mini512` 直接减小梯度方差。它们的效果几乎相同
（+0.0546 / +0.0542），很可能不是两个独立机制。

**5. 只有这两个变体越过专家线**（0.7828），各 +0.039。其余都还在专家之下。
所以现在的水平是"稳定超过启发式约 4 个点"，但离真正的好策略还有距离。

**6. 天花板在哪还不知道。** 0.8226 是不是这个场景的上限，没有测过 ——
需要构造一个上界（例如允许无限等待的理想调度）才知道还剩多少空间。

## 探针 E：失败分解 —— 22 个点缺口里，5.3 点是"物理拿不到"

**问题**：0.78（专家）/ 0.82（RL 最好）到 1.0 的缺口，拆成三块各占多少 ——

- **A 无路径**：源-目的在拓扑上就不连通，任何策略都服务不了；
- **B 容量**：路径在，但速率 × 窗口搬不完这么多量；
- **C 调度**：搬得完，但没在对的时刻把对的链路接上。

**只有 C 是策略能改进的**，所以这个分解决定"还剩多少空间"，也决定该不该继续调 RL。

**脚本**：`.tmp/probe_failure_decomp.py`（驱动 `.tmp/run_fd.sh`，专家 + BC 各跑一遍）
**方法**：环境一行不改，monkey-patch `RequestQueue.expire` / `.serve` 记账。每条过期请求
记录需求量、剩余量、完成度、以及路径是否可达。

（`routing.py:31-60` 预计算 all-pairs，与 key 库存无关），所以 `hops == 10**6`
就是"拓扑上不连通"，不是"这一刻没空"，A 这一项判得住。

**协议**：诊断场景（第 0 天、fixed、240 步、种子 7–18，同 `configs/var2_diag.yaml`）。

## 探针 G：失败的容量下界 —— **14% 的到达量在生命期内"没人能给它生成 key"**

**问题**：给 B 判一个**可证的下界**：不看链路忙不忙，只看物理速率。一条请求即使
把整条路径独占，它的剩余量也搬不完吗？

**脚本**：`.tmp/probe_capacity_bound.py`（驱动 `.tmp/run_cap.sh`）。
**方法**：对每条过期请求算

```
cap_opt = max over 路径   min over 该路径的每一跳   Σ_{t ∈ [到达, deadline)} rate(hop, t)
```

`cap_opt` 忽略竞争，所以是**上界**：`cap_opt < 剩余量` → 连独占都不够（记 B）；
`cap_opt ≥ 剩余量` → 物理搬得动（记 C）。

**第一版口径错在哪**：只算**静态最短路**，量出"100% 失败请求容量不足、`cap_opt` 中位 0.000"。
用 `.tmp/dbg_rate.py` 定位到原因：静态最短路恰好经过不可用的 LEO 卫星链路
（`E_Tokyo__Sat_LEO_1a` 的 `get_rate` 在 t=0,1,5,29 是 `67.4, 33.9, 7.56, 0`，
`is_available` 是 `True, True, True, False`）。改成**全路径的最宽路径（max-min）**后仍量出
大面积 `cap_opt = 0` —— 那**不是 bug**，而是下面探针 H 要量的东西：生命期内路径根本没全通过。

**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18）。

**结果**：

| | 专家 | BC 权重 |
|---|---|---|
| 量加权成功率 | 0.7801 | 0.7871 |
| 服务 keys | 130,615,573 | 131,780,557 |
| A 拓扑不可达 | 99 条 / 8,914,455 / **5.32%** | 99 条 / 8,914,455 / **5.32%** |
| B 容量不足（下界） | 244 条 / 23,260,340 / **13.89%** | 220 条 / 21,730,208 / **12.98%** |
| C 物理搬得动却没搬 | 1 条 / 2,201 / 0.00% | 2 条 / 7,550 / 0.00% |
| 过期总量 | 344 条 / 32,176,996 / 19.22% | 321 条 / 30,652,212 / 18.31% |

B 档 `cap_opt/剩余` 的**中位 = 0.000**（即过半 B 请求的路径上，每一跳在整个生命期里
生成量之和都是 0）。按静态最短路跳数分层（专家）：hops=2 → 149 条里 148 条（99%）容量不足，
剩 13,010,280；hops=3 → 96 条里 96 条（100%），剩 10,250,060。（BC 同向：126/127、94/95。）

**结论**：B 不是"差一点"，是 **0**。而 C 只有 1–2 条 —— 说明"路径存在"这个判据本身
太弱：真正卡住的是"路径在它活着的时候有没有全部通"。这正是探针 H。

## 探针 H：生命期内的"一路全通" —— **8.3–8.8 点结构上不可能，5.1–5.5 点才是策略的**

**问题**：把探针 E 的 A 之外那 16.7 点，按"源-目的在请求存活期内**是否曾经**存在一条
全通路径"再切一刀。

**脚本**：`.tmp/probe_joint_avail.py`（驱动 `.tmp/run_joint.sh`）。
**方法**：不改环境、不枚举路径。对每个槽 `t`，在"**当时可用**的边"构成的子图上算一次
连通分量；于是"src 与 dst 在 t 时刻存在一条全通路径"等价于**两个分量号相等**——
精确、不限制路径长度、一次 O(horizon·(V+E)) 就够。每个过期请求记
`avail_slots = #{t ∈ [到达, deadline) : src 与 dst 同分量}`。

分类（优先级从上到下）：`A` 静态拓扑不连通 → `B_avail` `avail_slots == 0` →
`C` `avail_slots > 0` 却没搬完。

**自检**：脚本第二个种子重算一遍分量表并比对，输出
`自检：可用性子图跨种子一致 = True` —— 可用性是"第 0 天"的确定性函数，与请求种子无关，
所以这个判读是干净的。

**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18）。

**结果**：

   把"拓扑通、时间不通"全塞进了"可达"，H 把这一档单独量了出来。

2. **完成度随全通槽数单调上升**（0.016–0.033 → 0.23–0.42 → 0.51–0.59），
   这是"决定成败的主要变量是路径有没有全通过，而不是策略选得好不好"的直接证据。

3. **策略真正还能拿的只有 C 那 5.1–5.5% 的量**，而它们的完成度已经到 0.33–0.41 ——
   就算把 C 全部做完，也只多 **(1 − 0.4) × 5.2% ≈ 3 个点**。最好模型 0.8283（逐种子均值）
   距 0.864（量加权口径）约 3.6 点，**和 C 的可回收量同量级**。
   也就是说：**继续调 RL 的天花板大约就是 3–4 个点**，不会有更大惊喜。

4. 想超过这个天花板，动的是**场景**不是策略：B_avail 的成因是"LEO/HAP 分时可见性
   的起伏比 30 槽的 deadline 更快"。把 `deadline_steps` 拉长（让请求能等到窗口）
   是直接杠杆 —— 但那要重做基线，属于换题不是调参。

**记账坑**：这两个探针里 `--policy rl` 用的是 **BC 权重**
（`outputs/supervised_pg_phased/supervised_pg_phased_latest.pt`），**不是**训练出来的 RL。
所以上面"BC 权重"那一列该读成 BC，不是 RL。训练后的策略要另跑一遍。

## 探针 I：可用性的时间结构 —— **排除"数据截断"，B_avail 是场景设定**

（LEO 过境窗口本来就错开），还是数据/口径问题（比如卫星链路只在开头几槽有速率、
之后整段是 0）？这两者的处理完全不同：前者是换题，后者是修数据。

**脚本**：`.tmp/probe_avail_trace.py`。
**方法**：只读 `rate_provider`，不跑策略。逐链路类型统计 240 槽里的可用边数、
按槽统计"连通 GS 对比例"。

**结果**：

|---|---|---|---|
| hap_sat | 900 | 0.068 | 16 |
| gs_sat | 840 | 0.014 | 11 |
| sat_sat | 175 | 0.512 | 240 |
| gs_hap | 63 | 0.440 | 240 |

数据集：`_T = 525600`、`slot_seconds = 60`（= 一整年），`min_link_rate = 1.0`，

> 同时最多 28/63 条边在线。F 看到的"占用率 1.000"是"被接上"，不是"可用"。

## 口径修正：探针 H 里 `--policy rl` 一直是**采样**跑出来的

**问题**：拿训练出来的 `outputs/r3_m512ent/checkpoint_final.pt` 重跑探针 H，
量出 **0.7830**，而同一个 checkpoint 在训练日志里的 `eval_validation` 末次是 **0.8283**。
同权重、同场景、同 12 个种子，差 **4.5 个点** —— 必须查清是探针错了还是训练日志错了。

**根因**：`MAPPOTrainer.evaluate_validation` 走的是
`act_batched(..., deterministic=True)`（`mappo_trainer.py:1034`），
而探针 H 调的是 `policy.act(obs)` —— 它的签名是
`act(self, obs, deterministic: bool = False, ...)`（`policy.py:211`），**默认采样**。
两者量的是两个不同策略：一个是策略的众数动作，一个是从策略里抽出来的样本。

所以之前探针 H 里 RL / BC 两列都是采样值，**和训练侧、和 `bc_diag_perseed.json`
都不在同一口径**。修法：给探针加 `--deterministic`，并把输出 json 里记录
`deterministic` 字段，避免以后再混。

**脚本**：`.tmp/probe_joint_avail.py`（新增 `--deterministic`）、
驱动 `.tmp/run_joint_det.sh`。
**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18）。**线程数 2（钉死）**。

**结果**（同一份 checkpoint，只改动作是否采样）：

| 动作 | 量加权成功率（pooled） | 训练侧 `eval_validation` | 差 |
|---|---|---|---|
| r3_m512ent，**采样** | 0.7830 | — | — |
| r3_m512ent，**确定性** | **0.8247** | **0.8283** | 0.4 点（pooled vs 均值） |

**结论**：那 4.5 个点全部是"采样 vs 确定性"，不是 bug。
采样落到 0.7830 是因为训练到后期熵已经升到 ≈ 3.9–4.0，
从分布里抽样会稳定地拿到比众数动作差的一档。**以后所有跨来源比较必须钉住确定性**。

## 探针 H（确定性重跑）：三策略同口径对照 —— 并推翻"B_avail 与策略无关"

**问题**：把专家 / BC 起点 / 训练后 RL 三个策略放到**同一个口径**（确定性）
下各跑一遍探针 H，看那三档损失（A / B_avail / C）分别被策略动了多少。
顺带检验旧结论"B_avail 和策略完全无关，是场景固有的"。

**脚本**：`.tmp/probe_joint_avail.py --deterministic`（BC 与 RL 各一遍，
专家本身恒确定性）；结果 `outputs/eval/joint_avail_{expert,rl_bc_det,rl_r3ent_det}.json`。
**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18），线程数 2（钉死）。
**判据**：`success_rate = served_keys / arrived_keys`，与训练侧同定义；三者的
pooled 值与各自的训练/评估侧读数分别对得上（见下表倒数第二列）。

**结果**：

| 策略 | pooled 量加权成功率 | 对照（训练/评估侧） | A 拓扑不可达 | B_avail 从未全通 | C 曾全通没搬完 | C 平均完成度 |
|---|---|---|---|---|---|---|
| 专家 PG-Phased | 0.7801 | 0.7828 | 8,914,455 / **5.32%** | 14,791,656 / 8.83% | 8,470,884 / 5.06% | 0.405 |
| BC 起点 | 0.7648 | 0.7680 | 同左（99 条） | 13,883,376 / 8.29% | 12,080,579 / 7.22% | 0.232 |
| **r3_m512ent（训练后）** | **0.8247** | **0.8283** | 同左（99 条） | 11,435,364 / **6.83%** | 5,441,002 / **3.25%** | **0.531** |

过期请求条数：专家 344 / BC 364 / RL 276；过期总量占到达量 19.22% / 20.83% / **15.40%**。
分母都是到达量 167,431,720（三策略一致，到达流与策略无关）。

**结论**：

1. **A 档（拓扑不可达）是完全钉死的**：三策略都是 99 条、8,914,455、**5.32%**、
   平均完成度 0.000。这一档无论怎么训练都不会动，是"孤立节点"（如 Stockholm、
   以及 `hop_distance = 10**6` 的那些对）的固有损失。
2. **推翻旧说法：B_avail 不是"与策略无关"**。它从 BC 的 8.29% 掉到 RL 的 **6.83%**，
   完成度 0.026 → 0.037。原因是那条旧的判据本身不严谨：
   `avail_slots` 量的是"**逐槽快照**里 src 与 dst 同分量"，而真实的可服务性
   还包含 **key 库存的跨槽效应** —— 一条边上一槽生成的 key 可以留到后面几槽继续搬运，
   所以"从未同时全通"并不意味着"一点都搬不动"。事实也正是如此：
   B_avail 档平均完成度恒为非零（0.026–0.037）。
   所以正确的读法是：**B_avail 是"逐槽快照不可达"，是真实不可服务量的一个上界**；
   其中能被库存救回来的那一小块（约 1.5 个点）是策略动的。
3. **C 档是策略的主战场，训练把它砍掉了六成**：7.22% → **3.25%**，
   平均完成度 0.232 → **0.531**。同时 BC 起点（7.22%）比专家（5.06%）**更差** ——
   行为克隆学到的分派比启发式规则差，训练才把它拉回来并反超。
4. **策略可争的剩余空间只有 3–4 个点**：RL 的总过期量 15.40% = A **5.32%（钉死）**
   + B_avail 6.83% + C 3.25%。A 动不了，C 是策略的主战场（已经回收掉 BC 那 7.22% 里的
   大半），B_avail 里只有靠库存能救的一小块能动。
   **所以把 C 全部清零也只有 +3.25 点（0.8247 → 约 0.857）**，
   剩下的 6.83% B_avail 基本要换 deadline 才碰得到（见探针 J）。
   这个"3–4 个点"的天花板与第三浪"最好模型 0.8283 离 0.859–0.864"是同一量级、互相印证。

**记账坑**：
* `pooled 量加权成功率` 与"12 个种子成功率的算术平均"不是同一个数（本例差 0.003–0.004）。
  与训练日志的 `mean_success_rate` 比时用算术平均，用 pooled 只能当近似。
* 探针输出的 json 现在带 `deterministic` 与 `checkpoint` 两个字段；
  看到没有这两个字段的旧 json（`joint_avail_rl.json`、`joint_avail_expert.json`）
  要知道它们分别是"采样"和"确定性"。

## 探针 K：C 桶解剖 —— 不集中在少数"对"上，但集中在少数"节点"上

**问题**：这 3.25%（RL）的 C 档是"唯一受策略控制"的损失。它是**均匀摊在所有需求上**
（那只能靠更长训练慢慢磨），还是**卡在少数几对 GS 上**（那就能做针对性机制）？
另外，训练到底把 C 档"改成了什么形状"——是抓住了窗口却搬不完，还是干脆错过窗口？

**脚本**：`.tmp/analyze_cbuck.py`（纯后处理，读 `outputs/eval/joint_avail_*.json`，
不重跑环境）。
**方法**：按 (src, dst) 归并剩余量算集中度（HHI + 前 10 对占比）；按节点归并；
按静态最短路跳数分层；按"生命期内全通槽数"分层；按完成度分箱对照。
**协议**：同探针 H（诊断场景，12 种子）。

**结果**：

| 指标 | 专家 | BC 起点 | r3_m512ent |
|---|---|---|---|
| C 档涉及 GS 对数 | 59 | 62 | 41 |
| 前 10 对占 C 档剩余量 | 39.4% | 36.9% | **50.5%** |
| HHI（均匀分布基线） | 0.0272（0.0169） | 0.0256（0.0161） | 0.0371（0.0244） |
| 跳数 2 占 C 档 / 完成度 | 56.2% / 0.484 | 60.4% / 0.274 | **59.6% / 0.626** |
| 跳数 3 占 C 档 / 完成度 | —  / — | 39.6% / 0.162 | **40.4% / 0.311** |
| 完成度 <0.01（完全没搬）占 C 档 | — | **44.9%** | **5.4%** |
| 完成度 0.25–0.50 占 C 档 | — | 17.6% | **54.4%** |

按**节点**归并（占 2×C 档剩余量；均匀基线 29 个 GS ≈ 3.7–4.0%）：

| 节点 | 专家 | BC | r3_m512ent |
|---|---|---|---|
| **McMurdo** | **21.9%** | **19.8%** | **20.2%** |
| MexicoCity | 11.8% | 18.4% | 10.0% |
| Santiago | — | 7.8% | — |
| Almaty | 4.7% | — | 7.0% |

**结论**：

1. **对级不集中**：HHI 0.037 只比均匀基线（0.024）高 50%，前 10 对也才占一半；
   涉及 41 对 GS。**所以没有"几条难线一刀切掉就行"的捷径**，这是整体性问题。
2. **但形状被训练改变了，而且改得很有指向性**：BC 的 C 档里 **44.9% 的量落在
   "一点都没搬"**（完成度 <0.01），训练后只剩 **5.4%**，同时 54.4% 的量挪到了
   "搬了一半"（0.25–0.50）。也就是说：
   **BC 的问题是不会利用窗口；训练后的问题变成了窗口利用上了但搬不完。**
   这是两种完全不同的短板 —— 后者是**容量/带宽**问题，不是选择质量问题。
   → 剩下的 3 个点想再往下压，靠"选得更好"没有多少空间，得靠**在窗口到来之前
   就把 key 预置到瓶颈边附近**（即更长的规划视野 / 库存前置），
   而不是靠更准的即时选择。
3. **节点级有明显偏斜，而且三个策略一致**：McMurdo 恒定吃掉 **~20%** 的 C 档损失
   （均匀基线 4.0%），专家 21.9% / BC 19.8% / RL 20.2% —— 三份不同策略给出同一个数，
   说明这是**结构性**的（南极站的地理位置决定了它的中继窗口又短又稀），
   不是某个策略的偏好。
   McMurdo 相关的 C 档对包括 `McMurdo->Tokyo`、`Auckland->McMurdo`、
   `Almaty->McMurdo`、`Bogota->McMurdo`、`Beijing->McMurdo`、`Chicago->McMurdo`、
   `Dubai->McMurdo`、`McMurdo->Vancouver`、`McMurdo->Nairobi` 等。
4. **跳数分层显示 C 档几乎全是 2 跳和 3 跳**（没有更长路径）：符合"短路径 + 中间一个中继"
   的形态，进一步支持"瓶颈在那一跳的容量，而不是路径太长"。
5. **长期影响**：由于对级不集中而节点级偏斜，如果想在论文里给出一个"改进方向"，
   最可辩护的一条是**把 McMurdo 这类极端节点的需求在时间上提前铺开**（或者承认它是
   场景硬约束），而不是宣称"改进了路由算法"。

## 探针 J：deadline 敏感性 —— "要不要换题"变成一个数字

**问题**：探针 H 判出 B_avail 那一档的成因是"LEO/HAP 分时可见性的起伏比 30 槽的
deadline 更快"。把 `deadline_steps` 拉长是直接杠杆，但要重做全部基线（换题）。
所以先离线算清：**拉到 60 / 120 / 240 槽，那一档能掉多少？**

**脚本**：`.tmp/probe_deadline_sens.py`。
**方法**：**不跑策略就能算**。这一档只取决于 (src, dst, 到达时刻, deadline) 四件事，
前三件由请求流决定、第四件是场景常数。所以只要 patch `queue.add_arrivals` 记下请求流，
再拿探针 H 那份"逐槽连通分量"表，就能对每个候选 D 直接算出
`avail_slots(D) == 0` 的量。**没有枚举路径**。
**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18）；rollout 用专家策略
（只为把 `expire` 和分量表跑活，读数本身与策略无关）。
**线程数 2（钉死）**。

**结果**（到达量 167,431,720，共 1,654 条请求，生命周期恒为 30 槽 / 100%）：

| deadline | 全样本「全通槽为 0」 | 占全体到达 | 平均可用槽 | 完窗口「全通槽为 0」 | 占全体到达 |
|---|---|---|---|---|---|
| **30（当前）** | 14.43% | **13.59%** | 14.87 | 15.06% | 12.55% |
| 60 | 8.17% | **7.69%** | 28.71 | 8.22% | 5.99% |
| 120 | 6.05% | **5.70%** | 51.34 | 6.36% | 3.00% |
| 240 | 3.19% | **3.00%** | 73.33 | ——（无样本） | —— |

另：端点不在拓扑里的量 9,825,004（**5.87%**，已从上面各行剔除，它对应探针 H 的 A 档）。
「完窗口」列 = 只有 D 窗口完整落在 240 步内的请求（D=240 时 a+240 ≤ 240 几乎无样本，
所以那格是空的，不是 0）。

**同一进程里的对撞自检**（这是本次加的，之前缺）：
把探针 H 的口径搬进 J 的同一个进程重跑，用同一个专家策略 ——

```
J 里的 H 口径 ：过期 344 条 / 19.22%   A 99 条/5.32%   B_avail 159 条/8.83%   C 86 条/5.06%
探针 H 的读数  ：过期 344 条 / 19.22%   A 99 条/5.32%   B_avail 159 条/8.83%   C 86 条/5.06%
```

**逐位相同**，所以两个口径是同一条线，可以互相比。

**结论**：

1. **拉长 deadline 确实能砍掉这一档，且见效很快**：30 → 60 槽就把"快照从未全通"
   从 13.59% 砍到 **7.69%（−5.9 点）**；到 120 槽再砍到 5.70%。
   这正是"换题"能拿到的量级 —— 一次改动就超过全部 PPO 超参搜索（第三浪最大单变量
   增益才 +1.5 点）的总和。
2. **但这是"快照口径"，它高估了损失。** 对撞给出了关键的一步：
   快照口径说"不可服务"共 13.59% + 5.87% = **19.46%**，
   而 H 口径实测 A + B_avail 只有 5.32% + 8.83% = **14.15%**。
   差的约 **5.3 个点是被 key 库存跨槽救回来的**（快照里不可达，实际靠已经攒在边上的
   key 搬完了，所以根本没过期）。所以"换 deadline 能拿回 5.9 点"要**打折**，
   真实可拿的比这小。
3. **副产物（新信息）：窗口越长，"可用比例"反而越低。**
   平均可用槽数 ÷ deadline：D=30 → 14.87/30 = **49.6%**；
   D=60 → 47.9%；D=120 → **42.8%**；D=240 → **30.6%**。
   这说明连通性有**长周期的低谷**，窗口拉得越长越会撞上低谷 ——
   所以"拉长 deadline"不是线性收益，边际效应递减。

**记账坑**：
* 离线表的分子是请求的**原始量**，探针 H 的分子是**剩余量**（amount − served），
  两者差一个 `served_frac`。做数量级比较没问题，做小数点后两位的比较不行。
* 左表的"占全体到达"分母恒为 167,431,720（全部到达），右表同理；
  但"全样本列的分母"是本 D 下的需求量（同一个数）。别把这几列串了。

## 探针 M：负载敏感性 —— 损失里只有 **5 个点**是拥塞，其余是外生

**问题**：探针 K 显示 C 档的形状已经从"完全错过窗口"变成"抓住窗口但搬不完"，
于是有两种完全不同的解释：**拥塞**（需求自己抢瓶颈边）还是**物理可用性**。
前者能靠更好的分配/预置库存去挣，后者只能换场景。

**脚本**：`.tmp/probe_load_sens.py`。
**方法**：**单变量** —— 只缩放 `requests.arrival_rate`（0.8 → 0.4 / 0.2 / 0.08），
其它一切不动（同一 checkpoint、同一场景、同 12 种子、确定性动作）。
需求抽稀了，排队消失，但"哪条边在哪个窗口可用"完全不变。
判据：**C 档随负载塌下去 = 拥塞（内生）；三档都不动 = 可用性（外生）**。
**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18），checkpoint
`outputs/r3_m512ent/checkpoint_final.pt`，线程数 2（钉死）。

**结果**：

| 负载× | arrival_rate | 到达量 | 成功率 | A | B_avail | C | C 平均完成度 |
|---|---|---|---|---|---|---|---|
| **1.0** | 0.80 | 167,431,720 | **0.8247** | 5.32%（99 条） | 6.83%（124 条） | 3.25%（53 条） | 0.531 |
| 0.5 | 0.40 | 88,073,440 | 0.8509 | 4.51%（50） | 6.28%（55） | 1.71%（19） | 0.592 |
| 0.25 | 0.20 | 43,936,491 | 0.8695 | 3.97%（24） | 4.49%（25） | 2.75%（16） | 0.640 |
| **0.1** | 0.08 | 16,762,547 | **0.8780** | 5.14%（11） | 2.74%（9） | 2.41%（7） | **0.664** |

**结论**：

1. **需求抽稀 10 倍，成功率只从 0.8247 涨到 0.8780（+5.3 点），并没有涨到 0.95。**
   所以**拥塞（内生、策略可争）只值约 5 个点**；剩下的 12–17 个点全部是
   **外生的物理/拓扑约束**（A 的孤立节点 + B_avail 的可见性低谷）。
   → 这就是"策略天花板"的直接测量：**约 0.878**。
   它与探针 H 的 0.857（C 全清零）同量级、互相印证，且更宽（因为降载还顺带减少了 A/B）。
2. **A 档近似恒定（A 条数却随负载等比缩小：99→50→24→11，占比 4.0%–5.3%）**：
   与负载无关，漂移只是抽样差异。**再次确认 A 是钉死的**。
3. **C 的平均完成度单调上升（0.531 → 0.592 → 0.640 → 0.664）**：
   负载越低，"窗口被利用的比例"越高。**这直接证明 C 档是拥塞造成的** ——
   窗口本身没问题，是同一时间别的请求把瓶颈边的 key 抢走了。
4. **C 的量占比不单调**（3.25 → 1.71 → 2.75 → 2.41）：到 ×0.25、×0.1 时样本只剩
   16 条 / 7 条，噪声主导，**这一列不能读趋势**，能读的是完成度那一列。
5. **B_avail 也随负载下降（6.83% → 2.74%）**：与探针 H"B_avail 不是与策略无关"
   同源 —— 负载低时排队短、库存不被抢，"快照不可达"的请求有更多机会靠库存被救回来。

**方向结论**：把策略从当前的确定性 0.8283 继续往上推，**可争的空间只有约 5 个点，
而且都是"拥塞下的分配"这一件事**（谁先拿瓶颈边的 key / 能不能在窗口到来前把 key 预置好）。
想再往上（0.878 → 0.95 那一段）**必须改场景**（拉长 deadline、或者接受 A 档的孤立节点）。
这条判断同时解释了为什么第三浪里所有 PPO 超参都只能在 ±1.5 点内动 —— 本来就没有多少
可争的量在那儿。

## 探针 N：C 桶的请求，在"窗口到来的那一刻"手上有多少货？

**问题**：探针 K 说 C 桶的形状是"抓住窗口但搬不完"，探针 M 说可争的 5 个点全在
"拥塞下的分配"。但这两种说法都留了一个没验证的岔路：

* **没预置** —— 策略从不提前把 key 铺到"过一会儿要用的边"上，窗口开了才开始攒；
* **攒不出来** —— 就算想预置，30 槽的窗口里那条路径根本攒不出够用的量。

前者是策略能挣的（更长的规划视野 / 库存前置），后者只能改场景。**这个探针就是来分岔的。**

**脚本**：`.tmp/probe_preposition.py`（三策略跑法见 `.tmp/run_preposition.sh`）。
**方法**：对每个到达请求记三个时点的库存画像。服务的语义是"沿一条**每跳库存都为正**的
路径，每槽搬 `min(各跳库存, 剩余量)`"，所以"这一槽最多能搬多少"就等于
**正库存子图上 src→dst 路径各跳库存的最小值**（瓶颈）：

| 记号 | 含义 |
|---|---|
| `bn@到达` | 到达当步末，正库存路径的瓶颈（`None` = 连一条正库存路径都没有） |
| `bn@首连` | 源-目**第一次物理全通**那一槽的瓶颈 |
| `bn_max` / `bn_sum` | 生命期内所有全通槽上瓶颈的最大值 / 之和 |

`bn_sum` 是"**如果这个请求独占它的窗口**，最多能搬走多少"的上界。判据：
`bn_sum < 剩余量` = 机会不够；`bn_sum ≥ 剩余量` 却没搬完 = 机会够、是分配/竞争的问题。

**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18），**确定性**动作，线程数 2（钉死）。

* 策略可争的 5 个点里，**"选得更好"最多能挣约 1 个点**（表 2 那 9 条）；
* 剩下约 7 个点落在"窗口内机会不够"这一侧，而它有两种根源 —— **没预置** 还是 **攒不出来**，

* 分开它们需要第二个量：`gen_ub = Σ_{窗口内物理相通的槽} min_{该槽可用最短路各跳} rate(e,t)`，

1. **`gen_ub` 第一版口径写错了，恒为 0**：原来用 `routing.shortest_path`（**静态拓扑**最短路）

   改成"**该槽可用边子图里的最短路**"才有意义。教训：这套 LEO 可见性是"打洞"的，
   任何**路径级**的量都必须建立在**当槽可用子图**上，静态最短路在这里是废的。
2. **表 1 各组之和只有 97.04%**：缺的 2.96% 是 episode 结束时**还没到期、也没完成**的尾部请求

3. **请求会被 `dataclasses.replace` 换成新对象**（部分服务时），但 `request_id` 不变，
   所以度量必须**按 id 挂**，不能按对象身份挂。
4. **`bn_sum` 不是物理上界**：它是在**实际库存轨迹**上积出来的，策略换了铺货方式，轨迹就会变。
   所以表 2 只能读成"在当前轨迹下机会不够"，不能读成"物理上不可能"。

## 探针 N（修正版）：把物理上界修对之后，策略还能挣多少？

**问题**：上一节的表 5/6 没跑出来。补跑时发现上一版 `gen_ub` 有**两个独立的口径错误，
而且方向都是把物理上界压小** —— 这一格恰恰是用来回答"训练侧还有多少可挣"的，
压小就会把结论判成"没得挣"。所以先修口径，再读结果。

**脚本**：`.tmp/probe_preposition.py`（本机直接跑 —— 专家档不需要 checkpoint）。
**方法**：三处修正。

1. **漏乘 `slot_seconds`**：`rate_provider.get_rate` 给的是 **key/秒**，而 `env._generate_keys`
   里是 `rate * scenario.slot_seconds`（= 60），`receding_horizon_milp.py` 的上界项也是这个
   口径。漏乘 60 → 上界小两个数量级。
2. **逐槽路径选错**：上一版取"**最少跳**"的可用路径。要的是**上界**，就该取瓶颈最宽的路径
   —— 即 **max-min（最宽路径）** 的瓶颈速率（Dijkstra 的 max-min 变体）。最少跳路径**不是**上界。
3. **比较对象改回"到达量"**：物理上界不该随"已经搬了多少"变化（按剩余量截断会让它随轨迹变化）。
   新增不截断的 `gen_raw`；旧的 `gen_ub` 只留作参考。

核对前提：`get_rate(eid,t)` 与 env 实际用的 `edge_windows[eid].rates[0]` 同源
（都是 `_clean_rate(_read_scalar(rate_key, t, link))`），可用性判据也是同一个 `is_available`。

**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18），确定性动作，线程数 2（钉死），**本机**
（16 逻辑核 / CPU torch）。内部对照：专家量加权成功率 **0.7801**、到达 **167,431,720**、
记录请求 **1719** —— 与节点上那一遍**逐位相同**。

**结果**（专家 PG-Phased；C 桶 = 生命期内曾全通却没搬完的 86 条 / 占到达量 8.90%）：

【表 5】`gen_raw`（窗口内纯物理可攒量，与策略/库存无关）vs 请求到达量

| `gen_raw` vs 到达量 | 请求数 | 占到达量 | 平均 `gen_raw` | 平均到达量 | 平均物理全通槽 |
|---|---|---|---|---|---|
| **物理够** | 35 | **3.00%** | 380,348 | 143,370 | 13.7 |
| 物理不够 | 51 | 5.91% | 67,090 | 193,896 | 6.0 |

|---|---|---|---|
| 库存够 + 物理够 | 7 | 0.95% | 0.699 |

**结论**：

1. **口径一修，"还能挣多少"从约 1 个点抬到约 3 个点**：上一节表 2 的旧口径说
   "机会够却没抓住"只有 9 条 / 1.08%；修正后策略能挣的是 **28 条 / 2.05%**
   （库存不够但物理够 = 有货可攒却没攒），再加 **7 条 / 0.95%**（库存够且物理够，
   完成度却只有 0.699 的那批）。
2. **但一大半 C 桶是钉死的**：51/86（**5.91% 到达量**）即使把窗口内路径每一跳**全程钉住**，
   可攒量也只有 67,090，而它们平均要 193,896，物理全通槽仅 6.0 个 —— 改策略没用。
3. **"物理够"的那批，时间上完全来得及**：35 条平均 **13.7** 个全通槽、可攒 **380,348**，
   平均只需 143,370 → 约 **5 个槽的持续激活**就能攒够，而它们有 13.7 槽可用。
   所以瓶颈**不是"攒不出来"，而是"根本没开始攒"**。
4. **方向因此收敛到一件事：为在途请求提前预置库存** —— 在请求到达那一刻就把它路径各跳
   **钉住持续激活**，而不是等库存自己长出来。这正是本节开头那个岔路的答案：落在**没预置**一侧。
5. **"预置"在本环境里是策略动作，不是物理自动发生的**：`env._generate_keys(resolved.activated_edges, ...)`
   只给**被激活的边**生成 key（且刚切过去的当槽速率减半）。**库存是策略"开出来"的**，
   这解释了为什么专家那种"来一个服务一个"的即时反应式策略会大面积 `bn@到达=0`。
6. **这条方向的代价还没量**：90 个节点每槽最多约 45 条边（双端口匹配），而一条路径要占掉
   等于其跳数的边。所以下一个该量的是「**在途请求的路径边数需求 vs 每槽可用边数**」——
   若两者同量级，预置就是个真正的调度取舍问题（不是"想预置就能预置"）。
7. 相对量级提醒：A + B_avail 合计 **14.75%** 的到达量是**物理不可达**（拓扑/可见性），
   C 桶里又有 5.91% 是**物理攒不够**。所以可争空间的总盘子仍不大 —— 上面这 3 个点
   已经是"改策略"这一侧能找到的最大一块。

**记账坑**：

1. **两个口径错的方向都是"把上界压小"**（漏乘 `slot_seconds`、逐槽取最少跳路径）。
   教训：凡是拿"上界"下结论的探针，**必须先自证这个量真的是上界** —— 构造一个显然能满足的
   极端解（例如"每一跳全程激活"），看它是否被判成"物理够"。一个不是上界的"上界"会把方向整个判反。
2. **物理量必须与"到达量"比，不能与"剩余量"比**：按剩余量截断会让同一个物理量随策略轨迹变化
   （搬得快 → 剩余量小 → 上界显得小），那就不再是物理量。不截断的 `gen_raw` 才是。
3. **探针可以在本机跑，且与节点同口径**：专家档在本机复现出节点上那一遍的
   0.7801 / 167,431,720 / 1719，**逐位相同**。以后专家与 BC 档的探针不必等节点
   （只有 RL 档才需要节点上的 checkpoint）。
4. **`widest_rate` 是 Dijkstra 的 max-min 变体**，比 BFS 重：12 种子 × 240 步本机 2 线程跑了约 10 分钟。
   按 `(src, dst, t)` 缓存后仍在可接受范围，但再加逐槽全对最宽路径会很慢 —— 后续探针要注意量级。

## 探针 N 的 BC 对照 + 探针 O：预置到底做不做得起、有没有在做？

**问题**：上一节把"可挣的那一格"量成 2.05%，并读成"策略**从不预置**"。但那个读数只说明
"请求到达时手上没货"（`bn@到达=0`），**没有回答两件更要紧的事**：

1. **BC 起点差在哪**：同一套口径在 BC 上读一次，专家与 BC 的差距落在哪一格？
2. **预置做不做得起**：每槽能激活多少条边是受双端口匹配约束的（上界 = 节点数 89），
   一条路径要占掉等于其跳数的边。若预算根本不够，"预置"就不是一个可选方向。

**脚本**：`.tmp/probe_preposition.py`（BC 档）+ `.tmp/probe_activation_budget.py`（探针 O，新建）。
**协议**：诊断场景（第 0 天、fixed、240 步、12 种子 7–18），确定性动作，线程数 2（钉死），本机。

|---|---|---|
| 量加权成功率 | 0.7801 | **0.7342** |

**结论 B**：

1. **预置预算完全不紧**：在途需求的路径跳数合计平均只有 **7.5**，而预算 89，
   240 槽 × 12 种子**一次都没触到预算上限**。
2. **边确实被长时间钉住**：每槽 60.8 条激活里有 **54.6 条是从上一槽保持过来的（89.8%）**，

3. 所以上一节"**从不预置**"的读法**只对了一半**。准确的说法是：
   **货攒了、边也钉住了，但钉住的不是需求要的那些边。**
   这也解释了为什么 `bn@到达=0` 能和"长游程 + 空预算"同时成立 ——
   生成只发生在被激活的边上，而服务要求**某条路径的每一跳都为正**，
   两者错位时，攒再多也用不上。
4. **BC 起点也比专家"有货"却更差**：BC 的 served 组 `bn@到达` 均值 **141,434**（专家 124,402）、
   首连等待 0.9 槽（专家 1.3）—— 但成功率低 4.6 点。再一次说明
   **"到达时有货"不是决胜项，"没货的那批能不能攒出来"才是**。

**方向（下一步）**：把「**被激活的边**」与「**在途请求真正要走的路径**」求重合度。若重合度低，
真正的杠杆是**让激活/生成跟着当槽在途需求走** —— 注意现有奖励里的
`dense_generation_importance_weight = 0.02` 奖励的是 `relay_importance` 上的生成，
**若那个重要性与当槽在途需求无关，它就会把货引导到"结构性中心"的边上**（这正是探针 P 要量的）。

**记账坑**：

1. 探针 O 的"激活预算"取**节点数 89**（每节点 1 发 1 收，且 u→v 与 v→u 不能共存 → 上界是节点数）。
   实测最多用到 60.8，从未接近，所以这个上界取得粗一点不影响结论。
2. **`dem` 用的是"当槽可用边子图上的 BFS 最短路"跳数**，不是实际服务路径；
   作为"需求要占几条边"的量它是够的（实际路径只可能更长）。
3. **探针 O 的成功率与探针 N 逐位一致（0.7801）**，说明新脚本没有破坏环境状态 ——
   以后新增探针都应这样交叉核对一次。
4. BC 档的记录请求数 1723（专家 1719），到达量逐位相同（167,431,720）—— 同一批请求，不同轨迹。

## 探针 P：被激活的边，和"在途请求真正要走的路径"，重合多少？

**问题**：探针 O 留下的反常组合 —— 专家每槽激活 **60.8** 条边、其中 **54.6** 条从上一槽保持
（保持率 89.8%）、游程平均 **9.92** 槽，而在途需求的路径跳数合计只有 **7.5**、预算（89）
**一次都没用满**。既然边钉得又多又久、预算又空着，为什么 C 桶还是 86.66% "出生即空"？
只剩一个解释待验证：**钉住的边不是需求要的那些边**。

**脚本**：`.tmp/probe_demand_alignment.py`（探针 P，新建）。
**方法**：逐槽把「当槽在途每个请求在可用边子图上的 BFS 最短路的边集合之并」（`needs`）
与「`env.last_activated_edges`」（`act`）求交，记 |needs|、|needs∩act|、覆盖率，以及
逐请求的（该走几跳 H、其中几跳被激活 cov、其中几跳有正库存 pos）。
注意 `needs` 只是代理：实际服务路径未必是最短路，且**激活影响的是生成（攒货），不是服务本身**
—— 服务只要求路径各跳库存为正（`partial_consume_for_request`），不需要边当槽被激活；
但库存只在被激活的边上产生，所以"路径上的边有没有被激活过"决定了货能不能攒出来。

**协议**：诊断场景（240 步、12 种子 7–18），确定性动作，线程数 2（钉死），本机。
内部对照：专家量加权成功率 **0.7801**、2880 槽、3551 个（请求,槽）样本 —— 与探针 N/O 一致。

**结果 A：探针 P（专家）**

【表 1】每槽均值

| act 激活边 | needs 需要边 | 重合 | **覆盖率** | act 里多余的边 | 在途（可达）请求 |
|---|---|---|---|---|---|
| 60.8 | 6.5 | 3.4 | **31.71%** | 57.3 | 1.2 |

【表 2】槽级覆盖率分布（只统计 needs>0 的槽，约占 46%）

| 覆盖率 | =0 | (0,25%] | (25%,50%] | (50%,75%] | (75%,100%] |
|---|---|---|---|---|---|
| 槽数占比 | 0.66% | 0.66% | 25.28% | 20.28% | 7.53% |
| 平均 needs | 3.8 | 3.8 | 11.1 | 13.2 | 7.5 |
| 平均重合 | 0 | 0.0 | 4.6 | 8.2 | 6.9 |

【表 3】逐（请求,槽）：路径激活情况

| 路径被激活的比例 | 请求数 | 占比 | 平均跳数 | 平均覆盖跳 | 平均有库存跳 |

**结果 B：探针 O 的 BC 档**（与专家同协议，成功率 0.7342）

| 指标 | 专家 | **BC 起点** |
|---|---|---|
| act 激活边 / keep 钉住 / sw 新切 | 60.8 / 54.6 / 6.1 | 60.2 / **55.8** / 4.4 |
| 保持率 | 89.8% | **92.7%** |
| **游程均值** | 9.92 槽 | **13.71 槽** |
| live 在途 / unr 不可达 | 5.6 / 4.4 | 5.9 / 4.4 |
| dem / 预算 峰值箱 | 0.19 | 0.38 |
| 需求 > 预算的槽 | 0/2880 | 2/2880（0.07%） |

**结论**：

1. **"钉错了地方"实锤**：需求只要 6.5 条边，专家激活 60.8 条，重合只有 **3.4 条**；
   82.37% 的（请求,槽）样本里，请求路径**只有一部分跳**被激活 —— 而路径只要有一跳
   从来没攒出货，这条路径就永远不通。这同时解释了探针 O 的两个反常
   （钉得久 + 预算空）与探针 N 的 `bn@到达=0`。
2. **BC 钉得更久、切得更少，却更差**：游程 13.71 槽（专家 9.92）、保持率 92.7%（89.8%）、
   每槽只新切 4.4 条（专家 6.1）。**"保持/少切换"本身不是美德** —— 钉错了边，
   保持越久错得越久。这直接怀疑第四浪里 `switch_cost` 相关的方向：
   若 r4 的某臂靠"少切换"涨点，涨的可能是错的点。
3. **缺的那 2-3 跳就是 C 桶的 4.4 点**：部分激活组的路径平均 6.2 跳、有货 4.2 跳、
   当槽激活 3.0 跳 —— 离"全通"差的那几跳，与探针 N「库存不够 + 物理够」5.38% × (1−0.173) ≈ 4.4 点
   的窟窿在量级上对上了。
4. **每槽 4.4 个不可达在途请求是常态**（两组都是 ~4.4/5.9）：任一时刻约 3/4 的在途请求
   处于物理不连通状态 —— 这就是 B_avail 桶（9.43%）的逐槽面目，改策略救不了，
   只能靠"连通时抓紧攒"。
5. **优化方向收敛为一条**：让**生成跟着当槽在途需求走** —— 具体：
   (a) 查特征侧：actor 能不能看见"每条边当前库存"与"这条边在不在某个在途请求的路径上"
   （`build_edge_features` 里有没有这两列；没有就是对着半瞎的状态做决策）；
   (b) 查奖励侧：`dense_generation_importance_weight=0.02` 奖励的是 `relay_importance` 上的生成，
   若该重要性与当槽在途需求无关，它就是把货引向"结构性中心"的推手 —— 正是错位的来源候选。
   这两条是下一步探针/改动的顺序。

**记账坑**：

1. **表 2 的分箱标签错位**：区间 (0%,25%] 被打成了 "=0"（`lo > 0` 的标签分支写错）。
   **数据（JSON）不受影响**，只有打印标签错；节点上已在跑的这版照旧，读它的 JSON 就行。
   本地脚本已修。
2. **探针 P 的 `live`（1.2）与探针 O 的 `live`（5.6/5.9）不是同一个口径**：P 只数"当槽
   存在可用路径"的在途请求（不可达的记 `unr` 后跳过），O 数全部在途。差值就是不可达数
   （≈4.4），两个探针互为印证而不是矛盾。
3. **`needs` 用 BFS 最短路做代理**：实际服务路径可能更长/不同。所以覆盖率 31.71% 是
   "对最短路的覆盖"，真实错位只会更严重（实际路径更长、更难全覆盖），不会更轻 ——
   结论方向不受代理偏差影响。
4. **激活影响生成、不影响服务**（服务只看各跳库存为正）—— 这是理解本探针的前提，
   也是为什么"覆盖率低"的后果是"攒不出货"而不是"送不了货"。别把两者混了。

## 特征/奖励审计：三处共用 relay_importance，而它的窗口够不着真实路径

**问题**：探针 P 结论指向"让生成跟着在途需求走"。审计两条线：(a) actor 能否看见
"每条边当前库存"与"该边是否在在途请求路径上"；(b) dense 奖励 0.02 × relay_importance
是否把货引向结构性中心。

**审计方法**：直接读代码（`graph_builder.build_edge_features`、`relay_importance.compute_relay_importance`、
`reward._dense_importance_reward`、`env._compute_storage_pathness`、`path_greedy` 打分）+ 配置
（`features.yaml`、`env_full.yaml`）。

**发现 A：actor 不是半瞎（特征侧排除嫌疑）**

`features.yaml` 边特征实际开关：`include_qkp_capacity_left: true`（每条边有
(cap−level)/cap 一列，库存可由 1−x 反推）、`include_last_activated: true`、
`include_req_hop: true`（两端点到最近 pending 源/宿的 hop，4 列）、
`include_relay_importance: true`。**模型看得见库存，也看得见"靠近需求"的提示**。
半瞎假设不成立。

**发现 B：relay_importance 是三方共用信号，且窗口只到 3 跳**

`compute_relay_importance` 按当槽 pending 请求给分（`remaining × urgency`，
urgency = exp(age/τ)），并非"与需求无关"——上一节的怀疑只对了一半。但真正的要害：

    total_hops = min(端点离src) + min(端点离dst) + 1 ≤ max_path_links = 3

才得分，再乘 `hop_decay_factor^(h−2) = 0.25^(h−2)`。对诊断场景**平均 6.2 跳**的需求路径
（探针 P 表 3），路径中段任何边都有 min(离src)+min(离dst) ≈ H−1 ≥ 5 → total_hops ≈ H > 3
→ **整条路径 0 分**；能得分的只有"3 跳内的捷径边"——多数根本不在需求的路径上。
scarcity 权重 ((cap−level)/cap) 还偏爱"空边"，与"在已有货的边上续攒"方向相反（次要）。

而这个信号被**三处**共用：
1. **特征列**（actor 看见的"需求相关性"）；
2. **dense 奖励**（`dense_generation_importance_weight=0.02`，生成量 × importance，
   且 `dense_low_importance_penalty=0.01` 惩罚低重要性激活——双重押注）；
3. **专家 PathScoreGreedy 的 dense_fill 第二遍**（空闲端口按 importance 排序填充；
   探针 O 量到专家每槽激活 60.8 条、需求只要 6.5 条——**那 57 条"多余激活"正是
   dense_fill 填的**，填谁由 importance 排序决定）。

若窗口问题证实，专家与 RL 是被**同一个错位信号**带偏的——这能统一解释：
专家自己也只有 31.71% 覆盖率；RL 模仿专家 + RL 奖励也用它，错位被三重放大。

**发现 C：有一个对冲项存在但偏弱**

`storage_pathness`（`_compute_storage_pathness`）：无跳数限制的 BFS 路径标记
（"被激活且在某个 pending 请求可用路径上"），storage_reward_weight=0.5（除以 1e6）。
它方向正确，但：(i) 只对 `added − from_new`（存量吸收部分）计奖；(ii) 权重相比
served(50)/failed(5) 小；(iii) 特征侧**没有**对应的"在路径上"指示列（req_hop 只是
"靠近端点"，不是"在 src→dst 路径上"）。

**下一步（探针 Q，已在跑）**：与探针 P 同轨迹，量 `imp`（策略看到的 importance 非零边集）
与 `needs`（BFS 路径边集）的重合度 + 逐请求"路径上有几跳拿到分"。预期交集接近 0。
若证实，改动候选（按侵入性排序）：
- A. `max_path_links: 3 → 8` + `hop_decay_factor: 0.25 → 1.0`（features.yaml）：
  让 importance 覆盖整条真实路径。**同时改专家、特征、奖励三方**，一改三得；
  但专家行为会变（基线 0.7801 需重测），BC 特征分布失配（warm-start 受影响）。
- B. 若 A 后中段仍缺分，补"在路径上"显式特征列（storage_pathness 的特征版）。
- C. scarcity 方向反转（奖励有货边续攒）——只在与 A 组合有效时考虑，单独动风险大。

## 探针 Q：relay_importance 对需求路径几乎全盲（实锤）

**问题**：验证审计发现 B 的推断 —— max_path_links=3 的窗口是否真的让三方共用信号
对真实需求路径给不出分。

**脚本**：`.tmp/probe_relay_coverage.py`（探针 Q，新建）。
**方法**：与探针 P 同轨迹（专家档、诊断场景 240 步、12 种子 7–18、确定性、线程 2），
逐槽取 `graph_builder.last_relay_importance` 非零边集（= 策略下一槽看到的 importance，
与 dense 奖励同源），与 needs（BFS 最短路边集）求交；逐（请求,槽）数路径上有几跳
拿到分。**成功率 0.7801 与基准逐位一致**（交叉核对通过）。

**结果**：

【表 1】每槽：imp 得分边集 vs needs 需求路径边集

| imp 得分边 | needs 需要边 | 重合 | **imp 覆盖率** | imp 里需求外的边 |
|---|---|---|---|---|
| **1.6** | 6.6 | 0.6 | **7.09%** | 1.0 |

【表 2】逐（请求,槽）：路径上 importance>0 的跳数

| 路径得分情况 | 请求数 | 占比 | 平均跳数 | 平均有分跳 |
|---|---|---|---|---|
| 整条路径有分 | 242 | 6.73% | 2.9 | 2.9 |
| 部分跳有分 | 748 | 20.80% | 6.0 | 1.5 |
| **一跳都没分** | **2606** | **72.47%** | 6.4 | 0.0 |

**结论**：

1. **实锤**：72.47% 的（请求,槽）需求路径**一跳都拿不到 importance 分**；得分边每槽
   只有 1.6 条（专家激活 60.8 条），对需求路径覆盖率 7.09% —— 比专家实际激活的覆盖率
   （31.71%）还低 4 倍。三方共用信号（特征列、dense 奖励、专家 dense_fill）对绝大多数
   在途需求是**瞎的**。
2. **能得分的只有"整条 ≤3 跳"的短需求**（6.73%，平均 H=2.9）和路径两端 1.5 跳。
   "结构性中心"的旧怀疑修正为：**不是引向中心，而是只看得见短需求** ——
   长需求的路径上没有任何梯度指向。
3. **专家 dense_fill 的排序因此退化**：60.8 条激活里 importance 有分的不到 2 条，
   排序键 (kept, imp, edge_score) 退化成 (kept, edge_score) —— "保持旧边 + 高速率边"
   主导了填充，这正是探针 O 量到的"钉住 54.6 条、游程 9.92 槽"的来源。
   专家的"钉错地方"不是选择错误，而是**信号缺失后的默认行为**。
4. 改动方案 A（max_path_links 3→8 + hop_decay 0.25→1.0/0.8）升级为首选：
   一处参数同时修复三方。注意专家侧参数是 `compute_dynamic_relay_importance` 的
   **函数默认参数**（不走 config），改 features.yaml 只覆盖特征列与奖励两方，
   专家方要另改 `greedy_relay_diffusion.py` 的默认值 —— 别只改一半。

**记账坑**：探针 Q 的 needs/imp 取的是 step 后（t+1 观测）状态，与探针 P 的 t 槽口径
差一槽；成功率逐位一致说明轨迹没被记录代码扰动，读数可与探针 P 直接对比。

## 窗口放开验证：imp 信号修复（7%→50%），专家 +0.8 点（噪声边缘）

**脚本**：`.tmp/probe_imp_window.py`（窗口验证，新建）。
**方法**：专家的 importance 来自 `GreedyRelayDiffusionPolicyV3` **实例属性**
（`max_path_links=3`、`hop_decay_factor=0.25` 默认，不走 config）→ 验证脚本直接构造
scorer 覆盖实例属性，并同步 env.config 的 relay_cfg（= 特征列 + dense 奖励的来源）。
两档：8/1.0、8/0.8，与对照（3/0.25）同协议 12 种子。

**结果**：

| 档（窗口/衰减） | 量加权成功率 | act | act∩needs | act 覆盖率 | imp 得分边 | **imp 覆盖率** |
|---|---|---|---|---|---|---|
| 对照 3/0.25 | 0.7801 | 60.8 | 3.4 | 31.71% | 1.6 | 7.09% |
| 8/1.0 | 0.7876 | 61.5 | 2.7 | 25.08% | 114.2 | **50.51%** |
| 8/0.8 | **0.7886** | 61.5 | 2.7 | 25.23% | 113.3 | **50.78%** |

**结论**：

1. **信号修复成功**：得分边 1.6 → 114 条/槽，imp 覆盖率 7.09% → 50.5%
   （needs 平均 5.7 条里 5.4 条有分）。特征列与 dense 奖励从此"看得见"长需求路径。
2. **专家 +0.75/+0.85 点**：低于 1.2 点的配对分辨率（单档不显著），但逐种子差
   12 个里 9-10 个为正、两档方向一致。专家受惠有限是合理的：它的服务决策主要走
   phased 的存量/路径服务阶段，importance 只影响 V3 边分的排序项。
3. **act 覆盖率反而降（31.71%→25.2%），不是坏事**：轨迹变了（成功率涨 → 在途少 →
   needs 6.6→5.7），且"激活覆盖 BFS 最短路"只是代理指标——真实服务路径未必是
   最短路。**别把代理指标的涨跌当成目标本身**，判据仍是成功率。
4. **决策：采纳 8/0.8**（成功率略优 + 保留"近需求优先"的语义）。正式改两处默认值：
   `features.yaml` 的 relay_importance 块 + `greedy_relay_diffusion.py` 的
   max_path_links / hop_decay_factor（V1/V2 继承链，V3 继承 V2）。
   对 RL 的意义大于对专家：解除特征列与 dense 奖励的"3 跳致盲"。
5. **RL 验证排在 r4 跑完之后**（节点资源）。风险已知：BC warm-start 的特征分布漂移
   ——importance 列从"几乎全 0"变成"0–1 连续"，GNN 需要适应；但边特征**维度不变**，
   可先不重训 BC，直接 RL 微调对比（若 KL/熵异常再回头重跑 BC）。

**记账坑**：

1. 第一版验证 patch 了 `compute_dynamic_relay_importance` 的函数默认参数——**无效**
   （成功率与对照逐位相同）：V3.score_edges 显式传实例属性，绕过了函数默认值。
   教训：patch 前先追"参数从哪来"，实例属性 > 函数默认 > config 的优先级要分清。
2. 专家侧参数不走 config，改 features.yaml 只覆盖两方（特征列/奖励）——
   训练侧实验若要专家同口径，`greedy_relay_diffusion.py` 默认值必须同步改。

1. **窗口修复对 RL 三档全部无增益**（最关键的 ent_ep2 档：−0.12 点，t=−0.65，完全打平）。

**问题**：用户要求整理项目结构、审核训练速度的底层代码。静态读代码的候选清单

| 两次手写 BFS | ~0.32–0.38 ms | **手写快于 scipy 85%**（配对实测 0.086 vs 0.591 ms）|
| **输出组装** | **~0.35–0.45 ms** | **真正瓶颈：逐边建 tuple + 调用方 np.fromiter 展平** |

手写 BFS 不能换 scipy 的原因：活跃图只有 88 节点，scipy shortest_path 的
多源调用开销（CSR 构造 + C 层派发 + 结果字典化）远大于 Python 层 deque 的
两次循环；配对计时证实手写快 85%。

**所以唯一能动的就是输出组装**。

### 改动

`graph_builder.py` 三处改动（全在 `_compute_req_hop_features` 和
`_build_physical_edge_rows_vectorized`）：

1. **`_compute_req_hop_features`**：返回值从 `dict[str, tuple[4 float]]`
   改为 `tuple[dict, np.ndarray]`。同一次扫边里同时填 dict（供 legacy
   逐行路径 fallback）和四个 `np.empty(n)` 列缓冲，最后 `column_stack`

2. **`build_edge_features`**：接双返回值，把 `req_hop_arr` 传给

## 2026-09-18 可复现性缺陷 + 测量规程违规

本轮先做速度优化，途中查出一个根因级的缺陷，它同时推翻了此前几浪的判读。

### 一、根因：rollout 动作采样从未播种（提交 `d4bd79c`）

**现象**：两个**完全同配置**的臂（`r7_fix_g999` 20 轮 vs `r7_fix_g999_long`
60 轮，只差 `--num-updates`）从**第 1 轮**起就分歧：

```
update 1:  mean_reward  91.81435939357533  vs  91.84482827798688
           mean_served_keys  93154758.407  vs  93183513.703   (差 0.03%)
第 20 轮 eval 差 0.037
```

**机制**：匹配采样器的 Gumbel 噪声用的是 torch **全局** RNG
（`policy.py` 的 `torch.rand(n_arcs+1)`），而 `torch.manual_seed` 只在主进程
（`MAPPOTrainer.__init__`）调用一次。rollout worker 是 `spawn` 出来的独立
解释器，`_worker_entry` 从头到尾**没有播种**，全局 RNG 由 OS 熵初始化。

叠加因素：8 个 worker 共享一个任务队列，**哪个 worker 处理哪个 seed 取决于
进程调度**；每个 worker 的 RNG 流跨 episode 累积（从不在 episode 间重设），
所以 seed→动作的映射随调度漂移。

**为什么长期没被发现**：`env.reset(seed=...)` 把请求流钉死了，于是
"请求相同、动作不同"，看起来像测量噪声而不是 bug。而评估走
`deterministic=True`，根本不抽 Gumbel，所以 eval 本身是**逐位确定的** ——
它如实反映了权重差异，反而让差异看起来"合理"。

**修复**：`MAPPOPolicy.set_sample_seed()` 用显式 `torch.Generator` 取代全局
RNG（接受 int 或 list，后者给 `act_batched` 每行一个，避免某行的噪声取决于
同批有几行、谁先算完）；worker 按 episode seed 播种；trainer 三条 rollout
路径（worker / serial / batched）统一走 `_reset_env`/`_reset_envs`。

### 二、我的终止语义修复是错的（已回滚，提交 `d048633`）

**训练成功率 25 轮不动，PPO 在这套配置下没有可测的效果。** 而且

### 七、修正后的结论


## 内存墙：并行铺开被 OOM 打断，根因是孤儿 worker（2026-09-19）

**发生了什么**：上一节写"3 种子并行（各 4 线程 = 12/32 核）"后，我又并行铺到
6 个 run（r9ext 52/53/54 + w329 62/63/64），判断依据是 `load average` 只有 10/32、
"28 核闲置"。**这个判断是错的——瓶颈不是 CPU，是内存。**

**症状**：

1. 6 个 run 里有 4 个在 30 分钟内消失，`/tmp/<run>.log` 只写到 update=1 或 2
2. 幸存的 run 每轮耗时翻倍：`rollout_s` 46 → 82s，`update_s` 145 → 196s
3. `free -g` 显示 used 110/125 GB，但 `ps` 里能看见的只有 ~42 GB

**根因（PSS 审计，`.tmp/mem_audit.py`）**：

| 组 | 进程数 | PSS 合计 |
|---|---|---|
| 孤儿 worker（PPid=1，multiprocessing.spawn） | 81 | **58.76 G** |
| r9ext_s53（活着） | 2 | 13.10 G |
| w329_s64（活着） | 1 | 13.10 G |

**每个 run 的真实内存是 ~13 GB，不是 1-2 GB。** 6 个 = 78 GB，加上被 OOM 杀掉后
**没有自杀的 worker**，累积到 110 GB。`Committed_AS` 达 228 GB（物理 125 GB），
swap 只剩 0.16 GB——这才是耗时翻倍的直接原因（内存带宽 + swap I/O 争抢）。

**孤儿怎么来的**：OOM killer 杀的是 **trainer 父进程**，`multiprocessing.spawn` 出来的
8 个 rollout worker 被 reparent 到 init（PPid=1）后**继续空转**。按启动时刻聚类，
孤儿分三批，对应三次被杀的 run：

| 启动时刻 | 个数 | PSS | 归属 |
|---|---|---|---|
| 05:01 / 05:15 / 05:17 | 27 | 16.2 G | 昨夜已死的 run |
| 11:45 / 11:48 / 11:58 | 27 | 20.2 G | 今早已死的 run（含 r9ext_s52） |
| 12:10 | 27 | 22.3 G | 本次被 OOM 的 3 个 |

即：**这个坑从昨夜就在积累**，我看到的 110 GB 里有一半是历史遗留。

**清理（`.tmp/kill_orphans.py`）**：判据是「PPid==1 且 cmdline 含 multiprocess」——
worker 自身 cmdline 里没有 run-name，无法自证归属，但 PPid 是可靠且完备的：
父 trainer 活着 → PPid=trainer_pid≠1 → 不是孤儿；父被 OOM 杀 → PPid=1 → 永远
不可能再产出结果。脚本带保护名单闸（活着的 trainer/shell 及其父），本次保护
`[1, 50155, 52777, 53548, 53549]`，其中 52777 是还活着的 w329_s64、53549 是
r9ext_s53——两者都在名单内，未被误杀。

清理结果：**杀 81 个，释放 58.76 G**，`MemAvailable` 13.4G → 73.3G，
`SwapFree` 0.16G → 7.64G。清理后幸存 run 立即恢复：
`rollout_s` 82 → 49s，`update_s` 196 → 155s。

**教训（写进规程）**：

- **并行铺 run 前先算内存，不是先看 load**。判据：`可用内存 / 13 GB` = 可并行 run 数。
  125 GB 机器上 8 个 run 就已到顶，考虑 swap 余量后 **6 个是实际上限**。
- **CPU 核数不是限制**：每个 run 只吃 3 核，32 核能跑 10 个；内存才是墙。
- **过载时每轮耗时会被拉长但不改变数值**（线程数没动），所以"跑得慢"不是
  唯一症状——要看 `rollout_s/update_s` 有没有异常上涨。
- 杀进程前务必查孤儿。`pkill -f train_graph` 只杀父进程，会**制造**新的孤儿。

## 从 outputs/ 历史挖出最强单参数线索：entropy_coef 0.001 → 0.01（2026-09-19）

**怎么发现的**：不再只跑新实验，而是把 `outputs/` 下**所有历史 run 的 resolved_config
做两两差异对比**（`.tmp/diff_runs.py`）。历史里已经躺着答案，但没人做过系统对比。

**线索一：`r7_base` vs `r7_fix_ent`** —— diff 显示 **271 个字段里只有 2 个不同**
（`project.run_name` 和下面这一个）：

| 字段 | r7_base | r7_fix_ent |
|---|---|---|
| `train.ppo.entropy_coef` | 0.001 | **0.01** |
| 验证成功率（u20） | 0.6159 | **0.7113** |

**+0.0954，且 0.7113 超过专家 0.6980** —— 这是全项目**唯一一个单参数改动就超过专家**的记录。
种子审计（`.tmp/seed_audit.py`）确认两者 `global_seed=42`、`env_seed=7` **完全相同**，
是干净的配对对照，不是种子混淆。

**线索二：`r8_base_s42` vs `r8_ent01_s42`** —— 同种子 42/42，只差 entropy_coef：

| run | entropy_coef | u5 验证 |
|---|---|---|
| r8_base_s42 | 0.001 | 0.6480 |
| r8_ent01_s42 | 0.01 | **0.6896** |

**+0.0416**，按 `docs/测试规范.md` §4⑦ 的 0.035 分辨率**可分辨**。

两次独立对照方向一致。**这个参数一直设错了**：`configs/rl_algorithm.yaml:77`
是 `0.001`，而 `train_full_rl.yaml` 不覆盖它——于是 r8/r9ext **所有** run 都在用
已被证明更差的值。

**机理**（与 r8 的发现一致）：本项目的训练侧优势早已饱和
（`mean_abs_advantage` 1.08 → 0.32），策略在训练分布上接近确定性。熵系数 0.001
时探索迅速坍缩，rollout 分布变窄，到验证 regime 就吃不到新的状态覆盖；
0.01 让策略在验证分布上仍保有熵。这与"涨的是验证侧、不是训练侧"（r8）方向吻合。

**行动**：新建 `configs/train_ent01.yaml`（纯增量覆盖，不改基线），
停止所有 ent=0.001 的 run，启动**配对实验 ent01_s42/43/44**（种子与
r8_base_s42/43/44 完全相同，只改 entropy_coef，30 轮）。

轮数取 30 而非 r8 的 15：`r7_fix_ent` 的曲线在 u20 **仍在上升**
（u15 0.7063 → u20 0.7113），15 轮会切在上升段中间，看不到平台。

**判读标准（事先定好，避免事后找解释）**：
- 若 ent01 三种子在 u15 的均值比 r8_base 的 0.6893 高出 ≥0.035 → 结论成立，写进报告
- 若高出 <0.035 → 落在分辨率内，判为"不足以确认"，需要更多种子
- 若持平或更低 → 推翻 r7/r8 两次线索，回到 0.001

**顺带修正一个此前的错误判断**：上一节我说"3 种子并行（12/32 核）是安全的加速手段"，
按 CPU 核数算是对的，但按**内存**算是错的——每个 run 13 GB，3 个就是 39 GB。
并行度必须由内存决定，不能用核数推。
