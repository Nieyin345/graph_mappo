## 4. 买服务器之前先看这一条：核多现在用不上

实测（本机）：
- **rollout 是单进程 CPU 受限的**：每轮 rollout 25 s（12 线程）vs update 15 s（GPU）；
- **8 个 worker 进程的并行效率只有 41%**，而且比单进程分块**还慢**（33 s vs 27 s）。

所以现在给我 64 核也不会线性变快。真正有用的是：

| 服务器特性 | 收益 |
|---|---|
| **单核性能强** | rollout 的 Python 开销直接受益（目前瓶颈） |
| **显存大** | 可把 `batch_chunk` 从 256 提到 512–1024，减少 update 的分块次数 |
| 核多 | **暂时用不上**，除非先修好 worker 路径（权重同步现在把整个 state_dict 塞进每个任务；H5 分块需要改成共享内存映射） |

如果想要"多核能吃满"，需要我先做那两项改造 —— 那是代码工作，不是买机器能解决的。

## 5. 上机后的第一条自检

```bash
python scripts/rl/train_graph_mappo.py --configs rl_algorithm.yaml train_diag_fast.yaml \
  --checkpoint outputs/supervised_pg_phased/supervised_pg_phased_latest.pt \
  --run-name diag_smoke --num-updates 3
```

期望值（本机含后台负载的实测）：

- 每轮 ~40 s（rollout ~25 s + update ~15 s），干净的服务器上应更快；
- update 1 的成功率落在 **0.72–0.75**；
- `V/R ≈ 0.05` 起步、`kl ≈ 0.001`、`actor_grad ≈ 0.26`、`critic_grad ≈ 0.27`；
- `entropy ≈ 3.16`。

若明显偏离，先查：数据/权重是否拷全、`rate_stats.json` 是否生成、`--device` 是否用上 GPU。

  --checkpoint outputs/supervised_pg_phased/supervised_pg_phased_latest.pt \
  --run-name full_rnd15 --num-updates 30

# B：8 个固定日 + 固定请求流（唯一变量是 fixed_episode_seed）
python scripts/rl/train_graph_mappo.py --configs rl_algorithm.yaml train_full_rl_fixdays.yaml \

解读：**B 涨而 A 不涨 → 泛化问题；两者都不涨 → 优化问题。**

## 7. 两个操作的坑（都踩过）

1. **一次只跑一个训练进程。** 本机曾有两个进程互相拖死 **12 小时**、零输出（很可能是驱动 TDR
   或休眠后 CUDA 上下文损坏，进程仍在空转吃满一个核）。判断特征：**进程活着、CPU 在涨、
   但 `metrics.jsonl` 不再前进**。我加过的"等前一个跑完再启动"的排队用了 `kill -0 <Windows PID>`，
   在 Git Bash 里认不出 Windows PID、会直接放行 —— 不要用 PID 排队，用 **metrics 行数**轮询。
2. **配置片段必须自包含。** `--configs a.yaml b.yaml` 是顺序深合并；`b.yaml` 如果只写一个键，
   剩下的会继承默认链里 `random_episode` profile 的值。我曾经因此让一个手臂静默跑成了
   `rollout_steps: 4320`（3 倍长）。**启动后核对日志里的 `running config:` 那一行。**
