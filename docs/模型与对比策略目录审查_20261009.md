# 主模型与对比模型代码结构审查（2026-10-09）

## 结论

**模型目录大体合理，不建议把 v2–v8 全部移动、合并或重写。** 当前 `model_zoo/` 是神经网络模型版本，`rl/` 是共享训练算法，`baselines/` 是随机/贪心/启发式策略，`scripts/` 是实验入口。主要问题不是文件放错了，而是**模型身份、评估注册不统一、版本名称混淆和历史代码维护成本**。

根据 `scripts/batch/run_paper_experiments.sh`（2026-10-07 配方），**拟用于论文的主要方法**为 `v8` 配合 `diag_selfnew_h3_w04.yaml` 等预测预备 overlay；它是否为目前训练成绩最好的方法，需要回到当期运行产物判断，不能仅由路径断言。**强化学习 v7 与物理信道 v7.5 是两套完全不同的版本体系。**

## 3. 为什么主模型不是默认 v2

`qkd_rl/model_zoo/__init__.py` 的注册器在缺少 `experiment.model` 时会兼容性回退 v2；`scripts/experiment.py` 命令行默认也写着 `v2`。这只是**代码的历史默认模型**，不是论文方法的唯一身份。论文配方通过 `scripts/experiment.py train --model v8 --config ...` 明确选择方法。

建议今后对任何正式比较执行以下约定：**必须显式传入模型版本与全部结构 overlay**，连同训练起点（从零或哪个 BC checkpoint）、种子、场景 H5 及评估任务指纹写入 manifest；任何一项缺失就不进入论文主对照表。

## 4. 目前尚存的结构问题与风险

1. **策略身份由配置共同决定。** 相同 `model_zoo/v8/` 在 `forecast_off`、`v8_bias`、`self_new`、`self_shuffle` 等覆盖下是不同实验臂。建议给实验 manifest 一个唯一的 `method_id` / resolved-config 哈希，而不仅一个 `model=v8` 标签。本次没有改变这项运行协议。
2. **历史代码复用。** `qkd_rl/rl/models/graph_mappo.py` 只是 v2 的重导出兼容入口，不能作为通用模型工厂；其他入口应使用 `qkd_rl.model_zoo.build_model`。
3. **评估入口散落。** `scripts/train/eval_fixed_scenario.py`、`scripts/baselines/eval_long_horizon.py` 实际是评估代码，位置不够统一。现阶段移动它们会破坏调用命令和文档链接；建议今后新评估入口放在 `scripts/eval/`，历史入口保留兼容。
4. **神经网络版本文件多且大。** 复制快照应当只维护 bugfix，不加新功能；新架构通过组合公共组件设计，旧快照只用于历史复现。
5. **v5 可见但不可运行。** 本地没有完整实现；如果未来需要作为正式神经网络对照，应先引入对应服务器分支的可复现代码与 checkpoint 配置，不应直接用空目录名称占位参评。
6. **从源到评估的闭环还需独立运行验证。** 本轮测试是在本地 Windows 上做了静态 AST 检查、配置合同和语法编译；由于此前本机 PyTorch 的 `c10_cuda.dll` 加载依赖错误，本轮**没有进行完整 v8 checkpoint 的模型前向/端到端对照评估**。需要在具备正常 PyTorch 环境的机器上按真实 checkpoint 验证。
