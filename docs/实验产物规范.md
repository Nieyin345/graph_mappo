# 实验产物规范（格式统一）

> **这是什么**：**每次实验产出的文件放哪、叫什么、里面有哪些字段**的强制规范。
> 目的只有一个：**任意两次实验的结果可以直接并排比较，不需要读日志、不需要问人。**
> **怎么用**：开跑前照 §2 建目录、§3 起名；跑完照 §4 写记录；收工前照 §7 自检。
> **改这份文档 = 新老产物不再可比**，改前先确认存档已冻结（见 §8）。
> 相关：[`测试规范.md`](测试规范.md)（判据）、[`00_索引.md`](00_索引.md)。

当前问题（2026-09-25 实测，就是本文要消灭的对象）：

| # | 现状 | 后果 |
|---|---|---|
| 1 | 评测 JSON 里 **expert 和 RL 的字段不一样**（expert 没有 `seeds`/`per_seed_generated_keys`） | 并排比较要手写两套解析 |
| 2 | `metrics.jsonl` **没有时间戳、没有节点名、没有代码指纹** | 无法复现，无法判断能否跨节点比 |
| 3 | 时间戳用 `time.gmtime()` 存成 UTC `Z`，日志时间却是本地 | 对不上时区 |
| 4 | **节点只写在目录名里**（`server_results_node342/`） | 换节点后读数字的人不知道是哪台机 |
| 5 | 目录名混用 `frozen_s42` / `frozen_isolated_s42` / `runs/` / `experiments/`；`frozen_20260924/experiments/experiments/` 出现过嵌套重名 | 找不清哪个是哪一批 |

---

## 1. 三条总原则

1. **原始数据只增不删**（`outputs/` 红线不变）。规范管的是**新增**文件；老产物保持原样，按 §8 登记，不就地改写。
2. **一个 (策略 × 窗口 × 种子) = 一条记录**，记录是**自包含**的：不看文件名、不看目录、不看日志，也能知道它是谁、什么时候、在哪台机、什么代码跑出来的。
3. **同名同义**：任何两个地方出现的同一个概念，必须用同一个 key 名。禁止 `success_rate` / `mean_success_rate` / `sr` 混用。

---

## 2. 目录布局（一批实验一个时间戳目录）

```
server_results[_<node>]/<batch-id>/
  BATCH.md              # 人读：这一批是什么、协议、结论（模板见 §6）
  # 产物原样放 raw/；台账是脚本从 raw/ 重建的（§4），不放在批次目录里
  raw/                  # 原始产物，原样搬回，不改内容
    metrics/<arm>/metrics.jsonl
    rollout/<arm>/rollout_debug.jsonl
    eval/<arm>_<window>.json          # frozen_eval 原始输出，未加工的
    logs/<arm>.train.log
  summaries/            # 加工产物：配对检验、汇总表
    paired_<A>_vs_<B>.json
```

- **`batch-id`**：`<YYYYMMDD>-<一句话主题>`，如 `20260925-critic-poolmax`。**必须带日期**。
- **`raw/` 里的文件保持工具原样**（`frozen_eval.py` 写什么就是什么）。**所有标准化只发生在台账与 `summaries/`**。
  ⟹ 这样既不破坏历史可比性，又拿到了统一格式。
- **`arm` 名**（一次实验里的一个对照组）：`<模型>-<配置要点>-s<训练种子>`，如
   `v3-poolmax-s42`、`v4-lstm-s42`、`v2-base-s42`、`expert`。
  规则：只用小写字母/数字/连字符；**不加** `outputs_` / `experiments_` 之类前缀；**配置要点必须能区分本批的对照组**。
- 节点名**只允许出现在 `server_results[_<node>]/` 这一层**，不许再往下沉积。

## 3. 文件名

| 文件 | 规则 | 例 |
|---|---|---|
| 每轮训练指标 | `metrics.jsonl`，**一行一轮**，字段见 §5.1 | `raw/metrics/v3-poolmax-s42/metrics.jsonl` |
| rollout 分解 | `rollout_debug.jsonl`，一行一轮，字段见 §5.2 | `raw/rollout/v3-poolmax-s42/rollout_debug.jsonl` |
| 单次评测 | `<arm>_<window>.json`，字段见 §5.3 | `raw/eval/v3-poolmax-s42_A.json` |
| 配对检验 | `paired_<A>_vs_<B>.json` | `summaries/paired_v3-poolmax_vs_v2-base.json` |
| **中心台账** | `outputs/model_ledger.jsonl`（全批次合并，脚本生成） | — |
| **模型结果台账** | `qkd_rl/model_zoo/<model>/RESULTS.md`（脚本生成，见 §6.5） | — |

**`window` 取值**：`A` / `B`（与 `frozen_eval.py` 的 `WINDOWS` 键一致，勿自造 `A1`/`valid`）。
**禁止**在文件名里同时塞策略全路径（旧产物 `rl_outputs_experiments_v2_frozen_s42_A.json` 就是这个毛病）——路径信息进台账的 `run.checkpoint` 字段。

## 3.4 ★ 版本号规则：代码一改就是新版本，独立文件夹

**任何代码改动（新模型、改结构、改观测、改奖励）都必须是一个新版本号 `v<N>`，
放在自己独立的目录 `qkd_rl/model_zoo/v<N>/`。绝不在原目录上改。**

**为什么**（这是踩出来的，不是洁癖）：

- 版本号一旦被两个不同的模型共用，**名字就不再指向唯一的模型**。本项目实测过：
  `v4` 同时被指给了 (a) repo 里的「需求隔离 + 4 跳站对注意力」和
  (b) 服务器另一分支的「LSTM 因果请求序列」。结果是一份**描述 (b) 的文档被当成 (a) 的
  架构说明**，诊断建立在错误的模型上。
- 历史臂的 checkpoint 是在旧代码下训的。原地改代码 ⟹ 旧 checkpoint 再也载不回来，
  而**载入失败常常是静默的**（形状对上就继续跑，语义已经变了）。
- 「这个数字是哪个代码跑出来的」必须能回答。版本号是回答它的最便宜手段。

**规则**：

1. **新版本号 = 新目录**。`model_zoo/v<N>/` 自带 `model.py` + `config.yaml` +
   `model_impl.py` + `graph_builder.py`，不 import 其它版本的实现
   （见 [`统一训练底座.md`](统一训练底座.md)：复制而非继承，让运行 manifest 能指纹
   完整源码）。
2. **版本号只增不改**。发现旧版本有 bug，**不改旧目录**：在新版本里修，并在新版本的
   台账里写「修了 vN 的什么 bug、同权重重评后差多少」。
3. **一个版本号只指一个模型**。发现重名（像 v4 那样），**给新的那个往后排号**，
   并在两边台账的「设计要点」里互相写明区别。
4. **版本号属于模型结构，不属于实验臂**。同一版本下的不同配置（隔离开/关、温度、
   学习率）是**同版本的实验臂**，命名见 §2 的 `arm` 规则，**不另开版本号**。
   ⟹ 判据：改了 `model_zoo/<v>/` 下的代码 → 新版本；只改 `configs/*.yaml` → 同版本。

## 3.5 ★ 记录放在模型自己的文件夹下，不汇总到一起

**每个模型类型在 `qkd_rl/model_zoo/<model>/` 下有自己的一份结果台账**，代码和它的成绩放在一起：

```
qkd_rl/model_zoo/v2/RESULTS.md     ← v2 的代码 + v2 的成绩
qkd_rl/model_zoo/v3/RESULTS.md     ← v3 的代码 + v3 的成绩
qkd_rl/model_zoo/v4/RESULTS.md     ← v4 的代码 + v4 的成绩
```

### 3.5.0 ★★ 服务器**禁止写代码**，本地是唯一代码源

**这句话是硬规则，不是建议。服务器上的 `.py` / `.yaml` 一律只读。**

```
本地改 → sync.sh 同步 → 服务器只负责跑 → 产物自动拉回本地 → 更新台账
```

#### 为什么（有两次实际损失）

1. **同步会被卡住**。`sync.sh` 用 `git push` 到节点的 `refs/heads/deploy`，
   节点的 `receive.denyCurrentBranch=updateInstead` **要求工作区干净**。
   在服务器上改过文件 ⟹ 工作区变脏 ⟹ **推送被拒**。实测 2026-09-26 就这样被挡了一次，
   要逐个文件 md5 核对才能安全清理。
2. **代码会永久丢失**。在服务器上改的代码不进任何 git 历史，
   删工作树 / 换节点 / 分支被清理时就没了。**实测已发生**：
   - `v5`（LSTM 因果请求序列）的实现，随分支消失，**代码已不可恢复**
   - `pairhist_v3` 用的 `pair_path_residual`，在当前 v3/v4 里**不存在**，同样丢失
   - 两次查遍服务器 372 个提交的全历史 `git log -S`、reflog、悬空对象、本地所有 ref、
     两份归档仓库副本，**均无**
   保住的是**数据**（checkpoint + metrics + train.log），丢的是**产出数据的代码**——
   于是这些 checkpoint **再也无法复现、无法续训、无法解释**。

#### 允许在服务器上做的

只有**产物**：`outputs/`、`.tmp/` 临时探针、日志。探针用完要么删，要么
`scp` 回来放进本地 `.tmp/`——**探针也是代码，也有价值**。

#### 三个铁律

> **① 删服务器上的任何东西之前，先确认本地有等价副本**（md5 核对，不是"应该有"）。
> **② 服务器上独有 = `outputs/` 里的产物**，这是唯一需要在删除前抢救的东西。
> **③ 换节点/重建服务器是安全的**——服务器工作树可以整个删掉重传；
> 「本地有、服务器没有」无害，「服务器有、本地没有」才是灾难。

#### 同步与回传

```bash
# 本地 → 服务器（推工作区快照，含未提交改动）
bash deployment/sync.sh

# 服务器 → 本地（训练完把产物拉回来；见 §3.5.2）
bash deployment/fetch_results.sh <run-name>
```

推送被拒（`Working directory has unstaged changes`）时的处理见 §3.5.0.1。

#### 3.5.0.1 推送被拒怎么办

```
! [remote rejected] ... -> deploy (Working directory has unstaged changes)
```

**不要直接 `git reset --hard`**——那会把节点上改的东西悄悄丢掉。
按顺序：

```bash
# 1) 看脏在哪
ssh qkd 'cd /opt/qkd/graph_mappo && git status --porcelain'

# 2) 逐文件确认本地有等价副本（md5 要比，不能只看文件名）
ssh qkd 'cd /opt/qkd/graph_mappo && md5sum <脏文件...>'
md5sum <本地同名文件...>          # 必须逐个一致

# 3) 只有确认"本地全都有且一致"才清理
ssh qkd 'cd /opt/qkd/graph_mappo && git checkout -- <改动> && rm -f <未跟踪>'

# 4) 重跑同步
bash deployment/sync.sh
```

**若某个脏文件本地没有**：先 `scp` 回来，再清理。永远不要在没有副本时丢东西。

**为什么**：要查"v3 到底跑过多少、成绩多少"时，直接进 v3 目录，不必在跨批次目录树里翻找，
也不会把 v2 的数字和 v3 的混淆。

**两层结构，各司其职**：

| 层 | 位置 | 作用 |
|---|---|---|
| 中心台账 | `outputs/model_ledger.jsonl` | 全部批次的**单一事实源**，一条记录一行；机器读写、跨模型配对检验用 |
| 模型台账 | `qkd_rl/model_zoo/<model>/RESULTS.md` | **人读视图**，只含该模型（+ 共享的 expert 锚），由台账生成 |

- 模型台账**由脚本生成，不手改**。生成命令：
  ```bash
  python scripts/diag/backfill_manifest.py --repo-root . --apply
  ```
- 每个模型台账的表格由脚本重写，但**文末「备注」段是人工维护的，重新生成时原样保留** —— 想写的话写在那里。
- 每个模型台账**自带「测试环境」表**（见 §4.1），所以单独把某个模型的文档发给别人也够用。

### 3.5.1 ★ 每次拿到结果就更新对应模型文档

**一次实验跑完、数字出来之后，必须做的一件事**：把新结果登记进台账。顺序固定：

1. 把原始产物放进所属批次的 `raw/`（§2）
2. 在批次目录写 `BATCH.md`（§6）
3. **重新生成台账**：
   ```bash
   python scripts/diag/backfill_manifest.py --repo-root . --apply
   ```
4. 检查 `<model>/RESULTS.md` 里新记录是否出现、`env_fp` 是否与对照一致

**这不是可选项。** 没有第 3 步，`RESULTS.md` 就是过期的；而一份过期的台账比没有更糟——
它看起来完整，实际少了最新那行，半年后据此判断"这个方向没跑过"。

### 3.5.2 ★★ 产物自动回传：一次训练完，必须落到对应的模型文件夹

**训练跑完，产物要自动拉回本地，并按「哪个模型 → 哪个目录」分流。**

```bash
bash deployment/fetch_results.sh <run-name>          # 拉一个 run
bash deployment/fetch_results.sh --all-v4            # 拉某模型全部
```

**落位规则（脚本按 `resolved_config.yaml` 的 `experiment.model` 自动判断）**：

| 产物 | 落到哪 |
|---|---|
| 该模型的训练产物（checkpoint/metrics/rollout_debug/train.log/config） | `server_results/<batch-id>/`（§2 的批次目录） |
| 冻结评测 JSON | `server_results/<batch-id>/eval/` |
| 该模型文档更新 | `qkd_rl/model_zoo/<model>/RESULTS.md`（重跑 §3.5.1 第 3 步） |

**不同的结果拉回不同位置**，靠三条键决定，缺一不可：

1. **`model`**（`experiment.model`）→ 决定进哪个模型的台账
2. **`batch-id`**（日期 + 主题）→ 决定进哪个批次目录
3. **`window`**（A/B）→ 决定是哪个窗口的读数

> **为什么必须按模型分流**：本项目吃过这个亏——`v4` 曾同时指两个模型，
> 结果一份描述 v5 的文档被当成 v4 的架构说明，**诊断建立在错误的模型上**。
> 分流不是整洁癖，是防止归错模型。

**回传后必做**：重跑台账生成（§3.5.1 第 3 步），确认新记录出现在
`<model>/RESULTS.md` 且 `env_fp` 与对照一致。

> ⚠ **回传是"抢救"，不是"备份"**。服务器是易失的：节点会被回收、
> 实验实例会重启、工作树会被删。产物**只在服务器上就是没保住**。
> `outputs/` 的只增不删红线管的是本地。

## 4. 统一记录格式（`model_ledger.jsonl`，每行一条）

### 4.1 ★ `environment` — 测试环境必须写清楚

**不写环境的数字，三个月后就没法用**：0.75 到底是在 4 GS / 1 HAP 拓扑、240 步、`random_day`
下测的，还是在别的窗口、别的到达率下测的？后者与前者的 0.75 根本不是一回事。

**`environment` 是必需字段**，`env_fp`（`fingerprint_id`）由前 8 位 sha1 生成，**完全相同才说明可比**：

```json
"environment": {
  "env_name": "qkd_full",
  "episode_steps": 240,
  "episode_start_mode": "random_day",
  "day_steps": 1440,
  "activation_window": [0, 295],
  "topology": {"num_gs": 4, "num_hap": 1, "num_sat": 1,
               "allowed_link_types": ["gs_hap","gs_sat","hap_sat","sat_sat"]},
  "requests": {"type": "poisson", "arrival_rate": 0.8, "amount_mean": 100000.0,
               "deadline_steps": 30, "pair_hotness": "zipf", "pair_zipf_s": 1.0,
               "pair_seed": 0},
  "routing": {"mode": "link_path", "path_selection": "shortest_available_path",
              "serve_order": "earliest_deadline_first"},
  "rate_provider": "h5",
  "fingerprint_id": "9091810f"
}
```

**规则**：

- **`env_fp` 不同 ⟹ 两行数字不可直接配对比较**，哪怕成功率看起来接近。
- 环境**变了就要在 `BATCH.md` 和模型台账的「备注」里写明变了什么**（如"删 Stockholm 后专家锚 0.6979→0.7674"，见 `实验日志.md` §2.2）。
- 现役 4 个批次（frozen / iso-attribution / retrain8 / diagnostics）的 `env_fp` **同为 `9091810f`**，所以它们之间可比。
- 取不到的字段写 `null`，**不许用"大概是默认值"填**——填错的环境比空着危险，因为空着会被人发现。

### 4.2 记录字段规则

- `kind` ∈ `{rl, expert, bc, train}`。**expert 也必须写这条记录**（旧格式里 expert 缺一半字段，是最常见的坑）。
- **`kind: train` 是训练记录**，结构与评测记录不同：`window` 为 `null`，`result` 放 `first_update` / `last_update` / `ppo_moved` 三个汇总，原始逐轮数据仍在 `metrics.jsonl`（manifest 不镜像全序列）。
  - `result.ppo_moved` = 是否存在某轮 `kl > 0` 或 `clip_frac > 0`。**这是 §7 自检 #1 的机器可读形式**：`false` 表示 PPO 从未真正更新过。
  - ⚠ **`kind: train` 的 `protocol.request_seeds` 是「训练器内部验证」的种子**（如冻结批的 `[7..11]`），**不是**冻结评测的留出种子（`100–114`）。两者用途不同，别混读：前者是训练过程中的选点，后者是标签外的最终读数。
- `per_seed_*` 数组**长度必须等于 `request_seeds` 长度，且一一对应**。这是配对检验的前提（[`测试规范.md`](测试规范.md) §4）。
- 聚合量统一前缀 **`mean_`**；逐种子统一前缀 **`per_seed_`**。不要出现裸 `success_rate`。
- 归一化口径写清楚：`mean_served_keys_per_step = mean_served_keys / episode_steps`（240）。
- `provenance.git_commit` 取 `git rev-parse HEAD`；工作区有未提交改动时 `dirty: true` 并附 `git diff --stat` 摘要。**`dirty: true` 的读数不能进论文主表**（[`测试规范.md`](测试规范.md) §8.2）。
- 同一 `arm` 的**每个窗口**各写一条记录；不要一个 JSON 里塞两个窗口。
- **一个测量只有一条记录。** 同一 `(checkpoint, window, request_seeds, evaluated_at)` 再次出现即为**复制品**，标 `duplicate_of`（见 §8.1 规则 2），不另计一次。

## 7. 收工前自检（5 条，缺一不许下结论）

1. **PPO 真动了吗**：看 `clip_frac` 是否 **> 0**；若全程为 0，再看 `kl` 是否 **> 1e-4**。
   ⚠ **`kl > 0` 不是判据**——浮点舍入使死掉的 run 也报正数。实测标定（2026-09-26）：

   | run | kl | clip_frac | 真的动了吗 |
   |---|---|---|---|
   | v5/pairhist | ~2e-3 | ~0.10 | ✅ 动 |
   | v4 `s42_bc8_u20` | 1.6e-05 … 5.6e-05 | **恒 0** | ❌ 没动 |
   | v3 `retrain8_*` | 4.9e-06 … 1.8e-05 | **恒 0** | ❌ 没动 |

   ⟹ 判据是 `clip_frac > 0`，或 `kl > 1e-4`。
   **这不是"效果差"，是"没训练"**，该次训练不构成任何架构结论。
   （2026-09-24 冻结批 = `episodes_per_update: 1` + `minibatch_size: 1024` 每轮只更新 1 次梯度；
   2026-09-25 的 `retrain8` 批次虽改成 8 集/轮，但 `rollout_steps: 240` 太小，
   每轮只够 `nb=2` 个 minibatch，**同样没动** —— 「预算已修复」的说法据此更正。）
2. **时间戳**：每条记录有 `ts_utc` / `evaluated_at_utc`，且是 UTC。
3. **指纹**：`provenance.git_commit` 已填；`dirty` 若为 true，读数不得进主表。
4. **对齐**：`per_seed_success` 长度 == `request_seeds` 长度（配对检验的硬前提）。
5. **可并排**：把本批记录与目标对照的记录**各粘一行**出来，key 集合应完全一致。不一致就是没按本规范写。

## 9. 附 · SSH 连不上怎么办（实测，2026-09-25）

拿产物、起 run、写探针都要先连上节点，所以这条放在规范里。

### 症状

```bash
ssh qinglong@clnode342.clemson.cloudlab.us      # ✗ Permission denied (publickey)
ssh qkd                                          # ✓ 通
```

### 三个原因叠加（缺一个都不至于这么难查）

1. **`ssh user@host` 不会套用 `~/.ssh/config` 里的 `qkd` 块** ⟹ 不加载 `IdentityFile`，
   也不会带上 `IdentitiesOnly yes`。
2. 唯一有效的私钥在 `~/.ssh/qkd_rl/qkd_rl_deploy`（无口令）。它**不在 ssh 的默认身份
   路径里**（默认只找 `~/.ssh/id_rsa` 之类），所以不会被自动提供；其余旧 key 已退到
   `~/.ssh/_retired/`。
3. **Git Bash 自带的 ssh 摸不到 Windows ssh-agent**。实测：

   ```bash
   ssh-add -l
   # Could not open a connection to your authentication agent.
   ```

   ⟹ 一旦没写 `IdentitiesOnly yes`，ssh 先去问 agent、拿不到就**放弃**，直接报
   `Permission denied (publickey)`。**`IdentitiesOnly yes` 是必须项，不是优化。**

### 正确做法

**一律用别名 `qkd`**，它会自动套上上面全部设置：

```bash
ssh qkd 'cd /opt/qkd/graph_mappo && /opt/qkd/venv/bin/python -m pytest tests/ -x -q'
```

必须直连裸地址时（首个新节点、别名还没指过去），**手动补齐两项**：

```bash
ssh -o IdentitiesOnly=yes -i ~/.ssh/qkd_rl/qkd_rl_deploy qinglong@<host>
```

推送本地脚本用 `bash scripts/diag/push.sh .tmp/xxx.py`（内部走 scp，同样靠别名）。

### 换节点时只改一行

CloudLab 每次重启实验都换主机名；`~/.ssh/config` 的 `Host qkd` 块**只改 `HostName`**：

```sshconfig
Host qkd
  HostName <新主机名>                      # ← 只改这行
  User qinglong
  IdentitiesOnly yes
  IdentityFile ~/.ssh/qkd_rl/qkd_rl_deploy
```

- 主机名用 `clnodeNNN.clemson.cloudlab.us` 这种 **bootstrap 实测能连、且已在
  `known_hosts` 里**的名字。**不要**用门户给的规范名
  `node0.qinglong-XXXXXX.rdmaopt-pg0.clemson.cloudlab.us` —— 后者不在 known_hosts，
  会 `Host key verification failed`。同一台机器有两个 DNS 名，用前者。
- 连对没连对，一条命令验证：`ssh qkd 'hostname; nproc; grep MemAvailable /proc/meminfo'`。

### 自检命令

```bash
ssh -G qkd | grep -Ei "hostname|user|identityfile|identitiesonly"
ssh-add -l        # 报 "Could not open a connection..." 是**正常**的，不代表 key 坏了
```
