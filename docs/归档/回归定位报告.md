# 回归定位报告：固定场景 0.82 → 0.76

> 2026-09-15，在 Clemson 节点（Xeon E5-2683 v3，28 物理核 / 56 线程，无 GPU）上完成。
>
> **结论先说**：**没有找到回归。** 那 0.06 的差距是**单次运行 + 单个训练种子**这个
> 测量方式本身的波动，不是代码退化。同一个数据流下两版代码确实能差 0.06，但换五个
> 数据流一配对，平均差是 **+0.010 ± 0.017**（标准误，t = 0.58，不显著），符号还随
> 数据流翻转。真正的产出是下面第 6 节那条分辨率结论 —— 它直接决定了奖励机制该怎么测。

## 1. 现象

用 `train_diag_fast.yaml`（单固定场景、240 步 rollout、held-out 验证窗口、12 个
评估种子、看 update 5 的确定性成功率）：

| 代码 | update 5 评估 |
|---|---|
| 会话前 `d1930a2` | 0.8174 |
| 当前工作区 | 0.7627 |
| 文档 §5.2 历史记录 | 0.7560 |

且当前工作区在 20 轮内全程平（0.7627 → 0.7645 → 0.7488 → 0.7690），而会话前是攀升的。
看起来像"某次改动把训练搞坏了"。

## 2. 分组 bisect

把工作区相对 `d1930a2` 的改动按**耦合关系**分三组（文件之间互相依赖，不能单独回退）。
每组各建一个 `git worktree`（detach 到 `d1930a2`），**只**把该组文件从工作区覆盖进去，
主工作区不受影响。脚本：`.tmp/bisect_groups.sh`。

```
group1  qkd_rl/rl/models/graph_mappo.py + qkd_rl/rl/algos/policy.py
group2  qkd_rl/rl/algos/mappo_trainer.py
group3  qkd_rl/env/env.py + qkd_rl/rl/algos/rollout_buffer.py + qkd_rl/rl/algos/rollout_workers.py
```

## 3. 结果

| 臂 | 覆盖的文件 | update 5 评估 |
|---|---|---|
| `ref1` | 无（裸跑 `d1930a2`） | 0.8174 |
| `ref2` | 无（同一份代码再跑一遍） | 0.8174 |
| `group2` | trainer | 0.8174 |
| `group3` | env + buffer + workers | 0.8174 |
| `g1b` | policy | 0.8174 |
| **`g1a`** | **graph_mappo.py** | **0.7572** |
| **`group1`** | **graph_mappo.py + policy** | **0.7572** |

两点：

- `ref1` 与 `ref2` **逐位相同**（每轮指标都一样）—— 训练和评估在这个配置下完全确定、可复现。
- `group1` 与 `g1a` 数字完全相同 ⇒ **`policy.py` 的改动在本配置下根本没被走到**
  （含它的 group1 和不含它的 g1a 完全一致）。原先"`_matching_log_prob_entropy_arrays`
  候选顺序不一致"的怀疑**就此排除**。

结论：**只有 `qkd_rl/rl/models/graph_mappo.py` 能复现这个下降。**

## 4. 但模型本身在数学上是等价的

既然定位到了模型文件，就直接检验它是不是真的改了行为。

### 4.1 同一份权重 → 同一份评估

用 `MAPPOTrainer.evaluate_validation()`（和训练时那条曲线同一协议）评估三份 checkpoint，
每份都用新旧两版模型各评一次。脚本：`.tmp/run_eval_same_weights.sh`。

| 权重来源 | 旧模型 | 新模型 |
|---|---|---|
| BC 预热权重 | 0.767955 | **0.767955** |
| 旧模型训练 5 轮的权重 | 0.817390 | **0.817390** |
| 新模型训练 5 轮的权重 | 0.757167 | **0.757167** |

**六位小数相同，`mean_served_keys` 也逐位相同。** 前向在动作选择上完全等价。

### 4.2 反向梯度也几乎等价

BC 权重上、同一批观测、同一个标量损失，两边各反传一次（`.tmp/grad_probe.py`）：

```
整体相对差 ||dG|| / ||G|| = 1.774e-10
参数数 101，相对差中位数 0.000e+00，最大 2.939e-07
  actor.*                    相对差 0.000e+00     <- 逐位相同
  critic.value_head.*        相对差 ~3e-07        <- 分段求和替掉切片求均值的浮点重结合
```

### 4.3 构造期的随机性也一致

`load_checkpoint` 里有一步会**重新随机初始化 critic 价值头**（reward 配置变了），
吃的是全局 RNG。如果两版模型构造时消耗的随机数个数不同，价值头会拿到完全不同的
初始权重 —— 那是数量级级别的差异。实测（`.tmp/rng_probe.py`）：构造后的 RNG 状态、
价值头 / actor / encoder 的初始权重摘要**全部一致**。这条也排除。

### 4.4 那 0.06 是怎么来的

只剩一个可测差异：critic 价值头 ~3e-7 的相对梯度差。它本身小到不可能移动 0.06，
所以只能怀疑"这个指标对训练过程的扰动本来就极敏感"。**这就是第 5 节要测的。**

## 5. 判定实验：换训练种子

同一份代码，只换训练种子（评估种子来自验证配置、不随训练种子变，所以是同一把尺子
量不同策略）。脚本：`.tmp/run_seed_spread.sh`（新代码）、`.tmp/run_seed_spread_old.sh`（旧代码）。

> 注意：`--seed` 会同时覆盖 `global_seed` 和 `env_seed`，而默认情况下 `env_seed`
> 来自配置里的 `request_seed`。所以 **`--seed 42` 和"默认"不是同一个数据流**，
> 不能混着比。下表全部用显式 `--seed`。

| 数据流 | `d1930a2`（旧） | 当前工作区（新） | 配对差（旧−新） |
|---|---|---|---|
| 默认（`env_seed = 7`） | 0.8174 | 0.7572 | **+0.060** |
| `--seed 42` | 0.7965 | 0.8076 | −0.011 |
| `--seed 43` | 0.7730 | 0.7414 | +0.032 |
| `--seed 44` | 0.7134 | 0.7535 | **−0.040** |
| `--seed 45` | 0.7591 | 0.7501 | +0.009 |
| **均值** | **0.7719**（sd 0.039） | **0.7620**（sd 0.028） | **+0.010 ± 0.017** |

**配平均差 +0.010，标准误 0.017，t = 0.58 —— 不显著，且符号随数据流翻转。**
`--seed 42` 上新代码（0.8076）甚至比旧代码（0.7965）**更高**。

> 默认流那一行（+0.060）就是最初报出来的"回归"。它是五个数据流里最大的一个，
> 但只有一个 —— 单看它会得出"代码退化了"，看全部五个则看不到效应。

顺带：旧代码自身的跨度是 0.7134–0.8174 = **0.104**，比那个"回归"的 0.06 还大；
两版代码各自的流间标准差（0.039 / 0.028）也远大于两者均值之差（0.010）。

## 6. 真正的问题：这个测量的分辨率

把上面几节合起来：

- 训练 + 评估**完全确定**：同一个种子、同一份代码，重跑逐位相同。
- 但换个训练种子，同一条 update 5 曲线可以从 **0.71 晃到 0.80**（跨度 0.083）。
- 而"代码差异"能被测量到的量级，落在同一区间里。

也就是说：

> **单次运行、单个数据流、update 5 的那一个数，无法分辨小于约 0.035（配对）
> 到 0.10（不配对）的真实差异。**

这条直接影响原定目标 —— "判断我们设计的奖励机制能不能推高成功率"。在这个协议下，
任何小于 0.035 的提升都测不出来，任何一次"变好了/变差了"的判断都可能只是换了
数据流。

**建议**（按性价比排序）：

1. **每个配置至少跑 3 个训练种子**，比较分布而不是单点。这一步不需要改代码，
   只是把 `.tmp/run_seed_spread*.sh` 的做法固化进流程。
2. **配对比较**：同一批训练种子下比两版配置的逐种子差值（`scripts/eval/compare_policies.py`
   已经做这个，但那是评估种子的配对；训练种子的配对现在是缺的）。
3. 之后再谈调奖励 —— 有了上面的分辨率，才谈得上"推高了 0.02 还是没推高"。

**成本参考**（本节点，新代码约 3 分钟/轮完整 5 轮 + 评估，旧代码约 9 分钟）：
3 个训练种子 × 两版配置 ≈ 40 分钟，换来一个能分辨 0.035 的结论。比在 0.06 的噪声里
反复调奖励划算得多。

## 8. 附带修掉的两个环境问题

- **`server_upload.sh` 的代码 tar 包会污染节点工作区**：它把本地工作区打成 tar 直接
  解压覆盖到 `/opt/qkd/graph_mappo`，盖掉 `server_sync.sh` 刚检出的那棵树，而且带
  进来的是 CRLF 行尾 —— 于是每个文件在 git 眼里都"被改过"，下一次 push 被
  `receive.denyCurrentBranch=updateInstead` 静默拒绝。已加 `--data-only` 开关，
  `server_bootstrap.sh` 改用它（代码只走 git 通道，那条通道会规范成 LF）。
- **`server_sync.sh` 单独运行时会回落到 ssh 别名的默认值 `qkd`**，而用
  `user@host` 直连的节点上并没有这个别名。现在 `server_bootstrap.sh` 会把目标写进
  `.tmp/qkd_host`，`server_sync.sh` 读回来。
