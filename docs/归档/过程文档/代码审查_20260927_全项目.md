## A. 实质问题（按严重度排序）

### A1 ★★ `_train_usage_head` 的时序仍然会破坏 PPO ——注释里的因果推理是反的

`mappo_trainer.update()` 现在在 **PPO epoch 之前**调 `_train_usage_head`（BCE 训
头+encoder）。注释声称这样"保证 BCE 不在 rollout 与 ratio 之间碰策略"——**恰恰相反**：

- `old_lp` 是 rollout 时在**旧头/旧 encoder（H0）**下存的；
- BCE 先跑 → 头/encoder 变成 H1；
- PPO 的 `new_lp` 在 **H1** 下算 ⟹ 第一个 minibatch 的 ratio 就系统性 ≠ 1，
  且这不是策略梯度造成的位移。

你们自己的探针（probe_v8b2_mech）已经量出后果：bias=4 时**一步 BCE 就把存量动作的
分数移动 ~386**（24/24 步）；对应臂的 kl 5–12、clip_frac ≈ 1.0 ——
**整个 update 的 ratio 全部撞 clip，PPO 实质死亡**。把 BCE 从 minibatch 循环挪到
epoch 之前只是把"每个 minibatch 都撞"变成"从第一个 minibatch 就撞"，**没有解决**。
bias=0 臂同理受害（encoder 更新也移动 actor 分数），只是量小（kl 0.002 / clip 0.16
里有一部分是这个来源，白白吃掉信任域）。

**修法（三选一，推荐 ①）**：
1. **把 `_train_usage_head` 挪到 PPO epoch 之后**：下一轮 rollout 与下一轮 ratio
   用同一个头，old/new 天然一致，bias 在整个 update 内是"冻结的状态特征"——
   这正是注释想要的性质，只是方向放反了；
2. 训完头后**重算并覆盖每个 step 的 `mean_log_prob`**（多一次全 buffer forward）；
3. bias 路径 stop-gradient + 头参数从 PPO 参数组剔除，BCE 只训头不训 encoder
   （代价：放弃"表示塑造"那一半机制）。

### A2 ★ v8 头训练路径上的三个"静默盲区"（都是你们自己红线明令禁止的形态）

1. **`_usage_logits_for` 里 `except Exception: return None`**：一旦模型 forward
   对某类 obs 抛错，头就**永不训练、零报错**——与 §10.11 坑 2（"症状与关闭逐位
   相同"）完全同形。你们的红线是"`except` 吞异常 + 门必须打印自己的输入"。
   至少要 log 一次异常并计数。
2. **`head_loss_value` 算完就扔**：`update()` 拿到返回值后没有进 `UpdateStats`、
   没有进 metrics.jsonl。头学没学到（BCE 降不降、AUC 多少）在训练过程中
   **完全不可观测**，只能等 run 跑完离线测——batch 1 的"两个种子 AUC≈0.5"
   本可以在第 2 个 update 就发现。把 head_bce（和一个在线 AUC/正例率）写进每轮日志。
3. **每次 update 新建 `torch.optim.Adam`**：动量与二阶矩清零 + bias-correction
   重启 ⟹ 头的有效步长每轮都经历"冷启动尖峰"；且 encoder 被两个优化器
   （PPO 的 Adam 有自己的动量状态）交替推动。头的 optimizer 应在 `__init__`
   建一次持久化。
   （次要：`_train_usage_head` 逐 obs 单图 forward，256 个/minibatch 不走
   batched path，纯浪费吞吐。）

### A3 ★ 全 v3 族 graph_builder 的跨回合状态泄漏（v3/v6/v7/v8 全中）

`env.reset()` 重置了 qkp/requests/request_history/history_buffer/metrics/reward_fn，
**但不重置 builder 的任何状态**。builder 里有三组带衰减的历史状态，清零条件都只有
"时间倒退"（`t < prev_t`）：

- `_v31_edge_use` / `_v31_edge_shortage`（v3/v6/v7/v8 的边特征 + v7 的
  `preparation_edge_values` 先验都吃它们）；
- `_path_recency`（v8 batch-2 新特征）。

新回合起始 t **晚于**上一回合末尾时不清零，残值按 `0.99^gap` 衰减——random_day
起日下 gap 可以很小（相邻天、回合 1440 步 ⟹ gap 0–几百槽，`0.99^100≈0.37`），
特征带着上一回合的值进入新回合。后果：
- 同一 seed 的读数**依赖回合执行顺序**（串行 vs worker、eval env 复用时跨种子污染）；
- `test_eval_determinism` 只测同顺序复跑，测不出这个。

另外 `_update_path_recency` **没有同槽守卫**：同一 t 被调两次会再 decay 一次、
再累加一次（`elapsed = max(1, 0) = 1`）；旁边的 `_v31` 块有
`env_state.t != self._v31_history_t` 守卫——不对称本身就是证据。

**修法**：给 builder 加 `reset_episode()`，在 `env.reset()` 里调用；recency 补
同槽守卫。改动 10 行以内，但会让 v3 族全部读数发生（微小的）位移——
在下一个大批次前修掉，别在批次中间修。

### A4 v8 标签与 bias（《v8 诊断报告》P1–P4 维持有效，此处只补新证据）

- **bias=4 过强已被你们自己的探针证实**（分数位移 386）——这正是上一份报告
  P1 预测的"new 标签下 tanh 饱和、标定失效"。修 A1 的时序只解决 ratio 一致性，
  **不解决 bias 量级**：rollout 期间行为仍被 ±4 个分数 std 的偏置支配。
  建议改 `w · zscore(tanh(logit))`（图内标准化，与头的绝对尺度解耦）或
  `w · σ(logit)` 只加正偏置。
- "new" 标签窗口 off-by-one（覆盖 K−1=7 槽，horizon=1 时窗口为空）；
- 标签非 policy-independent（pending 集合 + active_edges/include_stocked_edges
  都随策略变），docstring 与 `test_v8_usage_forecast.py` 的断言过强；
- BCE 无 `pos_weight`（正例 ~10%），loss_weight 0.05 → 信号易被淹没。

## 一、大局诊断：v1–v8 "效果不好"的根因不在模型

### 1.1 你们自己测出的天花板已经宣判了这件事

§10.9 的测量：现实策略天花板 ≈ **77–78%**，专家 0.7674 已吃掉 **96–98%**，
真正"有货可攒却没攒"的可争空间只有 **2.45% 到达量**。而 n=8 扩种子后
v3 ≈ 0.776–0.778 —— **v3 已经站在天花板区间里了**。

这意味着：任何架构改动的期望效应 ≤1–2 个点，而你们的测量分辨率是
单种子 ~0.035、n=3 ~0.02、n=8 才 ~0.008。**"改了没效果"是"效应量 < 分辨率"
的必然表现，不是哪一版模型做错了。** v4→v8 一路的"测不出"全部符合这个解释
（v8loss +0.0038、3/3 同向、t=3.14 差一点显著——这在 2.45% 的可争空间里
已经算方向正确的信号了）。

### 1.2 环境设计让"有趣的决策"变得免费——这才是 RL 打不出差距的结构原因

端口预算测量（§10.9）：上限 88 边/槽，专家只用 68.8%，**剩 31% 白送**；
专家每槽激活的边里 **98.5% 与当前请求无关**——它在无差别广撒网，而这
**没有任何代价**。当"预备"不占用任何稀缺资源时，无脑贪心就近似最优，
学习型策略在成功率上注定与专家打平。**RL 的价值只出现在决策有代价的地方。**

两条出路（二选一或都做）：

- **换主效应指标**：冻结评测里已经有一个显著、9 臂同向、无需任何新实验的结果——
  **RL 与专家 SR 打平的同时省密钥 24–28%**（专家 206.8 vs v2 148.4）。
  "同等服务水平、密钥成本降四分之一"比抠 0.4 个点的 SR 有说服力得多。
  专家瞎撒网正是它费钥的原因，这个故事和端口测量互相印证，是现成的论文主线。
- **让问题变难**：收紧端口预算（88 → 60 以下，让预备与服务竞争）、
  提高 arrival_rate、给激活加能耗/切换成本。贪心不再近似最优后，
  v8 这类"定向预备"才有增益空间。**在现在这个环境里继续改模型，
  是在一个已经饱和的任务上内卷。**

### 1.3 两个已发现但还没消化进模型的事实（§10.13）

- **时间特征错位**：需求周期在"节点本地时间"层面（13×日摆动），聚合到全局
  只剩 1.23×。模型喂的是全局 `minute_of_day_sin_cos`——这一路输入基本没用。
  tz offset 是静态常数，加 per-node 本地小时 sin/cos 是一行特征的事，
  而它正是"预测新激活"最该用的信号。
- **`pair_seed: 0` 不随 `--seed` 变**：所有训练、所有验证看到**同一组热点对**
  （MexicoCity→NewYork 占 15.4%）。两面性：(a) 对 v8 是好消息——热点是常数，
  "哪些边将来会被用"强可学；(b) 对论文是隐患——模型可能只是背了热点表，
  **至少要加一个 held-out pair_seed 的评测臂**，否则泛化性一问就倒。

## 二、v8 的具体问题（按严重程度排序）

### P1 ★ `bias_weight=4` 的标定将再错一次——这次是反方向（100 倍太弱 → ~20 倍太强）

`configs/v8_bias.yaml` 的标定依据是"训练后 per-arc |tanh(logit)| ≈ 0.05"。
但那是在 **batch-1 的 "used" 标签**头上测的：那个标签正例率高（候选弧多在路径上），
logit 分布在 0 附近，tanh 处于线性区。

batch-2 换 `label_mode: new` 后正例率只有 ~10.6%。BCE 会把大多数边的 logit
推向 log(0.106/0.894) ≈ **−2.1**，tanh(−2.1) ≈ **−0.97 —— 饱和**。
预测为正的边 logit 会升到 0 附近甚至为正。于是 tanh 的组内差距不再是 0.05，
而是 **~1.0**。实际偏置幅度 ≈ w × 1.0 = **4 个分数 std**，按你们自己的表
（w=20 → "头单独决定"）这等价于原计划尺度下的 w≈80——**头会淹没注意力分数**，
把正在服务的边整体压下去。batch-2 行为臂大概率又是一条"按构造就错"的臂，
只是这次从空操作变成过冲。

**这与 §10.12 的教训同源：标定常数必须用"被控对象在目标配置下训练后"的尺度。**
"used" 头和 "new" 头是两个不同的被控对象。

修法（任选，推荐 a 或 b）：
- (a) **先只跑 `v8loss` 臂**，在训好的 new-label 头上实测 tanh(logit) 分布，再定 w；
- (b) 把偏置改成**图内标准化**：`w · zscore(tanh(logit))`，w 直接就是"分数 std 的倍数"，
  与头的绝对尺度解耦，一次修好，以后换标签也不会再踩；
- (c) 用 `σ(logit)`（0..1，工作点在 base rate 附近非饱和区）且只加正偏置——
  额外的好处是不会把"正在服务"的边打下去（"new" 标签下它们是确定负例，
  tanh 方案会给它们满幅负偏置，与第一阶段的服务目标直接打架）。

### P2 "new" 标签窗口 off-by-one，且 horizon 的语义就是"预备提前量"——现在给的提前量可能不够

`rollout_buffer._fill_usage_labels`：

```python
lo = t if mode == "used" else t + 1
for u in range(lo, min(n, t + horizon)):   # "new" 实际覆盖 t+1 .. t+horizon-1
```

docstring 写的是 `(t, t+K]`，代码实际是 `(t, t+K)`——horizon=8 只看 **7 个未来槽**
（horizon=1 时 "new" 模式窗口为空、全零标签，这是这个 off-by-one 的极端形态）。

更重要的是语义问题：预备的收益 = 提前量内能多攒的密钥。设计动机是
"6–9 槽窗口攒不够"（§10.9 C 桶），那么**预测到"要用"的时刻离实际用还剩几槽，
决定了预备有没有肉**。标签在 t 给 1 的边，其新激活可能发生在 t+1——提前量 1 槽，
攒不出什么。建议：
- 修正边界（`min(n, t + horizon + 1)`），同步改 docstring 和测试；
- 用现成的离线 AUC 探针扫 K ∈ {8, 12, 16, 24}，画"可预测性 vs 提前量"曲线，
  选"AUC 还能看 × 提前量够攒"的折中点，而不是按请求窗口中位数定 K；
- 更进一步，标签可以改成"**将在 [t+d, t+d+K) 内新激活**"（留出最小提前量 d），
  逼着头学"早知道"而不是"刚知道"。

### P3 标签并不是 policy-independent——文档、docstring、测试的断言都过强了

`request_path_edge_mask = _request_shortest_path_union(active_edges, requests.get_pending())`，
两个输入都随策略变：

- **pending 集合**：请求被服务掉就退出 mask。"当前在路径上的边 100% 持续"
  部分是"没服务完就一直挂着"的伪影——策略变强，持续性会下降，标签分布漂移；
- **active_edges**：来自动作 mask，且 `include_stocked_edges` 开着时会把
  qkp>0 的边（纯策略产物）加进邻接图，**改变最短路本身**。

`test_v8_usage_forecast.py` 的 "POLICY-independent" 只测了"不读 matched_arcs"，
测不出这两条。后果不是致命的（on-policy 辅助任务本来允许非平稳目标），
但 (a) "不可被刷"的论证不成立——bias 影响服务 → 影响 pending → 影响标签，
环是闭合的；(b) 给头增加了一层它永远学不掉的噪声。

修法：标签（和 recency 特征）改在**静态物理拓扑**上算最短路并集
（pending 请求仍取实际队列，但路径不再依赖当前 active 子图），
让"策略 → 标签"的通路只剩 pending 一条，并把文档措辞改准确。

### P4 BCE 没有处理 ~10% 的类别不平衡，头"没学到"很可能是信号被淹没

三个种子里两个头 AUC ≈ 0.5。现在的损失是裸 BCE + `loss_weight: 0.05`，
正例 ~10%：梯度被海量易分负例主导，再乘 0.05，跟 PPO 噪声一比就没了。建议：

- `pos_weight ≈ (1−p)/p ≈ 8–9`（`binary_cross_entropy_with_logits` 原生支持）；
- 或只在"当前不在路径上"的边上计损失——这本来就是 "new" 标签的定义域，
  把平凡负例（正在服务的边，标签恒 0）剔出去；
- **把头的 AUC 做成 `metrics.jsonl` 每轮记录的指标**（现在只能事后离线测）。
  你们的红线是"门/判据类代码必须打印自己的输入"——头学没学到就是 batch-2
  的核心判据，它现在没有在线可观测量，等 6 条 run 跑完才知道又晚了。

### P5 `_path_recency` 跨回合泄漏 + 同槽重复累加（静默类，破坏可复现性）

`env.reset()` 重置了 qkp/requests/request_history/history_buffer/metrics/reward_fn，
**但不重置 builder 的 `_path_recency`**（也不重置 v3.1 的
`_v31_edge_use`/`_v31_edge_shortage`——同类问题，v3 起就存在）。清零条件只有
"t 倒退"。训练用 random_day 起日、回合 1440 步：新回合起始 t 晚于且接近上一回合
末尾时（gap 几十~几百槽），特征带着上一回合的残值进入新回合（0.99^gap 衰减不完）。

另外 `_update_path_recency` 没有同槽守卫：同一 t 被调两次会**再 decay 一次、
再累加一次**（`elapsed = max(1, 0) = 1`）。旁边的 v3.1 块有
`env_state.t != self._v31_history_t` 守卫，recency 没有——不对称本身就是坑的证据。

影响量级小，但属于你们最忌讳的"静默类"：同一 seed 的读数取决于**回合执行顺序**，
反向破坏 `test_eval_determinism` 想保证的东西。修法：给 builder 加 `reset_episode()`，
在 `env.reset()` 里调；recency 加同槽守卫。

### P6 头够不着最该用的两路输入（§10.12/10.13 各指了一条，batch 2 只补了一条）

batch-2 加了 `include_path_recency`（对应 AUC 0.63 的那行特征）——对。但还缺：

- **per-node 本地时间**（13× 的日周期全在这一层，全局时间近乎平的）；
- **per-pair 长窗到达率先验**（热点对是常数，`request_history` 现成就有数据；
  现在 pair 权重里只有 240 槽短窗）。

`history_encoder`（LSTM，32 槽回看）是现成承载体但整块关着；不过在
recency + 本地时间 + 到达率先验都是廉价标量特征的情况下，**先加特征后上 LSTM**
的顺序是对的，LSTM 的 2.3× 内存代价放最后。

## 三、建议的行动顺序（按性价比）

1. **（最便宜、先做）离线训头判定**：用已录轨迹离线监督训 new-label 头
   （加 pos_weight、加 recency/本地时间特征），不跑 PPO。
   AUC 到不了 0.7 → 这条路的上限就是零点几个点，直接降优先级；
   到得了 → 再花 PPO 预算。这符合你们"先做便宜判定"的既有哲学。
2. **修 P1（bias 标定）+ P4（AUC 在线指标）再跑 batch 2**，否则行为臂又是废臂——
   这将是同一条臂第三次"按构造无效"。
3. **P2/P3/P5 顺手修**（都是小 patch），P5 记得连 `_v31_*` 一起。
4. **战略层（决定论文命运的）**：
   - 把 **key_efficiency 提为主效应**（现成的 24–28%，9 臂同向）；SR 打平本身
     配合天花板测量（§10.9）是一个完整、诚实、可辩护的故事；
   - 或者**收紧资源**做第二组实验（端口预算砍到 60 以下 / arrival_rate 提高 /
     激活加成本），在贪心不再近似最优的 regime 里重跑 v3 vs v8——
     这是"RL 有增益"叙事唯一可能成立的地方；
   - 补一个 **held-out pair_seed** 评测臂，堵泛化性的问。
5. **诚实的预期管理**：即使 v8 batch 2 全修好，SR 上限 ≈ +1–2 点（2.45% 可争
   空间 × 完成度提升）。v8 的价值是把"预备到底有没有用"这个问题**关掉**，
   不是翻盘。翻盘的杠杆在第 4 条。
