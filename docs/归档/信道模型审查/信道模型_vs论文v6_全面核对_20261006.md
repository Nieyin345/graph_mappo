## 二、v6-baseline 下**唯一站得住的两条**不一致

### ⚠️ 不一致 1（真实，需处理）§3.3 式(104) 的 g_e 时序耦合未实现

**v6 式(103)(104)**：
$$A_e(t) = \min\{Q_e^{\max},\; B_e(t) + C_e(t)\},\quad C_e(t) = g_e(t-1)$$
$$g_e(t-1) = x_e(t-1)\cdot \bar R_e(t-1)\cdot \Delta \cdot [\gamma + (1-\gamma)\,x_e(t-2)]$$

**代码**（`qkd_rl/env/env.py:_generate_keys`，:354–368）：
```python
decay = float(switch_cfg.get("rate_decay_factor", 0.5))   # scenario_n45 设 0.0
for edge_id in activated_edges:
    rate = edge_windows[edge_id].rates[0]
    if edge_id not in self.last_activated_edges:   # 只看 t-1
        rate *= decay
    generated[edge_id] = rate * self.scenario.slot_seconds
```

**差异**：

| 项 | v6 式(104) | 代码 |
|---|---|---|
| 依赖的时隙 | `x(t-1)` **和** `x(t-2)` | 只有 `x(t-1)` |
| γ=0 时的语义 | `g = x(t-1)·R·Δ·x(t-2)` ⟹ **连续两槽激活才出码** | `rate×0` 若 t-1 未激活 ⟹ **单步判据** |
| γ 的位置 | 作用在**产率因子** `[γ+(1-γ)x(t-2)]` | 作用在**本槽速率衰减**（`rate_decay_factor`） |

**影响**：
- `scenario_n45.yaml` 取 `rate_decay_factor: 0.0` ⟹ 新链首槽不出码（PAT 捕获开销，与 v6 的物理动机一致）；
- **但 v6 的"二步确认"（x(t-2)）在代码里不存在** —— 按 v6，若一条链上一槽激活、上上槽没激活（γ=0），本槽也应**不出码**；代码却会给**满速**。
- 后果：代码比 v6 **乐观**——对"刚重连的链路"少罚一槽。对 RL 而言，这**降低**了"保持长链连续"的激励强度，与 v6 §128 声称的"迫使策略形成长程保持"**方向相反**。

**处置建议（二选一）**：
1. **改代码**：`_generate_keys` 增加 `x_e(t-2)` 判据（`env.py` 已存 `prev_activated_edges`，字段现成），实现 v6 的二步确认；
2. **改论文**：把式(104) 的 `[γ+(1-γ)x_e(t-2)]` 改为 `[γ+(1-γ)x_e(t-1)]` 或直接写成代码的"新链首槽衰减"形式。

> 需你拍板：v6 的 t−2 是**有意设计**（更严的建链保持约束）还是**笔误**？

### ⚠️ 不一致 2（真实，影响小）§2.2 式(56) r0 的权重

**v6 式(56)**：
$$r_0(\alpha) = \Big[ 0.423\,k^2\,(\sec\zeta)\!\int_0^{h_c}\! C_n^2(h)\Big(1-\frac{h}{H}\Big)^{5/3} dh \Big]^{-3/5}$$

**代码**（`rate_model_v2.py:r0`，:358–362）：
```python
def r0(self, elev_deg, A, hv):
    sec = 1.0 / np.sin(np.radians(np.maximum(elev_deg, 1.0)))
    integ = A * hv.c_a + hv.c_b          # 无权重 ∫Cn²dh
    return (0.423 * self.p.k ** 2 * sec * integ) ** (-3.0 / 5.0)
```
`hv.c_a/c_b` 是**无权重**的 `∫ Cn²·exp(-h/100) dh` 与 `∫ Cn²·rest dh`。

**注意**：代码里**有**带 `(h/H)^{5/3}` 权重的 `m_a/m_b`（`HVIntegrals`，:307–308），但那是给 **μ_2d（长时展宽 T）** 用的（`rate_model_v2.py:352`），**不是 r0**。

**实算影响**（服务器复算，`.tmp/check_r0_weight.py`）：

| H | 仰角 | r0 无权重 | r0 有权重 | 比 |
|---|---|---|---|---|
| 20 km (HAP-GS) | 90° | 15.309 cm | 15.782 cm | **+3.1%** |
| 20 km | 15° | 6.804 cm | 7.014 cm | +3.1% |
| 567 km (SAT-GS) | 90° | 15.305 cm | 15.639 cm | +2.2% |
| 567 km | 15° | 6.802 cm | 6.950 cm | +2.2% |

权重使 r0 大 2–3%（因积分**几乎全来自近地面 h≪H**，`(1-h/H)^{5/3}≈1`）。

**传递到耦合效率**（`.tmp/check_etaphi2.py`，D/r0→`smf_tt_ratio` 查表）：
| | D/r0 | η_φ |
|---|---|---|
| r0=6.804 cm | 8.818 | 0.03666 |
| r0=7.014 cm | 8.554 | **0.04026 (+9.8%)** |

**结论**：r0 权重项对地面链路耦合效率影响 **~+10%（约 +0.4 dB）**，在低仰角表陡区略大。**真实存在但很小**，对速率量级无实质影响。

**处置建议**：**以代码为准，改 v6**（v6 式(56) 的 `(1-h/H)^{5/3}` 更像把 μ_2d 的权重误抄到 r0；Fidler & Wallner 2008 的 r0 定义本就是**无权重** ∫Cn²dh）。同时 v6 应补一句说明 μ_2d 与 r0 用**不同权重**。

## 六、速率量级对照（v6 自述 vs 代码实算）

v6 §2.3/§3.1 自述（1550nm 晴夜 AOD=0.1）：
- S–G 仰角 30° ≈ **1–2 kbps**
- H–G **10⁵–10⁶ bps**
- S–G/S–H **10³ bps**

**代码实算**（同条件，见前文探针）：

| 链路 | v6 自述 | 代码实算 | 判定 |
|---|---|---|---|
| SAT-GS 30° | 1–2 kbps | **5.4 kbps** | 高 3–5×（见下） |
| HAP-GS 30° | 10⁵–10⁶ | **8.8e5 bps** | ✅ 吻合 |
| SAT-HAP 30° | 10³ | **4.6e3 bps** | ✅ 吻合 |

**SAT-GS 偏高 3–5× 的原因（v6 基准下）**：
- v6 参考点是"**总透过率 −36 dB** 的 S–G 链路"；代码在 aod=0.1/弱湍流下达 **−33.6 dB**（损耗更少 → 速率更高）；
- **不是** κ_x 造成（v6 无 κ_x），**也不是**仰角门限（v6=15°，代码=15°，**一致**）；
- 根因是 **AOD/湍流取值** 与 v6 举例条件的差异，属**标定松紧**，不是建模错误。
- 且 5.4 kbps 仍是 **10³ 量级（10^3.7）**，**未越出 v6 图 3(c) 的数据带**。

**一句话**：**代码速率量级整体合理**（H-G 10⁵⁻⁶、S-G/S-H 10³ 全吻合），**SAT-GS 中值偏高 3–5× 但仍在量级内**。
