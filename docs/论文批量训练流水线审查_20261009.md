# 论文批量训练流水线实审（2026-10-09）

## 结论

**脚本存在，但不能直接作为正式论文实验的一键产数入口。**

唯一的批量启动器是 `scripts/batch/run_paper_experiments.sh`（306 行），连接 `scripts/experiment.py` 及 BC/PPO、主表、消融、敏感性、留出集评估。模型入口是 `qkd_rl/model_zoo/v8/`；论文方法在当前配方中由 `v8_bias.yaml` + `diag_head_readout.yaml` + `diag_selfnew_h3_w04.yaml` 定义，基础对照包括 v2、关闭注意力/预测头的 v8、BC 和 scratch。论文方法的实际性质是 **self_new 未来需求预测/提前准备**，不能仅凭早期规划书称其为自洽承诺损失。

本轮为**只读核查**：没有启动训练、没有生成/覆盖 H5、没有改动流水线脚本或训练配置。运行了 `bash -n` 语法检查与 Python 解析配置核查。**本地**无 `dataset/global_v7/link_data.h5`、无 `outputs/experiments/v*/v7_*` 的正式训练目录；服务器状态和已产出的旧结果未在本轮验证。

## 已确认问题（按紧急程度）

### P0-1：2× / 3× 请求负载实际未改变

- `configs/scenario_v7.yaml` 定义 `requests.distribution_version: zipf_v7`，并使用 `arrival_rate_per_second = 0.0026666666666666666`（每分钟平均 0.16 个请求）。
- `configs/scenario_v7_x20.yaml` 只覆盖旧 `arrival_rate: 0.32`。
- `configs/scenario_v7_x30.yaml` 只覆盖旧 `arrival_rate: 0.48`。
- `qkd_rl/env/request.py::_zipf_v7_pair_rates` 实际只读取 `arrival_rate_per_second`。
- 执行 `.tmp/paper_pipeline_config_audit_20261009.py` 解析本地配置后，三组有效 `arrival_rate_per_second` **全部为 0.0026666666666666666**。因此原配置下 1×、2×、3× 都是 **0.16 请求/分钟**，不能用于负载压力论证。

**应修**：2× 明确覆盖 `arrival_rate_per_second: 0.005333333333333333`；3× 覆盖 `arrival_rate_per_second: 0.008`。启动前以真实合并配置和请求生成样本数断言 1:2:3。旧历史输出如有效字段一致，禁止直接以原标签展示成压力实验。

### P0-2：脚本提供的年度数据生成命令无效且捕获时间有误

脚本注释中的命令：
```bash
python tools/dataset_v2/build_dataset_v2.py --out dataset/global_v7 --days 365 \
  --constellation walker60 --cloud-model coverage_layers \
  --capture-gamma 0.20 --intra-slot-samples 4 --allow-era5-fallback
```

- `build_dataset_v2.py` 强制 v7 信道的 `cloud_model == station_markov`，明确拒绝 `coverage_layers`。所以这条命令不能原样使用。
- `--capture-gamma 0.20` 是弃用的兼容参数，当前代码换算为 `capture_time_s = 60*(1-0.20) = 48 s`。v7.5 主基线 `t_acq=5 s`；若数据由该参数生成，则全新建链速率大幅改变，与论文规范不符。
- 注释声称数据集 60 SAT/45 HAP/45 GS 为「100 节点」，但实际上是 **150 节点**。

**应修**：用 `--cloud-model station_markov --capture-time-s 5`，其他参数需按现行规范逐项核对；如服务器已有 H5，先读 `build_metadata.json` 和 H5 的 `capture_time_s` 属性，不先覆盖生成。不要把运行脚本里的旧示例当作可信构建记录。

### P0-3：计划矩阵与启动矩阵不一致

- `phase_main` 实际循环 5 种主要模型 × 3 种负载 × 3 种子 + scratch 仅 1×、3×；虽注释写「六臂 × 三负载」，实质不是完整矩阵。
- `phase_bc` 训练 BC checkpoint，但 `phase_eval` **没有评估纯 BC 基线**；`scripts/baselines/run_baselines.py` 只出现在脚本注释，不曾被调用，因此 Random/Greedy 也**不会随流水线评估**。
- 专家 `eval_expert.py`、流体上界及 MPC 只以 `v7_3x_full_ro_s42` 为参考任务，缺乏 1×、2× 相应的专家/启发式对照。
- 论文规划书中的多层级协同、不同气象鲁棒性等实验没有在此脚本里配齐；节点失效、规模切换并不等于天气鲁棒性。

**应修**：建立机器可核对的「论文图表每一行/曲线 ↔ run_id ↔ model/overlay ↔ baseline ↔ H5 ↔ seed ↔ 输出」矩阵，缺项不能视作全量完成。

### P0-4：敏感性基线和去图消融不是严格单变量

- 注释把 `full_ro` 当 `self_new w=0.0` 的 Figure 6 基线。但 `full_ro` 叠加 `configs/v8_bias.yaml`，真正的 `bias_weight=0.2`，v8 默认 `label_mode=new, horizon=8`；而 `selfnew` 是 `label_mode=self_new, horizon=3`。**不是 w=0.0 对照**。必须为 `self_new horizon=3 bias=0` 单独设臂。
- `nograph` 同时叠加 `no_attention.yaml`、`train_nograph.yaml`，缺少 `self_new` 的主要配置，且 BC 起点来自 `BCN` 而不是主方法 `BCV3`。如果直接与主方法比，不是「只去掉 GNN」，还同时改变注意力、预测头用法和初始权重。应控制同一基础模型/BC/标签/权重，只改变 `model.encoder.num_layers`。

### P1-1：大规模泛化配置不可能在 Walker60 上成立

- `scenario_v7_size_large.yaml` 请求 90 SAT + 45 HAP + 45 GS = **180 节点**。
- 当前数据基线只有 60 SAT，`ScenarioBuilder._apply_first_n` 会遍历现有节点并取其前 N 个，没有强制达到 90 SAT。即结果最多 150 节点，**不是 180 节点泛化**。
- 此文件自身已有注释承认需要 walker90 星座/新数据集；批处理脚本仍按可执行对照直接提交此组。

**应修**：若不增加 Walker90 与完整注册表、H5 链路，先将 Large 对照标为未支持，不把它计入 Figure 8。

### P1-2：运行失败可能被当成已完成、再次运行可能跳过失败项目

- `launch()` 只因 `$E/$model/$name` **目录存在**就跳过。启动过程会先建目录，后续若训练报错，该目录仍存在且下次会直接跳过，无法自动补跑。
- `wait_train()` 和 `phase_bc()` 检查进程退出，不核对每个 manifest.status、checkpoint_final.pt、退出码以及评估产物。
- `phase_eval()` 只后台提交任务，未等待、核对所有评测 JSON 和 task fingerprint，却输出「phase 完成」。新产生的日志只能从 /tmp 找；长时多机追溯不足。
- 只有 `--phase all` 调用 `probe_mem`，独立 `--phase main/ablation` 可能绕过内存门。

**应修**：run 完成定义应是 manifest completed + checkpoint 存在且可加载 + 指标齐全；失败的已有目录应允许在显式恢复模式安全续跑；退出码和完整 run ledger 统一记录；评估阶段出具 completed/failed/missing 汇总。

## 已核对的合理部分

- `scripts/batch/run_paper_experiments.sh` **存在**；脚本 `bash -n` 检查通过。
- 它确实调用统一 `scripts/experiment.py`，各模型版本和 checkpoint/配置记录由该层处理；BC 保存 checkpoint 更新号 0、PPO trainer 能适配宽度和优化器部分状态。使用 `--resume` 加载 BC **本身不是确定的 bug**，但应核对每个 run 的初始权重/被丢参数等日志。
- v8、v2、三组 BC 起点、大小/节点失效 overlay、上界/专家/MPC 入口文件都存在。
- 已在前次审查中修复消融 `w10` 曾写成 0.10 的问题，当前脚本会生成 1.0。注意 Figure 6 的 w0 基线缺陷**仍然存在**。
- 生产数据集和论文大批训练依赖 **Linux 服务器** 的 `/opt/qkd/graph_mappo`、`/opt/qkd/venv/bin/python`，不能在 Windows 本地原样全流程运行。

## 推荐修复顺序及实验复查

1. **先冻结当前服务器输出和原配置**，检查所有已训练 run 的 `experiment_config.yaml`、`manifest.json`、`build_metadata.json`、H5 属性，确认 1×/2×/3× 生效到达率与 t_acq。**先核验事实，再决定哪些必须重跑。**
2. 修正负载 overlay 和年度数据生成参数，加入强制预检（解析后的业务强度、节点数、站点云模型、5 s 捕获时长、相同物理任务指纹）。
3. 重列论文主表、BC-only、Random/Greedy/Expert 以及完整消融，真正补上缺失调用，并使每一组都具备同协议指标。
4. 消融拆成单变量，敏感性 w=0 用匹配的 `self_new horizon=3` 实现；大规模泛化要么扩展真实数据集，要么先取消该实验。
5. 将训练启动、重试、评估、结果核对拆成状态机或最少增加 checkpoint 与 manifest 状态审计。先跑 1 seed、少量时隙 smoke，再正式批跑。

**本轮没有修改训练脚本或 overlay，不生成新的“论文结果”。** 当前脚本若直接投入大规模训练，有显著风险产生 mislabeled / 不可比较的数据。
